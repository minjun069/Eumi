# 런타임 모니터링

수정일: 2026-11-09. 원격 Langfuse 관측과 로컬 상세 기록의 범위·검증 상태를 구분한다.

## 1. 구현 목적

런타임 모니터링은 에이전트가 어떤 순서로 실행됐고 어디에서 지연·실패했는지 확인하기 위한 기록이다. 원격 추적 서비스인 Langfuse에는 운영 정보를 보내고, 로컬 파일에는 실제 입출력과 처리 결과를 보관한다. 업무 판단과 실행 상태(`State`) 갱신은 [실행 흐름](ieumi-agent-workflow-design.md#2-에이전트-공통-실행-흐름)을 따른다.

| 목적 | 구현 방향 |
| --- | --- |
| 실행 과정 확인 | 한 실행의 최초 호출·질문 재개와 하위 노드·모델·도구 호출을 연결 |
| 운영 문제 구분 | 완료·부분 완료·실패·대기를 구분하고 실행 시간·사용량 기록 |
| 원격 수집 제한 | Langfuse에는 운영 정보만 전송하고 대화·실행 상태·오류 원문 제외 |
| 업무 실행 유지 | 추적 장애로 업무 호출을 반복하지 않고 실제 예외·취소는 호출자에게 전달 |

실행 완료는 답변 정확성이나 평가 합격을 의미하지 않는다. 품질 판정은 [평가 명세](../eval/docs/methods.md)를 따른다.

## 2. Langfuse 구현 상태

| 항목 | 상태 | 현재 범위 |
| --- | --- | --- |
| 추적 연결 | 구현 | [모니터링 모듈](../src/monitoring.py)의 Langfuse SDK 5 콜백을 [모의 데모](../demo/demo.py)와 [모델 시나리오](../demo/scenario_demo.py)에 연결. 호출마다 별도 콜백 사용 |
| 실행 식별 | 구현 | `execution.run_id`로 추적 식별자 생성, 세션 식별자에는 `run_id` 사용. 최초 호출·재개를 같은 추적에 연결하고 `execution.version` 기록 |
| 데이터 제한 | 구현 | 입력·출력·임의 메타데이터를 전송 속성에서 제외. 오류 문자열은 예외 종류로 치환하고 미디어 업로드 비활성화. 이름·ID·버전의 원문 포함 여부는 검사하지 않음 |
| 장애·종료 | 구현 | 추적 초기화·갱신·종료 실패는 경고 기록, 업무 재호출 없음. 종료 시 대기열에 남은 추적 기록을 전송. 잘못된 설정은 시작 시 거부 |
| 서비스 실행기 | 부분 연결 | 사용자 요청 그래프를 연결. HTTP 접수·DB 저장·알림까지의 전체 흐름은 아래 로컬 기록에서 확인 |
| 운영 수신·비용 | 미검증 | 실제 Langfuse 서버의 인증·수신·화면과 실제 모델 비용 산출은 확인하지 않음 |
| 운영 대시보드·알림 | 미구성 | 원격 대시보드 생성·자동 알림 미구성. 운영 임계값 미정 |

2026-11-01에 공통 그래프·데모·모니터링 테스트 **48개**가 통과했다. [모니터링 테스트](../tests/test_monitoring.py)는 실제 SDK의 전송 대상을 메모리로 대체해 실행 상태·재개 연결·동시 실행 분리·예외·취소 전파·원문 제외·모의 모델 사용량·도구 추적·추적 장애를 검사했다. 이는 실제 서버 수신 검증과 구분한다.

## 3. Langfuse 관측 항목과 해석

Langfuse에서는 한 실행의 추적 묶음을 `trace`, 그 안의 개별 호출 기록을 `observation`으로 표시한다.

| 항목 | 기록 | 해석 기준 |
| --- | --- | --- |
| 실행 경로·시간 | 최초 호출 `eumi.agent.start`, 재개 `eumi.agent.resume`, 그래프 `eumi.graph`와 하위 호출 | 실행 시간은 최초·재개 구간별로 확인. 추적 묶음의 전체 경과 시간에는 답변 대기가 포함될 수 있음 |
| 결과·오류 | `status`, `error_code`, `exception_type`, `response_kind` | 실패·실행 예외는 `ERROR`, 부분 완료·취소는 `WARNING`, 질문 대기는 정상 흐름 |
| 이력·실패·산출물 수 | `result_count`, `failure_count`, `artifact_count` | 호출 종료 시 실행 상태의 누적 수. 실패 수는 실패한 이력 항목 수이며, 최초·재개 값을 합산하지 않음 |
| 모델 사용량 | 모델명, 입력·출력 토큰, 비용 속성 | 모델이 사용량을 반환해야 수집 가능. 실제 비용 산출은 모델 가격 매칭 확인 필요 |
| 실행·배포 비교 | `run_id`, `version`, `phase`, 환경 | 실행 ID로 결과를 연결하고 배포 버전·환경별로 비교 |

최종 결과를 집계할 때는 실행 ID별 마지막 상태를 사용하고 대기·부분 완료·취소를 구분한다. 수집 비율을 낮춘 기록은 전체 실행 건수가 아니다. 이 값은 운영 진단용이며 자동 합격 판정이나 임계값은 적용하지 않는다.

실행 방법은 [실행 안내](../README.md), 설정 항목은 [환경변수 예시](../.env.example)를 따른다. 현재 한 프로세스에서 한 Langfuse 프로젝트를 사용하며, 콜백 설정을 전달한 LangChain 호출이 수집 대상이다.

## 4. 로컬 실행 증거

로컬 기록은 요청 접수부터 결과 저장·알림까지 실제로 주고받은 자료와 처리 결과를 확인하는 자료다. 평가자는 이 기록으로 모델에 제공한 근거, 도구의 반환값, 공개 응답과 저장 결과를 대조할 수 있다. 기록을 업무 실행 상태나 모델 입력, 실행 재개 자료로 사용하지 않는다.

### 4.1 기록 내용과 시점

각 호출에는 시작·종료 시각, 소요 시간, 호출 순서와 상위 호출 식별자를 남긴다. 입력은 호출 직전에 복사하여 실행 중 값이 바뀌어도 이전 값을 확인할 수 있게 한다.

| 기록 대상 | 보관 내용 |
| --- | --- |
| 요청 접수 | 사용자 요청·보고서 생성·취소 요청의 입력, 거절·중복·충돌·취소 처리 결과, HTTP 응답 코드와 본문 크기 |
| 질문 조회 | 조회한 대화·질문 식별자, DB에서 읽어 구성한 실행 상태 또는 조회 오류 |
| 노드 | 실행 전 상태, 노드가 반환한 갱신, 실제 반영한 갱신과 다음 실행 경로 |
| 모델 | 실제 메시지와 응답 형식, 모델 클라이언트의 원본 응답, HTTP 송수신 본문, 사용량과 오류 |
| 도구 | 선택한 인자와 실제 전달한 인자, 입력 형식, 원본 반환값과 오류 |
| 자료 조회·가공 | 조회 조건, 원자료의 버전·출처·열 정의, 연산별 입력·결과와 행 수 |
| DB 저장 | 저장에 사용한 실행 상태, 커밋 성공 여부, 사용자 응답의 저장 행 ID 또는 저장 오류 |
| 백엔드 알림 | 경로·본문·시도 번호·응답 대기 한도·인증 방식, 응답 코드·본문 크기와 수락 여부 |

JSON으로 해석할 수 없는 접수 본문은 내용 대신 크기와 검사 오류를 남긴다.

모델의 원본 응답은 형식을 검사하기 전에 남기므로 검사에 실패한 응답도 확인할 수 있다. DB 커밋 성공은 저장 함수가 반환한 뒤에 기록한다.

실행 기록이 활성화돼 있으면 도구를 직접 호출한 경우에도 기록하며, 같은 호출에 대해 에이전트가 이미 만든 도구 기록은 중복 생성하지 않는다.

보고서는 동별 실행 자리 대기(`report_wait`), 최초 분석 결과 확인(`prepare_report`), 요청 전체 처리(`api.report_request`)를 구분한다. 전체 처리 기록은 모든 동의 실행·재처리·저장과 완료 알림을 포함하며, HTTP로 접수한 요청은 접수 이후 경과 시간도 남긴다. 이 시간과 동별 업무 예산의 차이는 [보고서 실행 시간](ai-runtime-api-20261029.md#25-실행-시간)을 따른다. 상위 호출의 소요 시간에는 하위 호출 시간이 포함되므로 합산하지 않는다.

동별 실행 안에서는 선정·설명·인사이트 에이전트의 진입 State와 반환값을 각각
에이전트 호출 기록에 남긴다. 각 기록 아래의 공통 노드·모델·도구 기록으로
역할별 판단과 추가 조회를 확인한다. 단계 경계·근거 전달의 업무 원본은
[보고서 실행 기록](temp/analysis-report-workflow.md#5-보고서-실행-기록)이며 추적 파일은 이를 대체하지 않는다.

### 4.2 파일 조회와 연결

아래 경로는 서버의 출력 폴더 설정인 `SETTINGS_OUTPUT_DIR` 또는 왕복 검증기의 `--output`을 기준으로 한다. API 접수·실행과 왕복 검증의 증거 폴더는 새 식별자로 생성해 이전 기록과 구분한다.

| 파일 | 확인할 내용 |
| --- | --- |
| `requests/<요청 UUID>/request.json` | 사용자 요청·취소·보고서 생성 요청의 접수 입력과 HTTP 처리 결과 |
| `<대화 UUID>/<실행 폴더>/report.json` | 사용자 요청의 최종 실행 상태와 노드·모델·도구·산출물 선택·저장·알림 기록 |
| `<동별 실행 ID>/report.json` | 보고서 한 동의 대기·자료 확인·생성·재처리·저장 기록 |
| `batches/<묶음 UUID>/request.json` | 보고서 요청 전체의 동별 실행 ID·최종 상태·저장 여부와 완료 알림 기록 |
| `roundtrips/<검증 UUID>/evidence.json` | 검증기의 요청·응답, 로컬 알림 수신 기록, 저장 결과를 다시 읽은 값과 조회 시각 |

서버의 접수·실행·보고서 묶음 폴더에는 다음 보조 파일도 저장한다.

| 파일 | 저장 시점 | 내용 |
| --- | --- | --- |
| `trace.jsonl` | 호출 시작·갱신·종료 때마다 추가 | 실행 중인 호출과 완료된 호출의 기록 |
| `manifest.json` | 기록 시작 시 | 실행 코드·지침·평가 문서·Tableau 등록 파일의 내용 비교값(해시), Git 커밋과 실행 설정 |

실행·보고서 묶음의 `manifest.json`에는 원래 접수 기록의 파일 경로·호출 식별자·접수 시각도 남긴다. HTTP 접수 없이 직접 실행한 경우에는 이 연결이 없다. 업무 실행이 시작되기 전에 취소된 경우에도 종료 저장·알림을 별도 실행 폴더에 남기며, 이때는 취소 요청에 연결한다.

[사용자 요청 검증기](../experiments/api_roundtrip.py)는 알림을 받을 때 저장 행을 다시 읽고, [보고서 검증기](../experiments/report_roundtrip.py)는 요청 처리가 끝난 뒤 저장 결과를 다시 읽는다. `evidence.json`은 서버의 저장 성공 기록과 검증기가 다시 읽은 값을 대조할 때 사용한다. 실행 명령과 결과 조회 순서는 [사용자 요청 검증](api-roundtrip.md#1-사용자-요청)과 [보고서 생성 검증](api-roundtrip.md#2-보고서-생성)을 따른다.

### 4.3 보존 범위와 실패 처리

인증키·인증 헤더·쿠키와 설정 URL의 인증정보는 제외하거나 가린다. 외부 예외의 문자열은 저장하지 않고 오류 종류·코드·응답·검증 상세를 남긴다. JSON 결과 파일은 비밀값을 가린 사본을 임시 파일에 쓴 뒤 저장 경로의 파일로 교체한다.

| 파일 저장 중 입출력 오류가 난 위치 | 처리 |
| --- | --- |
| 서버 실행 기록 | 경고를 남기고 업무 실행을 계속한다. 누적 추적 파일에 쓸 수 없으면 메모리에서 수집을 이어 간다. 기록 실패 때문에 DB 저장이나 알림을 반복하지 않는다. |
| 왕복 검증 결과 | 저장 오류를 호출자에게 전달해 검증 실행을 실패로 끝낸다. 이미 업무 예외가 발생했다면 기록 오류로 바꾸지 않고 원래 예외를 전달한다. |

자료의 실제 버전은 조회 반환값에서 확인한다. 코드·설정의 파일 해시는 원자료 버전을 나타내지 않는다.

파일 DB와 로컬 알림 수신기로 확인한 결과는 실제 PostgreSQL·운영 백엔드 연동의 검증 결과와 구분한다. Tableau 화면 로딩·조건 적용 결과는 수집하지 않는다. 증거가 없거나 기록에 누락이 있으면 [평가 방법](../eval/docs/methods.md)에 따라 판정한다.

### 4.4 구현 위치

실행 코드는 기록할 시점과 확인한 결과를 전달하고, 공통 모듈이 기록 형식·시간 측정·파일 저장을 담당한다.

| 구현 위치 | 담당 기능 |
| --- | --- |
| [공통 추적 모듈](../src/execution_trace.py) | 입력 복사, 비밀값 가림, 호출 간 연결, 시간·반환·예외 기록, 파일 저장 |

호출 전체는 공통 함수로 감싸고, 함수 내부의 검사나 커밋 결과는 실제로 확인한 위치에서 기록한다. 공통 호출 함수는 업무를 한 번 실행하고 원래 반환값·예외·취소를 전달한다. 재시도 여부와 저장·알림의 성공 판단은 실행기가 결정한다.
