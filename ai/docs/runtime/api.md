# AI 런타임 API

수정일: 2026-11-11. 백엔드가 AI 실행을 요청하고, AI가 데이터베이스(DB)에 결과를 저장한 뒤 백엔드에 알리는 내부 연동 계약이다.

사용자 요청·보고서 생성별로 API 목록, 입력 필드, 접수 결과, 실행·저장·알림, 실행 시간, 연동 대조를 설명한다. 두 업무에 함께 적용하는 인증·알림 실패·운영 조건은 [공통](#3-공통)을 따른다. 실행 명령과 결과 판정은 [API 검증](api-verification.md)에서 다룬다.

## 1. 사용자 요청

백엔드가 사용자 질문의 DB 저장을 확정(커밋)한 뒤 AI에 실행을 요청한다. AI는 저장된 질문과 대화 기록을 읽고, 진행 상황과 결과를 `ai_message`에 직접 커밋한 뒤 저장 행을 백엔드에 알린다.

### 1.1 API 목록

| 식별자 | 목적 | 방향 | 메서드 | 경로 | 정상 상태 코드 |
| --- | --- | --- | --- | --- | --- |
| INT-01 | 사용자 질문 실행 | 백엔드 → AI | POST | `/internal/agent/runs` | 202 |
| INT-02 | 사용자 질문 실행 취소 | 백엔드 → AI | POST | `/internal/agent/runs/{conversationId}/cancel` | 202 |
| INT-07 | 저장한 AI 행 알림 | AI → 백엔드 | POST | `/api/internal/agent/notifications` | 204 |

### 1.2 입력 필드

#### INT-01 사용자 질문 실행

요청 본문에는 질문을 찾을 식별자와 선택적인 화면 문맥을 보낸다.

| 필드 | 의미 | 형식 | 필수 여부 |
| --- | --- | --- | --- |
| `conversationId` | 질문이 속한 대화 식별자 | UUID | 필수 |
| `messageId` | 실행할 사용자 질문 행의 식별자 | 양의 64비트 정수(`int64`) | 필수 |
| `context` | 사용자가 보고 있는 화면의 동·월 | 객체 | 선택 |
| `context.dongCode` | 화면에서 선택한 동 | 10자리 숫자 문자열 | 선택 |
| `context.month` | 화면에서 선택한 월 | 유효한 `YYYY-MM` | 선택 |

DB의 `question_id`는 이 사용자 질문 ID를 가리킨다. 원본 입력은 실행 상태(`State`)의 내부 작업 이력인 `results`에 `run_request`로 보관한다. 화면 문맥은 요청의 선호 조건인 `request.constraints.preferred`에 제공하여 모델이 목적을 파악할 때 사용한다. 별도 요청 캐시는 두지 않는다.

#### INT-02 사용자 질문 실행 취소

요청 본문 없이 경로에 취소할 대화를 지정한다.

| 경로 필드 | 의미 | 형식 | 필수 여부 |
| --- | --- | --- | --- |
| `conversationId` | 실행을 취소할 대화 식별자 | UUID | 필수 |

#### INT-07 저장한 AI 행 알림

요청 본문에는 방금 커밋한 AI 행을 찾을 식별자를 보낸다. 백엔드는 해당 행을 조회·반영한 뒤 204를 반환한다.

| 필드 | 의미 | 형식 | 필수 여부 |
| --- | --- | --- | --- |
| `conversationId` | 저장한 AI 행이 속한 대화 식별자 | UUID | 필수 |
| `messageId` | 방금 커밋한 AI 행의 식별자 | 양의 64비트 정수(`int64`) | 필수 |

INT-01의 `messageId`는 사용자 질문을, INT-07의 `messageId`는 AI가 저장한 진행·종료 행을 가리킨다.

### 1.3 접수 결과

INT-01은 다음 기준으로 접수한다. 400 응답에는 본문이 없다.

| 조건 | 상태 코드 | 처리 |
| --- | --- | --- |
| 유효한 새 질문 | 202 | 질문을 조회하고 실행 접수 |
| 정의되지 않은 필드·잘못된 형식 | 400 | 입력 거절 |
| 질문 없음·질문과 대화 불일치 | 400 | 입력 거절 |
| 접수 준비 중 DB 장애 | 503 | 미접수 상태로 종료 |
| 같은 질문이 실행·조회 중 | 202 | 추가 실행 없음 |
| 같은 대화의 다른 질문이 실행 중 | 409 | 새 실행 거절 |
| 이미 종료 행이 있는 질문 재요청 | 202 | 추가 실행·행 저장·알림 없음 |

단일 프로세스에서 실행 상태와 실행 작업(`Task`)을 확인해 중복 실행을 막고, DB의 종료 행 제약도 유지한다.

INT-02는 취소할 실행이 없어도 202를 반환한다.

| 취소 대상 | 상태 코드 | 처리 |
| --- | --- | --- |
| 실행 중 | 202 | 후속 실행을 중단하고 취소 행 저장·알림 |
| 실행 없음·이미 종료 | 202 | 추가 행 저장 없음 |

### 1.4 실행·저장·알림

AI는 아래 행을 저장·커밋한 뒤 INT-07로 알린다. 완료·취소·실패 행은 이번 질문을 끝내는 종료 행이다.

| 상황 | 저장하는 내용 |
| --- | --- |
| 각 최상위 업무 노드 시작 | 런타임이 정한 단계 이름을 진행 행의 `content`·`details`에 저장. `artifacts`는 기존 값 보존 |
| 완료·부분 완료 | 완료 행의 내용·산출물 |
| 사용자 정보 필요 | 완료 행의 되묻기 내용. 이번 질문은 종료 |
| 취소 | 취소 행. 추가 모델 호출 없음 |
| 시간 초과·실행 오류 | 실패 종료 행 |

단계 안내는 노드 실행 전에 저장·알림하며, 실제 작업 결과를 모델이 매번 요약해 보내는 방식은 아니다. 도구·하위 에이전트의 새 결과는 내부 이력에 보관하고 최종 응답에서 공개할 내용을 선택한다. 일반 사용자 요청은 새 중간 결과를 작성·전송하지 않는다.

백엔드는 INT-07이 가리키는 저장 행을 확인하고 본문 없는 204를 반환한다. 프론트는 1초마다 새 행을 조회해 진행 문구·상세 설명을 표시하고 종료 행을 받으면 조회를 멈춘다. 지도·차트 등 `artifacts`는 완료 행의 것만 표시한다. 표시 계약은 [AI 패널](../../../docs/api/ai-agent-panel.md#2-1-artifacts-형식)을 따른다.

먼저 커밋한 종료 행을 보존한다. 종료 중의 늦은 실행·취소가 새 종료 행으로 덮어쓰지 않는다.

다음 사용자 입력은 DB 대화 기록을 읽고 새 실행 상태·새 예산으로 시작한다. AI가 이전 내용을 이어갈지 새 요청인지 판단하며, 이전 내부 실행 상태·도구 결과·중단 지점은 복원하지 않는다.

### 1.5 실행 시간

[공통 실행 설정](../../README.md#설치설정)의 현재 기본값은 일반 실행 300초, 종료 응답 최대 30초, 모델 요청 30초다. 사용자 요청은 접수 준비의 DB 읽기부터 종료 행 커밋까지 전체 330초 안에 끝내도록 남은 시간으로 실행을 제한한다. 마지막 3초는 커밋에 남기며, 진행·종료 행의 DB 저장도 최대 3초다. 진행 저장·알림 시간도 전체 실행 제한에 포함한다.

DB 장애·프로세스 강제 종료에서는 종료 행 커밋을 보장할 수 없다. 동기 작업이 이벤트 루프를 막는 동안에는 시간 초과 감지도 지연될 수 있다.

백엔드에 제안한 설정은 다음과 같다. 실제 적용 여부는 백엔드와 대조해야 한다.

| 설정 | 의미 | 제안값 |
| --- | --- | --- |
| `execution-limit` | AI의 전체 실행 기한 | 330초 |
| `grace-period` | 백엔드의 추가 대기 여유 | 5초 |
| `unresponsive-after` | 진행 알림이 없는 실행의 응답 지연 판단 기준 | 40초 |
| `cancel-wait` | 취소 결과 대기 시간 | 3초 |

5초의 여유는 AI 실행 시간을 늘리지 않는다. 설정을 바꾸면 실행 기한은 `runtime_timeout+30`, 응답 지연 기준은 `llm_timeout+10`으로 계산해 백엔드에 다시 전달한다.

### 1.6 연동 대조

AI 서버와 [공통 OpenAPI](../../../docs/api/openapi.json)·[패널 계약](../../../docs/api/ai-agent-panel.md)의 사용자 요청 전달·저장 알림 기준은 다음과 같다. 문서·코드의 일치와 실제 배포 환경의 연동 성공은 구분한다.

| 항목 | AI 연동 계약 | 공통 계약과 대조 |
| --- | --- | --- |
| 질문 지정 | AI 호출에는 `messageId`와 선택적 `context` | 일치. 사용자 질문 접수 응답의 `questionId`와 AI 호출 필드를 구분 |
| 중복 접수 | 같은 질문은 202, 같은 대화의 다른 활성 질문은 409 | 일치 |
| 저장 알림·화면 갱신 | 저장 후 INT-07 알림, INT-03 미사용 | 일치. 화면은 1초마다 새 저장 행을 조회하며 알림이 화면으로 직접 전송되지는 않음 |

INT-03 상태 조회는 사용하지 않는다. 위 대조는 문서·코드 확인 결과다. 배포 환경에서 INT-01·02 호출, INT-07 수신과 시간 제한이 함께 동작하는지는 실제 요청의 저장·수신 기록으로 확인한다. 40초 기준은 모델 요청 한도에 근거한 값이며, 긴 도구 작업 중에는 별도 주기적 진행 알림이 없으므로 실제 데이터로 알림 간격을 확인해야 한다.

### 1.7 검증

실제 모델·파일 저장소·로컬 HTTP를 사용하는 [사용자 요청 검증](api-verification.md#1-사용자-요청)에서 실행 명령, 저장 행과 알림의 대조, 통과 조건을 확인한다.

## 2. 보고서 생성

백엔드는 월 분석 완료 후 대상 동의 보고서 생성을 요청한다. AI는 동별 보고서를 DB에 직접 저장하고, 요청한 모든 동의 생성·저장 시도가 끝나면 저장 건수와 실패 동을 백엔드에 알린다. 파이프라인의 월 분석 완료 요청(INT-04)은 백엔드 담당이며 AI에는 INT-05로 전달된다.

### 2.1 API 목록

| 식별자 | 목적 | 방향 | 메서드 | 경로 | 정상 상태 코드 |
| --- | --- | --- | --- | --- | --- |
| INT-05 | 동별 보고서 생성 | 백엔드 → AI | POST | `/internal/insight-reports/runs` | 202 |
| INT-08 | 요청 전체의 완료 집계 알림 | AI → 백엔드 | POST | `/api/internal/analysis/insight-report-completions` | 204 |

### 2.2 입력 필드

#### INT-05 동별 보고서 생성

요청 본문에는 요청 식별자, 기준 월, 대상 동 목록을 보낸다.

| 필드 | 의미 | 형식 | 필수 여부 |
| --- | --- | --- | --- |
| `requestId` | 보고서 생성 요청 식별자 | 비어 있지 않은 문자열 | 필수 |
| `month` | 보고서 기준 월 | 유효한 `YYYY-MM` | 필수 |
| `dongCodes` | 보고서를 생성할 동 목록 | 중복 없는 10자리 숫자 문자열의 비어 있지 않은 목록 | 필수 |

#### INT-08 요청 전체의 완료 집계 알림

요청 본문에는 이번 요청의 저장 결과를 보낸다. 집계 원본은 동별 실행 상태의 저장 성공 기록이며, 보고서의 완성도와 저장 성공 여부를 구분한다.

| 필드 | 의미 | 형식 | 집계·전달 기준 |
| --- | --- | --- | --- |
| `requestId` | 완료한 요청 식별자 | 문자열 | 접수한 값 그대로 |
| `month` | 보고서 기준 월 | `YYYY-MM` | 접수한 값 그대로 |
| `savedCount` | DB 커밋이 성공한 동 수 | 0 이상의 정수 | 부분 보고서도 커밋됐으면 포함 |
| `failedDongCodes` | 보고서를 DB에 커밋하지 못한 동 목록 | 동 코드 문자열 목록 | 자료 없음·생성 또는 저장 오류 등으로 커밋하지 못한 동 |

네 필드를 모두 보낸다. 전부 실패한 요청도 `savedCount` 0과 실패 동 목록으로 알린다.

### 2.3 접수 결과

정상 요청은 바로 접수하고 자료 조회·생성·저장은 뒤에서 실행한다. 입력 오류의 400 응답에는 본문이 없다.

| 조건 | 상태 코드 | 처리 |
| --- | --- | --- |
| 유효한 요청 | 202 | 동별 생성 접수 |
| 입력 오류 | 400 | 입력 거절 |
| 기존 실행 중 새 요청·같은 요청 재전송 | 202 | 새 생성 접수 |

기존 실행이나 보고서가 있어도 409로 거절하거나 204로 생략하지 않는다. 분석 결과의 수정 시각을 비교해 생성 여부를 결정하지 않으며, 요청할 때마다 생성한다.

### 2.4 실행·저장·알림

동별 생성 병렬 수는 모든 보고서 요청이 공유하는 `SETTINGS_REPORT_CONCURRENCY`로 제한하며 기본값은 2다. 한 동 안에서는 시각화 선정·시각화 설명·퀵 인사이트 에이전트를 순차 실행한다. 여러 동의 실행·저장·완료 집계와 알림은 보고서 생성 흐름의 책임이며, 각 에이전트의 작성 책임과 구분한다. 생성·검토·동별 재처리·저장 재시도는 [보고서 생성 흐름](../agent/report.md)을 따른다.

| 상황 | 저장·알림 동작 |
| --- | --- |
| 동별 결과 저장 | `region_insight_report`에 행 추가 또는 같은 동·월의 행 갱신(UPSERT) |
| 일부 항목 미완성 | 미완성 항목은 NULL로 저장 |
| 분석 결과 수정 시각 기록 | 조회한 분석 결과의 수정 시각을 `result_updated_at`에 저장 |
| 같은 동·월 요청 중첩 | 마지막으로 저장한 결과 유지. 시점에 따른 저장 거절 없음 |
| 요청한 모든 동의 생성·저장 재시도 종료 | INT-08로 저장 건수와 실패 동 목록 알림 |

`result_updated_at`은 생성 생략이나 저장 허용 여부를 판단하는 데 사용하지 않는다. 보고서를 백엔드에 전달해 저장하는 INT-06 PUT은 사용하지 않는다.

### 2.5 실행 시간

[공통 실행 설정](../../README.md#설치설정)의 일반 실행 한도를 동별 업무 노드의 누적 활성 시간에 적용한다. 세 에이전트의 단계 전환·수정과 동별 재처리는 같은 동의 남은 예산을 이어 쓴다.

| 구간 | 동별 업무 예산에 포함 |
| --- | --- |
| 업무 노드 실행·동별 재처리 | 포함 |
| 동별 실행 자리 대기 | 제외 |
| 최초 분석 결과 확인 | 제외 |
| 최종 DB 저장·완료 알림 | 제외 |

보고서 요청 전체의 완료 기한은 별도로 제한하지 않는다. INT-08까지 걸리는 시간은 동 수·대기열·저장 재시도에 따라 달라진다. 전체 완료 시간과 동별 대기·자료 확인 시간은 [로컬 실행 증거](monitoring.md#4-로컬-실행-증거)에 기록하며, 이 기록이 업무 예산의 집계 범위를 바꾸지는 않는다.

### 2.6 연동 대조

AI 서버는 위 계약을 기준으로 한다. [공통 OpenAPI](../../../docs/api/openapi.json)와 [보고서 연동 초안](../../../docs/api/insight-report.md)에는 아래 차이가 남아 있다. 백엔드 문서·구현과 대조해야 하며 문서 정리만으로 실제 연동이 완료되지는 않는다.

| 항목 | AI 연동 계약 | 공통 문서에 남은 내용 |
| --- | --- | --- |
| 요청 식별자 | 비어 있지 않은 문자열 `requestId` | UUID `requestId` |
| 대상 동 | `dongCodes` | `targets`의 `dongCode`·`resultUpdatedAt` |
| 접수 응답 | 본문 없는 202 | 202 `{accepted}` |
| 저장·완료 전달 | AI가 직접 DB 저장 후 INT-08로 요청 전체 집계 알림 | INT-06으로 백엔드에 보고서를 전달해 저장 |
| 재요청·중첩 | 매 요청 생성, 같은 동·월의 마지막 저장 유지 | 기존 작업 중단 권고, 분석 수정 시각 불일치 시 저장 거절 |
| 부분 보고서 | 미완성 항목 NULL 허용 | 시각화 3개와 설명을 필수로 요구 |

| 연결 대상 | 현재 상태 | 남은 확인·제약 |
| --- | --- | --- |
| 백엔드 | 실제 왕복 미검증 | INT-05 호출·INT-08 수신 확인 |
| DB 저장 SQL | 현행 컬럼으로 UPSERT하며 삭제된 `summary_lines`·`report`를 참조하지 않음 | 실제 DB 저장 미검증 |
| DB 권한 | [권한 스크립트](../../../db/migration/afterMigrate.sql)에 `eumi_ai`의 보고서 INSERT·UPDATE 반영 | 실제 적용 권한 미검증 |
| DB 제약 | [11/10 마이그레이션](../../../db/migration/V20261110_02__insight_report.sql)은 `quick_insight`, `graph_1~3`, `desc_1~3`, `result_updated_at` 8개 컬럼에 NOT NULL 적용 | AI의 미완성 항목 NULL 저장 계약과 충돌. DB 제약·업무 계약은 변경하지 않음 |
| 분석 갱신 후 화면 조회 | 분석 시각 비교 없이 저장 | 이전 자료로 작성한 보고서가 나중에 저장될 수 있음. DB 뷰의 `result_updated_at` 일치 조건에 따라 화면에서 숨겨질 수 있으며, 뷰 변경은 AI 범위 밖 |

### 2.7 검증

실제 모델·합성 자료·파일 저장소·로컬 HTTP를 사용하는 [보고서 생성 검증](api-verification.md#2-보고서-생성)에서 실행 명령, 동별 저장과 완료 집계의 대조, 통과 조건을 확인한다.

## 3. 공통

### 3.1 연결·응답

| 방향 | 연결 범위 | 인증 |
| --- | --- | --- |
| 백엔드 → AI | 내부망의 AI 수신 API | 별도 인증 없음 |
| AI → 백엔드 | INT-07·08 알림 | `Authorization: Bearer <SETTINGS_BACKEND_TOKEN>` |

이 문서의 모든 정상 응답에는 본문이 없다. 202는 요청 수락이며 새 실행 시작이나 결과 생성·저장 완료를 보장하지 않는다. 실제 처리는 각 업무의 접수 결과 표를 따른다. 알림 수신자의 204는 알림 수락을 뜻한다.

### 3.2 알림 실패

알림 응답 대기 한도는 기본 1초다. 저장 결과와 알림 결과는 따로 기록한다.

| 전송 결과 | 재시도 |
| --- | --- |
| 연결 장애·시간 초과·5xx | 같은 본문으로 즉시 1회 추가 시도 |
| 4xx | 재시도 없음. 404 포함 |
| 잘못된 204 응답 | 재시도 없음 |

실패는 실행 상태의 `notification` 기록과 서버 로그에 남긴다. 알림만 실패해도 저장된 결과를 삭제하거나 모델을 다시 실행하지 않는다. 영속 전송 큐와 재시작 후 자동 재알림은 없다.

입력 거절·중복 접수·취소와 저장·알림 결과의 확인 방법은 [로컬 실행 증거](monitoring.md#4-로컬-실행-증거)를 따른다.

### 3.3 운영 조건

설정·서버·컨테이너 실행은 [AI README](../../README.md)를 따른다. 업무별 계약 대조와 미연결 사항은 [사용자 요청](#16-연동-대조)·[보고서 생성](#26-연동-대조)에 있다.

| 대상 | 현재 조건 | 남은 확인·제약 |
| --- | --- | --- |
| 실행 프로세스 | 단일 워커. Docker도 워커 1개 | 여러 워커·재시작 복구 미지원 |
| 실행 기록 | 로그와 보고서 파일 보관 | 재개용 체크포인트가 아님 |
| 배포 환경 | 로컬 파일 DB·HTTP 검증과 실제 연동 구분 | 실제 모델·PostgreSQL·백엔드 왕복, 알림 토큰, 2GB 메모리 상한 검증 필요 |

검증 환경의 준비와 실제 연동을 확인하지 못하는 범위는 [API 검증의 공통 안내](api-verification.md#3-공통)를 따른다.
