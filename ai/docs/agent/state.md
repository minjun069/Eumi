# AI 에이전트 실행 상태와 기록

수정일: 2026-11-12.

실행 상태 객체(`State`)는 한 실행의 요청·대화·작업 이력·공개 응답·사용량을 함께 보관한다. 각 노드는 이 정보를 읽고 자신이 맡은 필드만 갱신하며, 후속 노드는 앞선 결과를 같은 객체에서 확인한다.

## 1. 구성

| 필드 | 이름 | 자료형 | 내용 |
| --- | --- | --- | --- |
| request | 요청 | object | 목적·확인된 대상·범위와 조건 |
| messages | 메시지 | array | 시스템 지침과 실제 대화 메시지 |
| results | 내부 작업 이력 | array | 모든 노드의 결정·호출·검증·재시도·응답 작성 기록 |
| response | 응답 | object 또는 null | 사용자 요청의 진행 안내·최종 결과·질문 또는 보고서 내부의 후속 판단용 응답 |
| execution | 실행 정보 | object | 실행 ID·시작 이벤트·상태·배포 버전·한도·오류 |

조회·계산 자료는 해당 작업의 `results[].output`에 둔다. 공개할 산출물은 `response.artifacts`에 둔다. `info`는 사용하지 않는다. 내부 작업 이력 전체를 화면에 공개하지 않는다.

하위 에이전트는 상위 에이전트가 호출하는 도구와 같은 경계로 취급한다. 상위의 호출 기록 `action`에 에이전트 이름·호출 인자를, `output`에 하위 반환값을 기록한다. 상위에서 별도 모델 검증은 호출하지 않으며 실패·취소된 하위 실행 결과는 후속 계산·공개 후보에서 제외한다. 이후 판단과 응답 작성은 상위 State의 이 기록을 읽는다. 상위 자료를 별도 인자·클로저로 하위 에이전트에 주입하거나, 반환값을 별도 결과 저장소에 보관하지 않는다.

보고서의 세 에이전트는 상하위 호출이 아니라 같은 동의 State에서 순차 실행한다. 단계 진입·선정·작성·검토·추가 자료는 기존 `results`에 기록하고, 완료된 앞 단계 기록을 후속 단계가 변경하지 않는다. 단계와 입력 참조의 구체적인 기록 형식은 [보고서 실행 기록](report.md#5-보고서-실행-기록)에 정의한다.

### 1.1 request

요청은 에이전트가 달성할 목적과 지켜야 할 조건을 나타낸다.

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| goal | string | 목적과 확인된 대상·지역·기간·자료 참조를 충분히 서술한 작업 설명 |
| constraints | object | 작업의 필수·선호·제외 조건 |
| constraints.required | string[] | 필수 조건. 생략 시 빈 목록 |
| constraints.preferred | string[] | 선호 조건. 생략 시 빈 목록 |
| constraints.excluded | string[] | 제외 조건. 생략 시 빈 목록 |

`goal`은 공백만 있는 문자열을 허용하지 않는다. 에이전트마다 대상의 종류와 확정 시점이 다르므로 공통 `subject` 필드는 두지 않는다. 아직 확인하지 않은 대상은 만들어 채우지 않고 작업 중 구체화한다. 도구를 호출할 때는 해당 도구가 요구하는 입력 인자로 변환한다.

분석 완료 이벤트에서는 시스템이 `goal`, `constraints`, 시스템 지침을 포함한 `messages`를 구성한다. 시작 종류는 `execution.event`에 보관한다. 보고서 요청 입력과 동별 자료·생성·저장 기록은 [보고서 실행 기록](report.md#5-보고서-실행-기록)을 따른다. 별도 요청 대상 분석 버전과 요청 수정 번호를 State에 두지 않는다. 대상 동·월과 저장·완료 알림은 [API의 보고서 생성 계약](../runtime/api.md#2-보고서-생성)을 따른다.

### 1.2 messages

시스템 지침은 시스템 메시지, 실제 요청·답변은 사용자 메시지, 실제 대화로 전달한 응답·질문은 AI 응답 메시지로 구분한다. 자동 실행의 `goal`을 가짜 사용자 발화로 복제하지 않는다. 외부 자료나 사용자 발화를 시스템 지침으로 승격하지 않는다.

코드는 `MessagesState`의 메시지 자료형과 병합 규칙을 사용한다. 도구 결과와 판단 이력의 원본은 `results`에 둔다. 모델 호출용 메시지 구성·이력 선별은 [컨텍스트](context.md)에서 별도로 정한다.

### 1.3 results

내부 작업 이력은 어떤 작업을 왜 선택했고 무엇을 얻었는지 검토할 수 있도록 남기는 기록이다. 각 기록은 다음 구조를 사용하며 노드 이름과 업무별 출력 구조는 해당 구현·도구 계약에서 구체화한다.

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| id | string | 기록 식별자 |
| node | string | 기록을 생성한 노드 종류 |
| decision | string | 기록 종류 또는 선택한 작업. 진행 판단 기록은 `decision` |
| reason | string | 결정을 검토할 수 있는 짧은 근거 요약 |
| action | object 또는 null | 수행한 호출·검증 등 작업. 없으면 null |
| action.name | string | 작업 또는 도구·에이전트 이름 |
| action.arguments | object | 실제 작업 인자. 업무별 구조는 도구 계약에서 정의 |
| output | object 또는 null | 작업 결과 또는 저장 위치. 자료·산출물·출처·실제 자료 버전·오류·검증 판정 등을 해당 작업 출력에 포함 |
| description | string | 결과의 대상·기간·의미 설명 |
| outcome | string | 해당 작업 처리의 `success` 또는 `failure` |

진행 판단 기록은 `node="decide"`, `decision="decision"`으로 식별한다. 다음 단계는 `output.next`, 필요한 정보와 판단 근거는 `output.reason`과 기록의 `reason`에 담는다. 작업 선택 및 실행은 `results`에서 최근 진행 판단을 읽는다. `needs`, `input_refs`, `sources`, `validation` 필드는 두지 않는다. 검증과 재시도는 각각 작업 기록으로 남긴다. 도구 설정 검사와 보고서 검토의 검증 기록에는 검증 대상·기준·판정과 이유가 드러나야 한다. 공통 작업 선택 및 실행은 모델 검증 기록을 생성하지 않는다.

`outcome`은 처리 성공·실패를 뜻한다. 정상 조회의 빈 결과는 성공이며 자료 없음은 `output`에 기록한다. 검증을 정상 수행해 부적합을 발견한 경우에도 처리 자체는 성공이고 부적합 판정은 `output`에 남긴다. 처리 오류는 실패로 기록한다. 개별 성공이 전체 요청 완료를 뜻하지 않는다.

선택 이유는 호출 전에 기록하고 호출 결과를 이어 기록한다. 도구 부적합 판정과 보고서 검토 결과는 해당 검사를 수행했을 때 기록한다. 결정 자체의 기록과 호출 결과의 기록을 구분할 수 있다. 완료된 실패·재시도 이력을 덮어쓰지 않는다. 각 노드는 자신의 기록만 추가·완성하며, 다른 노드의 기존 이력을 수정하지 않는다. 노드는 판단·작성 기록을 추가하고, 공통 실행 함수는 호출 시작·반환·오류와 재시도를 같은 State에 기록한다. 그래프는 노드가 반환하거나 처리 오류·한도로 종료할 때 새 기록과 누적 사용량을 함께 반영한다. 프로세스 강제 종료 전의 노드 내부 기록을 복구하는 계약은 별도 저장 구현이 필요하다.

응답 작성도 작업 이력에 남긴다. 작성 기록은 과거 결과를 보존하고 `response`는 현재 공개할 내용을 나타낸다. 전체 이력은 참고할 수 있지만 실패·부적합·이후 수정된 자료를 유효한 근거로 동일 취급하지 않는다.

### 1.4 response

사용자 요청에서는 현재 진행 안내·최종 답변·질문과 선택한 산출물을 보관한다. 보고서 역할은 같은 구조로 내부 후속 판단용 응답도 보관한다. 이 필드가 갱신됐다는 사실만으로 사용자 화면에 표시된 것은 아니며, 저장·표시 시점은 [실행 흐름](workflow.md#21-사용자-요청의-진행-안내와-결과-전달)을 따른다.

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| id | string | 공개 응답 식별자. 질문 답변 연결에도 사용 |
| kind | string | `progress`, `intermediate`, `final`, `question` |
| label | string | 진행 단계 이름 또는 응답 제목. 단계별 고정 문구는 [실행 흐름](workflow.md#21-사용자-요청의-진행-안내와-결과-전달) 참조 |
| content | string | 메시지·설명·출처·해석 한계·미해결 사항 |
| artifacts | array | 현재 공개할 해석·차트·표·UI 등 산출물 |
| artifacts[].type | string | 산출물 종류 |
| artifacts[].data | object | 산출물 내용 또는 조회 가능한 참조. 정의된 유형은 아래 개별 명세를 따르며 그 밖의 상세 구조·표시 계약은 미정 |

정의된 산출물 유형은 [Tableau 시각화](tableau.md)와 [행정동 분석 보고서](report.md#5-보고서-실행-기록)를 따른다.

아직 공개할 내용이 없으면 `response=null`이다. `sources`, `issues`, `result_refs`, 별도 `references` 필드는 두지 않는다. 필요한 출처와 한계는 `content` 또는 관련 산출물의 내용에 포함한다. 필드 제거가 출처·한계 설명의 생략을 뜻하지 않는다.

`progress`는 단계 시작 안내, `final`은 마지막 응답, `question`은 추가 질문이다. `intermediate`는 작성 후 진행 판단으로 돌아갈 때 쓰는 공통 그래프의 응답 종류이며, 현재 보고서 내부 보완과 모의 출력 시험에서 사용한다. 일반 사용자 요청의 작성 노드는 `final`만 반환한다. 응답 종류와 실행 상태는 별개이며 최종 응답도 완료·일부 완료·실패로 종료할 수 있다.

런타임이 진행 문구를 갱신할 때는 기존 산출물을 유지한다. 하위 결과가 `results`에 들어와도 새 산출물을 `response`에 자동으로 추가하지 않는다. 응답 작성은 최종 답변에 공개할 산출물을 선택한다. 사용자 요청의 진행·종료 행 저장과 백엔드 알림, 완료 행 산출물만 표시하는 화면 규칙은 [연동 API](../runtime/api.md#14-실행저장알림)를 따른다.

### 1.5 execution

실행 정보는 시작 원인과 현재 상태, 적용한 배포 구성, 누적 사용량을 나타낸다. 개별 작업의 성공 여부는 `results[].outcome`에 기록하고 전체 실행의 상태와 구분한다.

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| run_id | string | 실행 ID |
| event | string | `analysis_pipeline`: 데이터 분석 파이프라인에서 시작, `user_request`: 사용자 요청으로 시작 |
| status | string | 아래 실행 상태 |
| version | string | 지침·도구·API 구성을 함께 식별하는 배포 버전 |
| budget | object | 자원별 누적 사용량(`used`)과 한도(`limit`) |
| error | object 또는 null | 실행 전체의 오류 코드(`code`)와 원인(`cause`). 정상 상태에서는 null |

사용자 요청의 run_id는 백엔드가 발급한 conversation_id와 같다. 내부 실행 상태와 ai_message.status는 구분하며, 상태별 저장·알림은 [API의 사용자 요청 계약](../runtime/api.md#1-사용자-요청)을 따른다.

| status | 의미 |
| --- | --- |
| queued | 접수 후 실행 대기 |
| running | 실행 중 |
| waiting_input | 내부 질문 생성 상태. 서비스 API는 질문을 DB 완료 행으로 저장하고 이번 요청 종료 |
| completed | 완료 |
| partial | 일부 작업만 마친 종료 |
| failed | 실패 종료 |
| cancelled | 취소 종료 |

`execution.version`에는 자료 버전을 넣지 않는다. 실제 조회한 자료 버전은 해당 도구의 `output`에 둔다. 배포 버전에서 적용한 지침·도구·API 구성을 확인할 수 있도록 배포 시 관리한다. 서비스 API는 이전 실행의 체크포인트를 재개하지 않는다.

#### 실행 예산

| 예산 필드 | 사용량 누적 기준 | 한도 적용 |
| --- | --- | --- |
| steps | 실제 업무 노드 진입 직전에 1회. 상위·하위 모두 포함 | 다음 업무 노드 진입 전 확인. 질문 대기·답변 전달 자체와 한도 후 종료 응답은 제외 |
| tool_calls | 도구 호출 시도 직전에 1회. 실패 호출과 응답 작성의 비교표 렌더링 포함 | 다음 도구 호출 전 확인 |
| agent_calls | 하위 에이전트 호출 시도 직전에 1회 | 다음 하위 호출 전 확인 |
| retries | 실패·부적합 작업을 보완하는 후속 호출 직전에 1회 | 인자 수정·대체 도구·대체 에이전트도 포함. 실패 건수로 대신 계산하지 않음 |
| active_seconds | 업무 노드에서 실제 경과한 초. 중첩 모델·도구·하위 실행 시간은 한 번만 누적 | 모델·도구 호출은 남은 시간으로 제한하고 노드 종료 시 동기 처리 시간을 함께 반영 |
| final_model_calls | 한도 후 종료 응답용 모델 호출 직전에 1회 | 전체 실행에서 최대 1회. 재시도 없음 |
| final_active_seconds | 한도 후 종료 응답에서 실제 경과한 초 | 전체 실행에서 최대 30초. 일반 실행 시간과 중복 집계하지 않음 |

재시도 집계 기준은 위 표와 같다. 현재 구현은 직전 호출의 실패·부적합 여부만 읽으므로 여러 호출에 걸친 보완과 독립적인 새 작업을 구분하지 못한다. 재시도 집계는 이 기준을 모두 구현한 상태가 아니며, 이 구분을 위해 새 필드를 추가하지 않는다.

새 최상위 실행에서만 배포 설정을 읽어 일반 한도를 State에 초기화한다. 이후 한도와 사용량의 원본은 `execution.budget`이다. results 개수로 단계 수나 호출 수를 추정하지 않는다. 단계를 제외한 호출 한도는 해당 종류의 다음 호출을 시도할 때 적용하며, 마지막 허용 호출의 반환 자체를 실패로 바꾸지 않는다.

하위 에이전트는 상위의 이벤트·배포 버전·누적 예산을 복사해 같은 잔여 한도 안에서 실행한다. 반환된 `response`, `results`, `execution`을 상위 호출 기록의 output에 보관한 뒤, 그 execution의 누적 사용량을 상위 budget에 반영한다. 반환 사용량에는 진입 전 사용량도 포함하므로 전체 값을 다시 더하지 않는다. 하위마다 사용량을 0으로 초기화하거나 설정에서 한도를 다시 읽지 않는다. 현재 호출은 순차 실행이다.

보고서의 단계 전환은 새 최상위 실행이나 하위 호출을 만들지 않는다. 한 동의 세 에이전트·수정·실행 오류 재처리는 같은 `execution.budget`을 계속 사용하며, 단계가 바뀔 때 사용량을 초기화하거나 다시 합산하지 않는다. 보고서의 역할 전환 자체는 `agent_calls` 집계 대상이 아니다.

처음 한도에 도달한 에이전트가 공유 종료 응답 예산을 사용한다. 이 단계에는 새 도구·하위 에이전트·렌더링을 허용하지 않는다. 성공한 호출 결과와 기존 공개 산출물로 한계·미해결 사항을 작성한다. 종료 응답이 실패하거나 별도 예산까지 소진되면 추가 모델 호출 없이 기존 공개 결과와 종료 사유를 반환한다. 하위가 이 예산을 사용한 경우 응답은 상위 results에 남으며, 상위는 추가 모델 호출 없이 기존 공개 결과와 종료 사유를 반환한다.

서비스 API는 되묻기를 DB 완료 행으로 저장한다. 다음 입력에서는 대화 기록으로 새 State를 만들고 예산을 초기화한다. 기존 작업 이력·중단 지점을 복원하지 않는다. 내부 질문 대기 상태(`waiting_input`)와 DB 완료 상태는 목적이 다르다. 공통 실행기의 `resume_graph`는 로컬 그래프 검증에 사용하며 서비스 API는 호출하지 않는다.

서비스 API와 연결할 때의 기록은 다음과 같다. 새 최상위 필드는 추가하지 않는다.

| 정보 | 기록 위치·방법 |
| --- | --- |
| 실행 요청 원본 | `conversationId`, `messageId`, 선택적 `context`를 `results`의 `run_request` 기록에 있는 `action.arguments`에 보관 |
| 질문 연결 | 접수한 원본 `messageId`로 DB의 `question_id` 구성 |
| 실제 대화 | DB 조회 후 `messages`에 보관 |
| 화면 문맥 | `request.constraints.preferred`에 제공 |
| 백엔드 알림 | 각 POST 본문과 성공·실패를 `results`의 `notification` 기록에 보관 |
| 보고서 저장 집계 | 동별 `report_save` 성공 기록에서 계산 |

사용자 요청의 초기 DB 조회·실행 준비 시간은 `active_seconds.used`에 포함한다. API는 State의 일반·종료 잔여 시간 합계에서 DB 커밋용 3초를 남겨 전체 실행을 제한한다. 진행 저장·알림 시간도 이 전체 실행 제한에 포함된다.

노드 예산은 다음 호출에 쓸 수 있는 양을 제한하고, API의 경과 시간 제한은 HTTP 실행을 마칠 시점을 제한한다. 두 제한은 같은 사용량의 복사본이 아니다. 이벤트 루프를 막는 동기 처리·DB 장애·프로세스 강제 종료에서는 정시 커밋을 보장할 수 없다.

## 2. 노드별 쓰기 범위

아래는 읽기 범위가 아니라 논리적인 쓰기 책임이다. 모델에 제공할 컨텍스트의 범위·선별 방침은 별도로 정한다.

| 쓰기 주체 | 쓰기 범위 | 기록 내용 |
| --- | --- | --- |
| 작업 목적 파악 | request.goal, request.constraints, results | 요청 구체화와 파악 결과 기록 |
| 작업 선택 및 실행 | results, response | 최근 진행 판단에 따른 선택·호출·도구 검사·재시도 기록. 현재 업무 노드의 반환은 results만 갱신 |
| 작업 진행 판단 | results, response | 충분 여부·부족한 내용·다음 진행 방향. 현재 업무 노드의 반환은 results만 갱신 |
| 응답 작성 | results, response | 일반 업무의 최종 답변·산출물, 보고서의 작성·검토와 후속 판단용 응답 |
| 사용자 정보 요청 | results, response | 질문 작성 이력과 질문 응답 |
| 실행 계층 | messages, execution, response | 지침·실제 대화 기록, 상태·사용량·오류 관리, 단계 시작 안내와 오류·취소 종료 응답 |

공통 그래프는 작업 선택·진행 판단에 진행 안내용 `response` 갱신을 허용하지만, 현재 서비스의 단계 안내는 런타임이 각 최상위 노드 시작 전에 고정 문구로 작성·저장한다. 모델이 작업 결과를 `response`에 실시간 작성하는 기능은 아니다. 노드가 반환하는 갱신은 공통 그래프에서 허용 필드·응답 종류와 기존 산출물 보존 여부를 검사한다.

## 3. 초기화와 남은 계약

`create_state(request, settings, messages=..., version=..., event=...)`는 새 실행을 만든다. 요청·메시지·이벤트 종류는 호출자가 제공하고 `results=[]`, `response=null`, `status=queued`, 사용량 0으로 초기화한다. 이벤트는 필수이며 미등록 종류를 거부한다. 저장된 실행 재개에 이 함수를 사용하지 않는다.

`execution.event`는 실행을 시작한 원인을 나타낸다. 업무 노드와 모델은 변경하지 않으며 하위 에이전트도 상위 값을 상속한다. 질문 답변으로 같은 실행을 재개할 때도 유지한다. 그래프의 최초 진입과 이벤트별 시각화 허용 목록 조회에 이 값을 사용한다. `analysis_pipeline`은 작업 진행 판단, `user_request`는 작업 목적 파악으로 진입한다. 작업 목적 파악 다음에는 항상 작업 진행 판단으로 이동한다. 질문 답변 후에는 두 종류 모두 작업 목적 파악으로 돌아간다.

백엔드가 발급한 conversationId를 사용자 execution.run_id로 사용한다. 같은 대화의 다음 질문도 같은 ID를 사용하지만 State와 예산은 새로 만든다.

| 항목 | 상태 | 남은 내용 |
| --- | --- | --- |
| 업무별 출력 | 개별 명세에서 정의한 범위 외에는 미정 | `action.arguments`, `output`, `artifacts[].data`의 추가 상세 자료형·검증 기준 |
| 컨텍스트 | 현재 노드별 입력은 [모델 입력 구성](../runtime/prompts.md)에 정의 | 추가 결정은 [컨텍스트](context.md#3-현재-구성과-남은-결정) 참조 |
| 배포 연동 | 실제 환경 검증 필요 | 백엔드·DB의 계약 반영과 실제 저장·알림 왕복. [사용자 요청 연동](../runtime/api.md#16-연동-대조)·[보고서 생성 연동](../runtime/api.md#26-연동-대조)·[운영 조건](../runtime/api.md#33-운영-조건) 참조 |

현재 코드의 JSON 객체 허용은 업무별 상세 계약의 정의 완료를 뜻하지 않는다. 공통 그래프의 실행 연결·노드 갱신 제한·질문 복원과 State 예산 처리는 구현 코드에 연결했다. 서비스 API는 영속 체크포인트와 동시 재개를 사용하지 않는다. 실행은 [AI README](../../README.md), 저장·알림 검증은 [API 검증 절차](../runtime/api-verification.md)를 따른다.
