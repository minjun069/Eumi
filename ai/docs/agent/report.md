# 행정동 분석 보고서 생성

수정일: 2026-11-12. 확정 요구사항과 현재 구현 범위를 기록한다. 실제 DB·화면 연동은 미검증이다.

## 1. 목적과 적용 범위

데이터 분석 파이프라인 완료 후 행정동별로 시각화와 설명, 퀵 인사이트를 생성한다. 퀵 인사이트는 선정한 시각화의 검토를 통과한 설명에서 핵심 내용을 3~4문장으로 요약한 것이다. 보고서 생성 흐름은 시각화 선정·시각화 설명·퀵 인사이트 에이전트를 순서대로 실행하고, 각 에이전트는 공통 실행 흐름에서 자기 산출물에 필요한 작업과 완료 여부를 판단한다.

자료·판단·산출물의 원본 보관은 [기존 State 계약](state.md)을 따른다. State 필드 변경의 확인 절차는 [설계 준수 기준](../coding-guide.md#1-설계-준수와-state)을 따른다. 해석 지침을 변경하기 전에는 사용자 확인을 받는다.

## 2. 실행 요청

백엔드가 분석 완료 후 AI 서버에 보고서 생성을 요청한다.

| 입력 | 의미 |
| --- | --- |
| `requestId` | 요청 식별자 |
| `month` | 보고서 기준 월 |
| `dongCodes` | 보고서를 생성할 행정동 목록 |

요청 접수 → 행정동별 세 에이전트 순차 실행 → 동별 결과 저장 → 전체 처리 종료 순서로 진행한다. 여러 동의 실행·저장·완료 집계와 알림은 보고서 생성 흐름이 맡고, 각 에이전트는 자기 산출물 작성에 집중한다. 행정동별 작업은 제한된 수로 병렬 실행한다. 전체 처리 후 INT-08로 저장 건수와 실패 동을 알린다.

접수 API의 경로·입력 검사·응답·중복 실행 기준은 [보고서 생성 계약](../runtime/api.md#2-보고서-생성)을 따른다. 기존 보고서의 존재·수정 시각과 관계없이 매 요청을 생성하고 같은 동·월에는 마지막 저장 결과가 남는다. 동시에 처리하는 동 수는 `SETTINGS_REPORT_CONCURRENCY`로 제한하며 기본값은 2다.

## 3. 행정동별 생성 흐름

| 에이전트 | 입력 | 산출물 | 검증 기준 |
| --- | --- | --- | --- |
| 1. 시각화 선정 | 대상 동·월, 조회·가공 자료와 출처 | 선정 뷰, 선정 이유, 근거 참조, 설명 가능한 범위와 제외한 비교 | 뷰 적합성·중복, 근거 충분성, 설명 범위 |
| 2. 시각화 설명 | 검토를 통과한 선정, 해당 근거·설명 범위, 자기 단계에서 추가 확보한 자료 | 검토를 통과한 뷰별 설명과 근거 참조 | 설명 정확성, 추가 자료 확보 판단, 뷰·근거·설명 일치 |
| 3. 퀵 인사이트 | 검토를 통과한 설명과 해당 근거 | 검토를 통과한 핵심 문장 3~4개 | 요약 충실성, 중복·새로운 주장 여부 |

세 에이전트는 각각 작업 진행 판단으로 시작하며 [공통 노드 전이](workflow.md#2-에이전트-공통-실행-흐름)를 사용한다. 보고서 생성 흐름은 이 세 에이전트를 정해진 순서로 실행한다. 작성과 검토는 응답 작성 안의 별도 모델 호출이며, 후속 작업이 필요하면 작성·검토 이력을 남기고 같은 에이전트의 진행 판단으로 돌아간다. 진행 판단이 추가 조회·가공 또는 확보한 자료로 재작성할지를 결정하고, 추가 작업을 선택한 경우 작업 선택 및 실행이 구체적인 도구와 인자를 정한다. 조회 범위는 자기 산출물의 책임과 [자료 접근 계약](data.md)을 따른다.

후속 에이전트는 앞 단계에 보완·재선정·재작성을 요청하지 않으며, 앞 단계의 산출물도 변경하지 않는다. 설명 에이전트의 추가 자료는 이미 정한 뷰와 설명 범위 안에서 사용한다. 인사이트 에이전트는 근거를 확인하더라도 검증된 설명에 없는 주장을 추가할 수 없다. 현재 입력과 허용된 추가 조회만으로 해결하지 못하면 §4의 부분 완료·NULL 기준을 적용한다.

- 선정 에이전트는 상세 뷰 `EmbedDetailV01~08` 중 데이터에 적합한 서로 다른 3개를 선택한다. 자기 단계의 검토·수정에서 같은 조합의 재선정도 허용한다.
- 뷰의 일부 비교 자료가 없어도 근거가 있는 내용으로 설명 범위를 제한해 선정할 수 있다. 선정 이유에 설명 범위와 제외한 비교를 기록하며, 작성·검토도 같은 범위를 따른다. 자료 부족 시 3개 미만을 허용한다.
- 기준 월 이전 자료도 조회할 수 있다. 조회·해설 범위는 상세 뷰에서 나타나는 내용을 설명하는 데 필요한 범위로 한정한다.
- 선정·근거 검토를 통과하면 설명 에이전트로 진행한다. 뷰별 설명은 순차 작성하고, 인사이트 에이전트는 검토를 통과한 설명을 요약한다.
- 설명·인사이트 작성과 자기 검토는 같은 모델에 서로 다른 프롬프트로 각각 요청한다. 검토에서는 작성 내용을 근거와 대조한다. 부적절 판정 후 항목별 최대 3회 수정하며, 검토의 부적절 사유를 재작성 입력에 포함한다. 추가 조회를 하거나 실행 오류를 재처리해도 이 수정 횟수를 초기화하지 않는다.
- V01·V07의 추세 기간은 요청의 `month`를 포함한 최근 6개월이다. 요청 월이 12월이면 시작 월은 7월이다. 화면과 해설에 같은 기간을 적용한다.

## 4. 산출물과 실패 처리

AI가 `region_insight_report`에 직접 저장한다. 백엔드에 보고서를 전달해 저장하지 않는다. 완성하지 못한 항목은 NULL로 저장한다.

`result_updated_at`에는 보고서의 근거로 조회한 분석 결과(`region_result`)의 수정 시각을 기록한다. 생성·저장 여부 판단에는 사용하지 않는다. INT-08 집계·실패 전송 규칙은 [연동 API](../runtime/api.md)를 따른다.

| 저장 항목 | 내용 | 형식 | 분량 |
| --- | --- | --- | --- |
| `quick_insight` | 선택한 뷰들의 설명 범위만 요약 | 줄바꿈으로 구분한 문자열 | 항목당 한 문장, 총 3~4개 |
| `graph_1~3` | 선택한 Tableau 뷰명 | 선정한 뷰마다 한 항목 | 최대 3개 |
| `desc_1~3` | 각 뷰의 설명문 | 항목당 한 단락 | 항목당 최대 3문장 |

| 상황 | 처리 |
| --- | --- |
| 자료 부족으로 전체 산출물 생성 불가 | 부분 완료 허용. 완성하지 못한 항목은 NULL로 저장 |
| 일부 행정동의 실행 오류 | 성공한 동의 결과를 유지하고 전체 동의 첫 처리 후 실패한 단계만 추가 1회 재처리 |
| 개별 설명문 실패 | 해당 설명만 재처리 |
| 생성 후 저장 실패 | 같은 생성 결과로 저장만 최대 2회 추가 재시도. 대기 간격 없이 실행 |

서버 재시작 후 실행 복구는 구현 범위에 포함하지 않는다.

검토 수정 3회를 소진한 항목은 동별 재처리에서 다시 작성하지 않는다. 정상 조회의 자료 부족과 검토 부적합은 실행 오류와 구분한다. 실행 오류 재처리는 실패한 단계·항목만 이어가며, 후속 단계의 판단으로 완료된 앞 단계를 다시 실행하는 기능은 제공하지 않는다.

각 동은 독립된 `execution.budget`을 사용하며 세 에이전트의 작업·수정과 실행 오류 재처리가 그 누적 사용량을 이어 쓴다. 단계 전환에서 새 State나 새 예산을 만들지 않고 사용량을 다시 합산하지 않는다. 에이전트 간 순차 전환은 상위 에이전트의 하위 호출이 아니므로 `agent_calls`를 늘리지 않는다. 기존 실행 한도가 먼저 소진되면 항목별 최대 수정·재시도 횟수 이전에도 종료한다. 저장할 수 있는 검증된 결과는 보존한다.

공통 실행 한도는 [실행 설정](../../README.md#설치설정)을 따른다. 모델에 남은 실행량을 고려한 작업 축소·종료 판단을 요구하지 않으며, 한도 검사는 기존 실행기가 담당한다.

## 5. 보고서 실행 기록

State와 중첩 필드는 기존 구조를 사용한다. 요청 입력·자료·판단·초안·검토·수정·저장 이력의 원본은 동별 `results`다. 전송용 모델 입력과 DB 인자는 State에서 만든다.

| 기록 | 보관 내용 | 사용 목적 |
| --- | --- | --- |
| 실행 입력 | `output`의 `requestId`, `month`, `dongCodes`, `dongCode` | 조회·선정·보고서 저장의 대상 특정 |
| 분석 결과 확인 | 동·월과 분석 결과의 `updated_at` | 자료 존재 확인과 저장할 기준 시각 기록. 시점 비교에는 사용하지 않음 |
| 조회·가공 | 도구가 반환한 자료·출처·버전·검증 기록 | 선정·설명·검토에 필요한 근거 보존 |
| 에이전트 진입 | `report_stage` 기록의 `action.name`에 `<역할>_agent`, 기존 `action.arguments`의 `view_key`, `result_ids`에 입력 참조 | 현재 단계와 앞 단계 전달 자료를 특정. 이후 조회·판단·작성 기록을 해당 단계 이력으로 구분 |
| 뷰 선정 | `output.views[]`의 `view_key`, `reason`, `evidence_ids`. `reason`에는 설명 범위와 제외한 비교 포함 | 선정 검토 후 설명 작성의 대상·근거로 사용. 후속 단계는 이 기록을 변경하지 않음 |
| 작성 | `action.arguments`의 `view_key`, `result_ids`, `output.content`의 초안. 퀵 인사이트의 `view_key`는 null | 대상·앞 단계 산출물·추가 조회 근거를 참조하고 작성 내용 보관 |
| 검토 | `output.call_id`, `accepted`, `reason` | 재작성 시 이전 초안과 함께 제공 |
| 에이전트 종료 | `composition` 기록의 `action.name`에 `<역할>_agent`, 기존 `output.content`, `status`, `reason`과 산출물 참조 | 역할별 완료·부분 완료를 구분하고 재처리 때 종료한 앞 단계 재실행 방지 |
| 최종 보고서 | DB 컬럼에 대응하는 보고서를 작성 이력과 `response.artifacts`의 `analysis_report`에 보관 | 공개 산출물 구성과 DB 저장 |
| 저장·재처리 | 각 시도와 성공·실패를 별도 기록. 기존 초안·검토·실패 기록 유지 | 미완료 단계 재처리와 저장 결과 확인 |

보고서 생성 흐름은 같은 동의 State로 공통 그래프를 `report_selection` → `report_description` → `report_insight` 순서로 실행한다. 각 그래프는 자기 역할의 작업 선택·진행 판단·응답 작성을 실행한다. 작성·검토 후 후속 판단이 필요하면 `intermediate` 응답과 이력을 진행 판단에 전달한다. 이는 보고서 내부의 다음 판단을 위한 기록이며 사용자 대화의 중간 결과로 저장·알림하지 않는다. 세 역할의 선택 목록에는 앞 단계 에이전트 호출이 없다.

단계 전환과 오류 재처리는 `results`에 남은 단계·검토·작성·완료 기록에서 진행 위치를 찾는다. 후속 단계의 자료·판단은 새 기록으로 추가하고 선정·검토를 통과한 설명 기록을 덮어쓰지 않는다. 모델 입력과 저장 산출물은 이 이력에서 매번 구성하며, 별도의 단계별 업무 상태나 전달용 원본을 유지하지 않는다.

적용 프롬프트는 [보고서 지침](../../src/instructions/analysis-report.md)과 [모델 입력 구성](../../src/prompting.py)에 있다. 요청 접수·여러 동의 실행·저장·알림은 [API](../../api.py), 한 동의 순차 실행은 [보고서 실행기](../../src/report_flow.py), 입력·산출물 구조는 [State](../../src/state.py), 각 역할의 판단·선정·작성·검토는 [업무 노드](../../src/agent_nodes.py)가 맡는다. DB 조회·저장은 [DB 연결](../../src/database.py)이 맡는다. 생성 결과와 State는 기존 출력 디렉터리 아래 `<run_id>/report.json`에도 남긴다. 이 파일은 재시작 복구에 사용하지 않는다.

## 6. 구현 범위와 남은 연결

보고서의 세 에이전트를 공통 실행 흐름에 연결하고 순차 실행·작성·검토와 자기 단계의 추가 조회를 분리했다. 동별 실행·오류 재처리·저장·알림은 보고서 생성 흐름에서 관리한다. 역할별 산출물·판단·검토 정확성은 [노드 평가](../../eval/docs/nodes/README.md)에서 확인한다. 한 동·월의 단계 전달·보고서 구성·반환과 실행 성능·안정성은 [동별 보고서 실행 평가](../../eval/docs/execution/dashboard-report.md)에서 확인한다.

로컬 상세 기록과 임시 파일 DB 연결은 [보고서 생성 검증](../runtime/api-verification.md#2-보고서-생성)을 따른다.
`report.json`에는 기존 사용자 요청과 같은 추적 형식으로 모델 입력·응답과 도구·노드·저장 기록을 함께 남긴다.
동별 재처리는 같은 기록기에 누적하며, 별도 업무 State나 재개 저장소로 사용하지 않는다.

| 연결 | 현재 상태 | 남은 확인·제약 |
| --- | --- | --- |
