# AI Agent State

수정일: 2026-11-06.

## 1. 구성

| 필드 | 이름 | 자료형 | 내용 |
| --- | --- | --- | --- |
| request | 요청 | object | 목적·확인된 대상·범위와 조건 |
| messages | 메시지 | array | 시스템 지침과 실제 대화 메시지 |
| results | 내부 작업 이력 | array | 모든 노드의 결정·호출·검증·재시도·응답 작성 기록 |
| response | 공개 응답 | object 또는 null | 현재 표시할 진행 안내·중간 결과·최종 결과·질문 |
| execution | 실행 정보 | object | 실행 ID·시작 이벤트·상태·배포 버전·한도·오류 |

조회·계산 자료는 해당 작업의 `results[].output`에 둔다. 공개할 산출물은 `response.artifacts`에 둔다. `info`는 사용하지 않는다. 내부 작업 이력 전체를 화면에 공개하지 않는다.

하위 Agent는 상위 Agent가 호출하는 도구와 같은 경계로 취급한다. 상위의 호출 기록 `action`에 Agent 이름·호출 인자를, `output`에 하위 반환값을 기록한다. 상위에서 별도 모델 검증은 호출하지 않으며 실패·취소된 하위 실행 결과는 후속 계산·공개 후보에서 제외한다. 이후 판단과 응답 작성은 상위 State의 이 기록을 읽는다. 상위 자료를 별도 인자·클로저로 하위 Agent에 주입하거나, 반환값을 별도 결과 저장소에 보관하지 않는다.

### 1.1 request

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| goal | string | 목적과 확인된 대상·지역·기간·자료 참조를 충분히 서술한 작업 설명 |
| constraints | object | 작업의 필수·선호·제외 조건 |
| constraints.required | string[] | 필수 조건. 생략 시 빈 목록 |
| constraints.preferred | string[] | 선호 조건. 생략 시 빈 목록 |
| constraints.excluded | string[] | 제외 조건. 생략 시 빈 목록 |

`goal`은 공백만 있는 문자열을 허용하지 않는다. Agent마다 대상의 종류와 확정 시점이 다르므로 공통 `subject` 필드는 두지 않는다. 아직 확인하지 않은 대상은 만들어 채우지 않고 작업 중 구체화한다. 도구를 호출할 때는 해당 도구가 요구하는 입력 인자로 변환한다.

분석 완료 이벤트에서는 시스템이 `goal`, `constraints`, 시스템 지침을 포함한 `messages`를 구성한다. 시작 종류는 execution.event에 보관하고, 이벤트 ID·분석 ID·실행 소유권의 연동 정보는 서버가 실행 ID에 연결해 보관한다. 별도 요청 대상 분석 버전과 요청 수정 번호를 State에 두지 않는다. 대상 분석을 특정하는 방법과 게시 계약은 [연동 API 초안 §3](ai-runtime-api-20261029.md#3-데이터-저장조회)을 따른다.

### 1.2 messages

시스템 지침은 시스템 메시지, 실제 요청·답변은 사용자 메시지, 실제 대화로 전달한 응답·질문은 Assistant 메시지로 구분한다. 자동 실행의 `goal`을 가짜 사용자 발화로 복제하지 않는다. 외부 자료나 사용자 발화를 시스템 지침으로 승격하지 않는다.

코드는 `MessagesState`의 메시지 자료형과 병합 규칙을 사용한다. 도구 결과와 판단 이력의 원본은 `results`에 둔다. 모델 호출용 메시지 구성·이력 선별은 [컨텍스트](ai-agent-context.md)에서 별도로 정한다.

### 1.3 results

각 기록은 다음 구조를 사용한다. 노드 이름과 업무별 출력 구조는 해당 구현·도구 계약에서 구체화한다.

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| id | string | 기록 식별자 |
| node | string | 기록을 생성한 노드 종류 |
| decision | string | 선택한 작업·진행 방향·부족한 내용·후속 처리 |
| reason | string | 결정을 검토할 수 있는 짧은 근거 요약 |
| action | object 또는 null | 수행한 호출·검증 등 작업. 없으면 null |
| action.name | string | 작업 또는 도구·Agent 이름 |
| action.arguments | object | 실제 작업 인자. 업무별 구조는 도구 계약에서 정의 |
| output | object 또는 null | 작업 결과 또는 저장 위치. 자료·산출물·출처·실제 자료 버전·오류·검증 판정 등을 해당 작업 출력에 포함 |
| description | string | 결과의 대상·기간·의미 설명 |
| outcome | string | 해당 작업 처리의 `success` 또는 `failure` |

부족한 정보는 `decision`에 구체적으로 적는다. `needs`, `input_refs`, `sources`, `validation` 필드는 두지 않는다. 검증과 재시도는 각각 작업 기록으로 남긴다. 도구 설정 검사와 보고서 검토의 검증 기록에는 검증 대상·기준·판정과 이유가 드러나야 한다. 공통 작업 선택 및 실행은 모델 검증 기록을 생성하지 않는다.

`outcome`은 처리 성공·실패를 뜻한다. 정상 조회의 빈 결과는 성공이며 자료 없음은 `output`에 기록한다. 검증을 정상 수행해 부적합을 발견한 경우에도 처리 자체는 성공이고 부적합 판정은 `output`에 남긴다. 처리 오류는 실패로 기록한다. 개별 성공이 전체 요청 완료를 뜻하지 않는다.

선택 이유는 호출 전에 기록하고 호출 결과를 이어 기록한다. 도구 부적합 판정과 보고서 검토 결과는 해당 검사를 수행했을 때 기록한다. 결정 자체의 기록과 호출 결과의 기록을 구분할 수 있다. 완료된 실패·재시도 이력을 덮어쓰지 않는다. 각 노드는 자신의 기록만 추가·완성하며, 다른 노드의 기존 이력을 수정하지 않는다. 노드는 판단·작성 기록을 추가하고, 공통 실행 함수는 호출 시작·반환·오류와 재시도를 같은 State에 기록한다. 그래프는 노드가 반환하거나 처리 오류·한도로 종료할 때 새 기록과 누적 사용량을 함께 반영한다. 프로세스 강제 종료 전의 노드 내부 기록을 복구하는 계약은 별도 저장 구현이 필요하다.

응답 작성도 작업 이력에 남긴다. 작성 기록은 과거 결과를 보존하고 `response`는 현재 공개할 내용을 나타낸다. 전체 이력은 참고할 수 있지만 실패·부적합·이후 수정된 자료를 유효한 근거로 동일 취급하지 않는다.

### 1.4 response

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| id | string | 공개 응답 식별자. 질문 답변 연결에도 사용 |
| kind | string | `progress`, `intermediate`, `final`, `question` |
| label | string | 데이터 조회 중·비교 결과·해석 완료 등 표시 문구 |
| content | string | 메시지·설명·출처·해석 한계·미해결 사항 |
| artifacts | array | 현재 공개할 해석·차트·표·UI 등 산출물 |
| artifacts[].type | string | 산출물 종류 |
| artifacts[].data | object | 산출물 내용 또는 조회 가능한 참조. 유형별 구조·렌더링 계약은 미정 |

아직 공개할 내용이 없으면 `response=null`이다. `sources`, `issues`, `result_refs`, 별도 `references` 필드는 두지 않는다. 필요한 출처와 한계는 `content` 또는 관련 산출물의 내용에 포함한다. 필드 제거가 출처·한계 설명의 생략을 뜻하지 않는다.

`progress`는 진행 안내, `intermediate`는 실제 중간 결과, `final`은 마지막 응답, `question`은 추가 질문이다. 응답 종류와 실행 상태를 구분한다. 중간 결과 전송 후에도 작업이 계속되면 `running`이며, 최종 응답의 실행 상태는 완료·일부 완료·실패 등 실제 결과를 따른다.

공개 응답은 현재 표시할 전체 내용으로 갱신한다. 진행 문구만 바뀌어도 이미 공개한 유효한 산출물은 유지한다. 수정·제외한 결과는 최신 산출물 목록에 반영하고 이유를 설명한다. 하위 결과가 `results`에 들어왔다는 사실만으로 공개하지 않는다. AI 서버는 공개 내용을 DB 행으로 저장하고 두 식별자로 백엔드에 알린다. 저장·POST 계약은 [연동 API 초안](ai-runtime-api-20261029.md)을 따른다.

### 1.5 execution

| 필드 | 자료형 | 내용 |
| --- | --- | --- |
| run_id | string | 실행 ID |
| event | string | `analysis_pipeline`: 데이터 분석 파이프라인에서 시작, `user_request`: 사용자 요청으로 시작 |
| status | string | 아래 실행 상태 |
| version | string | 지침·도구·API 구성을 함께 식별하는 배포 버전 |
| budget | object | 아래 자원별 누적 used와 limit |
| error | object 또는 null | 실행 전체의 오류 code·cause. 정상 상태에서는 null |

사용자 요청의 run_id는 백엔드가 발급한 conversation_id와 같다. 내부 실행 상태와 ai_message.status는 구분하며, DB 표현과 미확정 대응은 [연동 API 초안 §3.1](ai-runtime-api-20261029.md#31-대화메시지)를 따른다.

| status | 의미 |
| --- | --- |
| queued | 접수 후 실행 대기 |
| running | 실행 중 |
| waiting_input | 내부 질문 생성 상태. 서비스 API는 질문을 DB 완료 행으로 저장하고 이번 요청 종료 |
| completed | 완료 |
| partial | 일부 작업만 마친 종료 |
| failed | 실패 종료 |
| cancelled | 취소 종료 |

`execution.version`에는 자료 버전을 넣지 않는다. 실제 조회한 자료 버전은 해당 도구의 `output`에 둔다. 배포 버전에서 적용한 지침·도구·API 구성을 확인할 수 있도록 배포 시 관리한다. 서비스 API는 이전 실행의 체크포인트를 재개하지 않는다.

#### 실행 예산

| budget 필드 | used 누적 기준 | limit 적용 |
| --- | --- | --- |
| steps | 실제 업무 노드 진입 직전에 1회. 상위·하위 모두 포함 | 다음 업무 노드 진입 전 확인. 질문 대기·답변 전달 자체와 한도 후 종료 응답은 제외 |
| tool_calls | 도구 호출 시도 직전에 1회. 실패 호출과 응답 작성의 비교표 렌더링 포함 | 다음 도구 호출 전 확인 |
| agent_calls | 하위 Agent 호출 시도 직전에 1회 | 다음 하위 호출 전 확인 |
| retries | 실패·부적합 작업을 보완하는 후속 호출 직전에 1회 | 인자 수정·대체 도구·대체 Agent도 포함. 실패 건수로 대신 계산하지 않음 |
| active_seconds | 업무 노드에서 실제 경과한 초. 중첩 모델·도구·하위 실행 시간은 한 번만 누적 | 모델·도구 호출은 남은 시간으로 제한하고 노드 종료 시 동기 처리 시간을 함께 반영 |
| final_model_calls | 한도 후 종료 응답용 모델 호출 직전에 1회 | 전체 실행에서 최대 1회. 재시도 없음 |
| final_active_seconds | 한도 후 종료 응답에서 실제 경과한 초 | 전체 실행에서 최대 30초. 일반 실행 시간과 중복 집계하지 않음 |

재시도 집계 기준은 위 표와 같다. 현재 구현은 직전 호출의 실패·부적합 여부를 읽는 이전 처리로 돌아간 상태다. 여러 호출에 걸친 보완과 독립적인 새 작업을 구분하지 못하므로, 재시도 집계의 전체 구현은 완료되지 않았다. 이 구분을 위해 새 필드를 추가하지 않는다.

새 최상위 실행에서만 배포 설정을 읽어 일반 한도를 State에 초기화한다. 이후 한도와 사용량의 원본은 `execution.budget`이다. results 개수로 단계 수나 호출 수를 추정하지 않는다. 단계를 제외한 호출 한도는 해당 종류의 다음 호출을 시도할 때 적용하며, 마지막 허용 호출의 반환 자체를 실패로 바꾸지 않는다.

하위 Agent는 상위의 이벤트·배포 버전·누적 예산을 복사해 같은 잔여 한도 안에서 실행한다. 반환된 `response`, `results`, `execution`을 상위 호출 기록의 output에 보관한 뒤, 그 execution의 누적 사용량을 상위 budget에 반영한다. 반환 사용량에는 진입 전 사용량도 포함하므로 전체 값을 다시 더하지 않는다. 하위마다 사용량을 0으로 초기화하거나 설정에서 한도를 다시 읽지 않는다. 현재 호출은 순차 실행이다.

처음 한도에 도달한 Agent가 공유 종료 응답 예산을 사용한다. 이 단계에는 새 도구·하위 Agent·렌더링을 허용하지 않는다. 성공한 호출 결과와 기존 공개 산출물로 한계·미해결 사항을 작성한다. 종료 응답이 실패하거나 별도 예산까지 소진되면 추가 모델 호출 없이 기존 공개 결과와 종료 사유를 반환한다. 하위가 이 예산을 사용한 경우 응답은 상위 results에 남으며, 상위는 추가 모델 호출 없이 기존 공개 결과와 종료 사유를 반환한다.

서비스 API는 되묻기를 DB 완료 행으로 저장한다. 다음 입력에서는 대화 기록으로 새 State를 만들고
예산을 초기화한다. 기존 results·중단 지점을 복원하지 않는다. 내부 waiting_input과 DB 완료는
서로 다른 목적의 상태다. 공통 실행기의 resume_graph는 로컬 그래프 검증에 남아 있으며
서비스 API는 호출하지 않는다.

INT-01 입력은 results의 run_request 기록 action.arguments에 원본으로 보관한다.
conversationId·messageId·선택적 context만 사용하며 새 최상위 필드는 추가하지 않는다.
조회 후 실제 DB 대화가 messages에 들어간다. 접수 시 원본 입력의 messageId로 DB question_id를 만든다.
화면 문맥은 request.constraints.preferred에 제공한다. 알림 시도는 results의 notification 기록에
POST 본문과 성공·실패를 남기며, 보고서 집계는 동별 report_save 성공 기록에서 계산한다.

사용자 요청의 초기 DB 조회·실행 준비 시간을 active_seconds.used에 포함한다.
API는 State의 일반·종료 잔여 시간 합계에서 DB 커밋용 3초를 남겨 전체 실행을 제한한다.
진행 저장·알림 시간도 이 외부 실행 제한에 포함된다. 개별 노드 예산과 실제 벽시계 제한은
동일한 값의 별도 사용량 사본이 아니며 각각 호출 예산·HTTP 실행 마감을 제어한다.
이벤트 루프를 막는 동기 처리·DB 장애·프로세스 강제 종료에서는 정시 커밋을 보장할 수 없다.


## 2. 노드별 쓰기 범위

아래는 읽기 범위가 아니라 논리적인 쓰기 책임이다. 모델에 제공할 컨텍스트의 범위·선별 방침은 별도로 정한다.

| 노드·계층 | 쓰기 범위 | 기록 내용 |
| --- | --- | --- |
| 작업 목적 파악 | request.goal, request.constraints, results | 요청 구체화와 파악 결과 기록 |
| 작업 선택 및 실행 | results, response | 선택·호출·검증·재시도 기록, 진행 안내 |
| 작업 진행 판단 | results, response | 충분 여부·부족한 내용·다음 진행 방향, 진행 안내 |
| 응답 작성 | results, response | 작성 이력, 실제 중간·최종 공개 결과 |
| 사용자 정보 요청 | results, response | 질문 작성 이력과 질문 응답 |
| 실행 계층 | messages, execution | 지침·실제 대화 기록, 상태·사용량·오류 관리 |

작업 선택 및 실행과 작업 진행 판단의 진행 안내 갱신은 공개된 유효 산출물을 보존한다. 새로운 중간·최종 산출물의 공개 구성은 응답 작성이 맡는다. State 자료형만으로 이 범위가 강제되지는 않는다. 구현 시 노드 갱신 경계에서 검사해야 한다.

## 3. 초기화와 남은 계약

`create_state(request, settings, messages=..., version=..., event=...)`는 새 실행을 만든다. 요청·메시지·이벤트 종류는 호출자가 제공하고 `results=[]`, `response=null`, `status=queued`, 사용량 0으로 초기화한다. 이벤트는 필수이며 미등록 종류를 거부한다. 저장된 실행 재개에 이 함수를 사용하지 않는다.

`execution.event`는 실행을 시작한 원인을 나타낸다. 업무 노드와 모델은 변경하지 않으며 하위 Agent도 상위 값을 상속한다. 질문 답변으로 같은 실행을 재개할 때도 유지한다. 그래프의 최초 진입과 이벤트별 시각화 허용 목록 조회에 이 값을 사용한다. `analysis_pipeline`은 작업 선택 및 실행, `user_request`는 작업 목적 파악으로 진입한다. 질문 답변 후에는 두 종류 모두 작업 목적 파악으로 돌아간다.

백엔드가 발급한 conversationId를 사용자 execution.run_id로 사용한다. 같은 대화의 다음 질문도 같은 ID를 사용하지만 State와 예산은 새로 만든다.

| 미정 항목 | 확정할 내용 |
| --- | --- |
| 업무별 출력 | action.arguments·output·artifacts[].data의 상세 자료형과 검증 기준 |
| 컨텍스트 | 노드별 제공 정보, 이력 가공·선별·길이 관리 |
| 연동 | 백엔드 공개 응답·게시 메타데이터·저장·재개 계약. API 초안 §4 참조 |

현재 코드의 JSON 객체 허용은 업무별 상세 계약의 정의 완료를 뜻하지 않는다. 공통 그래프의 실행 연결·노드 갱신 제한·질문 복원과 State 예산 처리는 구현 코드에 연결했다. 서비스 API는 영속 체크포인트와 동시 재개를 사용하지 않는다. 서비스 API의 실행·저장·알림 검증은 AI README와 API 왕복 검증 문서를 따른다.
