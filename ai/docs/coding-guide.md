# AI 코드 작업 지침

수정일: 2026-11-12. AI 코드를 작성·수정·검토할 때 확정된 설계와 실행 상태의 전달 경로를 보존하는 기준이다. 프로젝트 공통 규칙과 지침 유지 관리는 [프로젝트 지침](../../../AGENTS.md)을 따른다. 실행 명세는 [현재 문서 목록](README.md)에서 확인한다.

실행 상태(`State`)는 요청·작업 이력·공개 응답·실행 한도를 함께 보관하는 자료다. 구현은 [실행 상태 명세](agent/state.md)의 필드와 쓰기 범위를 따른다.

## 1. 설계 준수와 State

- 새 필드 추가를 금지한다. State의 중첩 `output`, 모델 응답, 도구 인자에도 적용한다. 기능·집계 기준의 승인을 필드 추가 승인으로 확대 해석하거나, 다른 이름·위치에 같은 필드를 만들어 우회하지 않는다.
- 최신 사용자 결정, 확정 명세, 현재 구현 사실, 구현자의 제안을 구분한다. 추측·제안·미정 항목을 확정 요구로 바꾸거나, 구현한 뒤 문서를 맞춰 정당화하지 않는다.
- 역할·단계·노드의 통합·분리·생략, 모델 판단과 코드 처리의 배분, State 필드·의미, 산출물 소유·등록, 검증·중단·재개 위치는 사용자 결정 없이 바꾸지 않는다. 전체 구현·최소화·라이브러리 활용·새 구현 요청과 ‘구현 시 결정’ 문구도 설계 변경의 포괄적 승인이 아니다.
- 실행별 요청·시작 이벤트·자료·선택·호출·검증·응답·한도·사용량은 정해진 State 필드를 원본으로 사용한다. 별도 함수 인자·클로저·객체 속성·캐시·모델 입력에만 보관하거나, State와 별도로 동기화하는 경로를 만들지 않는다. 하위 에이전트도 도구처럼 호출하고 반환값을 상위 작업 이력인 `results`에 기록한다.
- 초기화 이후 한도·누적 사용량은 State에서만 읽고, 하위 호출·재개·데모에서도 공유 계약을 유지한다. 전달·보관은 [State 계약](agent/state.md)을 따르며, 미정 계약을 우회 구현하지 않는다.
- 모델 입력과 도구 인자는 State 및 명세가 허용한 배포 구성에서 만든다. State에서 즉시 계산한 지역 변수나 전송용 데이터는 만들 수 있지만, 독립적인 실행 상태로 보관하지 않는다. 새 판단·호출 결과는 정해진 `results` 기록 경로에 저장한 뒤 다음 판단에 사용한다. 기록 시점이나 복원용 상태를 저장하는 시점인 체크포인트 경계를 바꿔야 하면 먼저 확인한다.
- 모델·자료원 클라이언트, 도구 명세, 배포 설정, 비밀키는 실행별 업무 자료와 구분한다. 비밀키를 State나 모델 입력에 넣지 않는다. 실행마다 달라지는 값을 ‘설정’이라 이름 붙여 State 밖에 숨기지 않는다. 명세가 별도 보관을 허용한 값은 그 근거·보관 위치·복원 방법을 확인한다.
- 검토할 때 각 입력을 누가 만들고, 어디에 원본을 보관하며, 누가 읽고, 재개할 때 어디서 복원하는지 추적한다. 같은 State와 식별된 배포 구성으로 실행을 복원할 때 별도 업무 자료를 다시 넣어야 한다면 State를 우회했는지 확인한다. 로그·실행 추적 기록은 관측용이며 누락된 State를 대신하지 않는다.

## 2. 범위와 확인

- 시작할 때 목표·범위·유지할 동작을 짧게 정리한다. 전체 구현 요청은 실행기·설정·모델 연결·데이터·검증·데모의 관련 범위를 함께 다룬다. 예시 파일만 수정하고 전체 완료로 보고하지 않는다. 설명 요청을 수정 요청으로 확대하지 않는다.
- 저장소와 기존 결정을 먼저 확인한다. 요구 범위, 실제 연동 입출력, 기능 제거, 프레임워크, 설정 입력 방식, 대기·재개·취소 정책, 새 공통 계층·연결 규격이 미확정이면 의존하는 구현 전에 질문한다. 이미 확정한 사항과 명칭·지역 변수·동작을 보존하는 중복 제거는 다시 묻지 않는다.
- 질문에는 쉬운 용어로 결정 대상, 현재 설계와의 차이, 같은 기준의 선택지와 영향을 제시한다. 비용뿐 아니라 판단 기록·검증·실패 처리·재개 단위를 설명한다. 사용자가 의미를 되물으면 설명과 선택지를 함께 다시 제시한다.
- 무응답을 동의로 간주하지 않는다. 답변 전에는 의존하는 코드·명세를 수정하지 않으며 독립적인 조사·정리는 계속한다. 답변 후 가정·계획·문서를 갱신하고 다른 구조를 조용히 채택하지 않는다.
- 기존 폴더·빈 파일·API 초안만으로 범위를 넓히거나 호환성 요구를 만들지 않는다. 실제 연동·사용자 유지 조건을 확인한다. 전체 구조 재검토 요청을 받았다면 현재 타입을 유지할지 되묻는 것으로 구현 판단을 미루지 않는다.

## 3. 구현과 책임

- 설계의 단계·역할·State를 현재 함수·자료형·실제 사용처에 대응시킨 뒤 유지·통합·제거와 동작 영향을 판단한다. 파일 이동부터 시작하지 않는다. 기존 존재, 메서드 부재, 미래 확장 가능성만으로 유지·제거·추가를 결정하지 않는다.
- 최소 구조는 필요한 책임·상태·검증을 보존하며 전달·변환·동기화를 줄이는 것이다. 기존 구현을 보호하기 위한 래퍼나 미래용 범용 계층을 덧붙이지 않는다. 최초 구현부터 책임별 배치·읽는 순서·이름·중복·필요한 주석을 정리한다. 간결함을 이유로 기능·검증을 생략하거나 과도하게 압축하지 않는다.
- 실제 서비스와 실험은 같은 실행 코드·업무 노드를 사용한다. 시나리오·고정 응답·합성 자료·성공·실패를 강제하는 분기는 데모·테스트에 둔다. 실험이 공통 코드를 호출하며 공통 코드는 실험 자료에 의존하지 않는다. 테스트 준비 코드는 자료·모의 응답·환경 구성만 제공하고 별도 실행기를 복제하지 않는다.
- 모델과 연결하는 어댑터는 요청 구성·응답 변환을 맡으며 업무 판단·실행 규칙을 숨기지 않는다. 설정을 어디서 읽고 사용하는지, 기본값·검증이 중복되지 않는지 확인한다. 호출 횟수·시간·재시도 제한은 원본과 규칙을 한곳에 두고 실제 실행 시점에 검사한다. 한도 계산, 실행 중단, 개별 호출의 시간 초과는 숫자가 같아도 역할이 다르면 합치지 않는다.
- 현재 사용하는 상태·입출력·업무 구조는 관련 로직 가까이에 `TypedDict`로 정의한다. 값이 들어오거나 전달되는 경계에서 검증이 필요하면 `TypeAdapter`를 사용한다. 필드 제약·기본값·값만으로 판단하는 일관성 규칙은 자료형과 함께 정의한다. 고정 구조를 일반 `dict`로 임시 구현하고 타입 정의를 완료했다고 하지 않는다.
- 라이브러리의 메시지·도구 검증을 복제하지 않는다. 작은 타입은 실제 재사용·중첩 구조·필수값 검증에 도움이 되면 유지한다. 타입 수를 줄이려 수동 검증을 반복하거나 검증을 약화하지 않는다. 범주마다 폴더·기반 클래스·변환 계층을 만들 필요는 없다.
- 형식 검사, 실행 제한, 업무 결과 타당성의 책임을 구분한다. 현재 질문·버전·사용량을 알아야 하는 검사는 실제 실행 지점에서 한다. 검증을 정상 수행해 부적합을 확인한 경우와 작업 실행 중 오류가 난 경우를 구분한다. 공개 응답·모델 입력·체크포인트·관측 로그의 목적과 필요한 복사·격리를 보존한다.

## 4. 변경·검증·완료

- 변경 전 Git 상태와 사용자 수정분을 확인하고 보존한다. 관련 없는 변경을 되돌리거나 커밋하지 않는다. 원복도 대상과 기준을 확인하고 수행한다.
- 구현 전후에 설계 대응과 State 전달 경로를 대조한다. 별도 자료 재주입 없는 복원, 상하위 호출, 미검증 결과 차단, 상태 격리 등 변경에 해당하는 동작을 검증한다. 테스트 통과를 설계 준수로 대신하지 않는다. 미승인 이탈을 발견하면 그 부분의 구현을 중단하고 차이·조정안을 알린다.
- 테스트는 명세에 따른 노드 전이·호출·검사·완료 또는 질문·재개 흐름과 재작업·취소·누적 한도·결과 보존을 검증한다. 타입·파일 이름을 정당화하는 테스트를 만들거나, 구조 변경에 따른 기존 동작 검증을 단순 삭제해 통과시키지 않는다. 변경에 맞는 테스트·정적 검사와 수정 전후 비교를 수행하고 기존 문제와 신규 문제를 구분한다. 사용자가 검증 실행을 보류하면 실행하지 않고 코드·문서 수정과 미검증 범위 보고에 집중한다.
- 실험에서도 구현된 업무 노드는 그대로 실행하고 미연결 모델·외부 도구 경계만 대체한다. 노드 자체가 미구현이면 모의 노드 검증 범위를 공통 연결·상태·재개로 한정한다. 완료 전에 공통 코드에 시나리오·고정 결과·데모 전용 인자가 남지 않았는지 확인한다.
- 문서는 현재 동작과 미구현·미확정 사항을 구분한다. 검토 결과·구조 선택 근거·시험 기록은 README 등 해당 문서에 두고 작업 지침에 누적하지 않는다. 오류 처리 규칙을 한곳에서 관리하는 것과 오류를 기록·관측하는 것을 구분한다. 실제 입력 경계, 오류 전달 경로와 모니터링 구현 범위를 확인한다.
- 커밋은 책임·기능별 최소 단위로 구성한다. 기존 구현 수정은 해당 구현 커밋에 흡수하되 히스토리 변경 전 사용자 작업을 보존하고 중간 커밋의 의존성을 확인한다.
- 완료 시 실제 변경·근거·검증·남은 결정을 보고한다. 설계 역할이 코드에서 어디에 구현됐는지와 입력의 생성·보관·사용·복원 경로를 대조한 결과를 남긴다. 테스트·정적 검사 결과는 이 설계 대조 결과와 구분한다. 일부 구현·임시 처리·생략·미완료는 이유와 남은 작업을 명시하며, 미실행 테스트와 미완료 구현을 구분한다. 적용 지침도 프로젝트 지침의 유지 관리 규칙에 따라 정리한 상태로 마친다.
