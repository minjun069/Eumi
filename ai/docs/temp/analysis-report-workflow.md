# 행정동 분석 보고서 생성 계획

작성일: 2026-11-06. 수정일: 2026-11-08. 사용자 확인 사항과 현재 구현 범위를 기록한다. 실제 DB·모델·화면 연동은 미검증이다.

## 1. 목적과 적용 범위

데이터 분석 파이프라인 완료 후 행정동별로 시각화와 설명, 퀵 인사이트를 생성한다. 이 이벤트 전용 보고서 생성 흐름으로 구성하고, 기존 공통 실행 흐름과 도구를 재사용한다.

State 필드와 해석 지침은 변경 전에 사용자 확인을 받는다. 중첩 필드 추가·의미 변경도 포함한다. 자료·판단·산출물의 원본 보관은 [기존 State 계약](../ieumi-agent-state.md)을 따른다.

## 2. 실행 요청

백엔드가 분석 완료 후 AI 서버에 보고서 생성을 요청한다.

| 입력 | 의미 |
| --- | --- |
| `requestId` | 요청 식별자 |
| `month` | 보고서 기준 월 |
| `dongCodes` | 보고서를 생성할 행정동 목록 |

요청 접수 → 행정동별 작업 1·2·3 실행 → 동별 결과 저장 → 전체 처리 종료 순서로 진행한다. 행정동별 작업은 제한된 수로 병렬 실행한다. 전체 처리 후 INT-08로 저장 건수와 실패 동을 알린다.

| API | 동작 |
| --- | --- |
| `POST /internal/insight-reports/runs` | 위 세 입력으로 보고서 생성 요청 |
| 202 | 작업 접수 후 비동기 실행 |
| 400 | 입력 형식 오류 |

위 응답은 본문이 없다. `requestId`는 비어 있지 않은 문자열, `month`는 유효한 `YYYY-MM`, `dongCodes`는 중복 없는 10자리 숫자 문자열 목록이다. 빈 목록과 정의되지 않은 입력 필드는 거부한다.

진행 중인 요청이 있어도 202로 접수한다. 기존 보고서의 존재·수정 시각과 관계없이 매 요청을 생성한다. 시점 비교와 생성 생략은 하지 않는다. 동시에 처리하는 동 수는 SETTINGS_REPORT_CONCURRENCY(기본 2)로 제한한다. 같은 동·월은 마지막 저장 결과가 남는다.

## 3. 행정동별 생성 흐름

| 작업 | 실행 방식 | 사용 도구 | 산출물 | 검증 기준 |
| --- | --- | --- | --- | --- |
| 1. 시각화 선정·근거 확보 | 공통 실행 흐름으로 조회·가공·선정 | 데이터 조회, 데이터 가공 | 선택한 뷰, 선정 이유, 설명에 필요한 근거 자료 | 선정 적합성, 뷰 중복 여부, 설명 근거 충분 여부 |
| 2. 시각화별 설명문 생성 | 뷰별 독립 작성·검토 | 없음 | 각 뷰의 설명문 | 근거와 수치·기간·비교 내용 일치, 뷰의 표현 범위 준수 |
| 3. 퀵 인사이트 생성 | 검증된 설명과 근거를 요약·검토 | 없음 | 핵심 문장 3~4개 | 설명과 일치, 내용 중복·새로운 주장 없음 |

- 작업 1은 상세 뷰 `EmbedDetailV01~08` 중 데이터에 적합한 서로 다른 3개를 선택한다. 같은 조합의 재선정도 허용한다.
- 기준 월 이전 자료도 조회할 수 있다. 조회·해설 범위는 상세 뷰에서 나타나는 내용을 설명하는 데 필요한 범위로 한정한다.
- 작업 1의 선정·근거 검증을 거쳐 작업 2로 진행한다. 작업 2의 뷰별 설명은 순차 실행하고, 작업 3은 검증된 설명을 요약한다.
- 작업 2·3은 같은 모델을 사용하되 작성과 자기 검토(self-reflect)를 서로 다른 프롬프트로 각각 호출한다. 검토에서는 작성 내용을 근거와 대조한다. 부적절 판정 후 최대 3회 수정하며, 검토의 부적절 사유를 재작성 입력에 포함한다.
- V01·V07의 추세 기간은 요청의 `month`를 포함한 최근 6개월이다. 요청 월이 12월이면 시작 월은 7월이다. 화면과 해설에 같은 기간을 적용한다.

## 4. 산출물과 실패 처리

AI가 `region_insight_report`에 직접 저장한다. 백엔드에 보고서를 전달해 저장하지 않는다. 완성하지 못한 항목은 NULL로 저장한다.

`result_updated_at`에는 보고서의 근거로 조회한 분석 결과(`region_result`)의 수정 시각을 기록한다. 생성·저장 여부 판단에는 사용하지 않는다. INT-08 집계·실패 전송 규칙은 [연동 API](../ai-runtime-api-20261029.md)를 따른다.

| 저장 항목 | 내용 | 확정 수준 |
| --- | --- | --- |
| `quick_insight` | 항목당 한 문장, 총 3~4개의 인사이트. 선택한 뷰들의 설명 범위만 요약 | 줄바꿈으로 구분한 문자열 |
| `graph_1~3` | 선택한 Tableau 뷰명 | 확정 |
| `desc_1~3` | 해당 뷰를 설명하는 한 단락, 최대 3문장 | 확정 |

| 상황 | 처리 |
| --- | --- |
| 자료 부족으로 전체 산출물 생성 불가 | 부분 완료 허용. 완성하지 못한 항목은 NULL로 저장 |
| 일부 행정동의 실행 오류 | 성공한 동의 결과를 유지하고 전체 동의 첫 처리 후 실패한 단계만 추가 1회 재처리 |
| 개별 설명문 실패 | 해당 설명만 재처리 |
| 생성 후 저장 실패 | 같은 생성 결과로 저장만 최대 2회 추가 재시도. 대기 간격 없이 실행 |

서버 재시작 후 실행 복구는 구현 범위에 포함하지 않는다.

검토 수정 3회를 소진한 항목은 동별 재처리에서 다시 작성하지 않는다. 정상 조회의 자료 부족과 검토 부적합은 실행 오류와 구분한다. 각 동은 독립된 `execution.budget`을 사용하며 작업 1·2·3과 재처리가 그 누적 사용량을 이어 쓴다. 기존 실행 한도가 먼저 소진되면 항목별 최대 수정·재시도 횟수 이전에도 종료한다. 저장할 수 있는 검증된 결과는 보존한다.

## 5. 승인된 State 전달

최상위 State 필드는 유지한다. 요청 입력·자료·판단·초안·검토·수정·저장 이력의 원본은 동별 `results`다. 전송용 모델 입력과 DB 인자는 State에서 만든다.

| 기록 | 구조·소비자 |
| --- | --- |
| 실행 입력 | `output`의 `requestId`, `month`, `dongCodes`, `dongCode`. 조회·선정·보고서 저장이 읽음 |
| 분석 결과 확인 | 동·월과 분석 결과의 `updated_at`. 자료 존재 확인과 저장할 기준 시각 기록에 사용하며 시점 비교는 하지 않음 |
| 조회·가공 | 기존 도구의 자료·출처·버전·검증 기록을 유지 |
| 뷰 선정 | `output.views[]`의 `view_key`, `reason`, `evidence_ids`. 선정 검토 후 설명 작성이 읽음 |
| 작성 | `action.arguments`의 `view_key`, `result_ids`로 대상·입력 기록을 지정. 퀵 인사이트의 `view_key`는 null. `output.content`에 초안 저장 |
| 검토 | `output.call_id`, `accepted`, `reason`. 재작성은 이전 초안과 이 검토 기록을 입력으로 읽음 |
| 최종 보고서 | DB 컬럼에 대응하는 보고서를 작성 이력에 기록하고 `response.artifacts`의 `analysis_report`로 공개. DB 저장은 이 산출물을 읽음 |
| 저장·재처리 | 각 시도와 성공·실패를 별도 기록. 기존 초안·검토·실패 기록은 유지 |

보고서 생성은 공통 그래프의 `report` 역할로 실행한다. 작업 선택·진행 판단에서 조회·가공하고, 응답 작성에서 뷰 선정·검토와 순차 설명·인사이트 작성·검토를 수행한다. 선정 검토가 부적합하면 공통 작업 선택으로 돌아간다. 실행 오류 후에는 이미 검증한 선정·설명을 유지하고 미완료 단계부터 이어간다.

적용 프롬프트는 [보고서 지침](../../src/instructions/analysis-report.md)과 [모델 입력 구성](../../src/prompting.py)에 있다. 요청 접수·동별 실행은 [API](../../api.py), 입력·산출물 구조는 [State](../../src/state.py), 선정·작성·검토와 모델 응답 구조는 [업무 노드](../../src/agent_nodes.py), DB 조회·저장은 [DB 연결](../../src/database.py)이 맡는다. 생성 결과와 State는 기존 출력 디렉터리 아래 `<run_id>/report.json`에도 남긴다. 이 파일은 재시작 복구에 사용하지 않는다.

## 6. 구현 범위와 남은 연결

보고서 전용 역할·작성 및 검토, 동별 실행·재처리, API와 직접 DB 저장을 연결했다. 작업 1은 공통 Agent가 수행하고 작업 2·3은 도구 없이 작성·검토한다.

로컬 상세 기록과 임시 파일 DB 연결은 [API 검증 안내](../api-roundtrip.md#6-보고서-생성-api의-임시-db-검증)를 따른다.
`report.json`에는 기존 사용자 요청과 같은 추적 형식으로 모델 입력·응답과 도구·노드·저장 기록을 함께 남긴다.
동별 재처리는 같은 기록기에 누적하며, 별도 업무 State나 재개 저장소로 사용하지 않는다.

| 연결 | 상태 |
| --- | --- |
| DB 직접 저장·NULL | INSERT·UPDATE 권한은 BE 측 부여 예정. 부분 NULL은 기존 DB 제약과 충돌하여 실제 연동 미완료. DB 스키마·권한은 AI에서 변경하지 않음 |
| 상세 근거 조회 | `region_result`, `bh_region_contribution`, 동·월·구분별로 합산한 `flow_detail` 일평균, 동 코드와 연결한 `bh_grid_anomaly` 조회 연결 |
| V06 요인별 기여도 | DB 저장 자료가 없어 실제 자료원 확인 대기. 원지표나 점수를 기여도로 바꾸지 않음 |
| V01 도시 중앙 50% 범위 | 계산 근거 공급 미연결. 현재는 해당 동의 월별 점수 조회가 가능하며 중앙 범위 수치는 만들지 않음 |
| Tableau 화면 | 그래프명과 설명을 저장. 실제 화면에 동일한 6개월 기간이 적용되는지는 미검증 |
| 실행 검증 | 모의 모델·임시 파일 DB로 로컬 HTTP 접수·생성·저장·상세 기록 검증. 로컬 INT-08 왕복 검증. 실제 모델·PostgreSQL·BE 왕복은 미검증 |
