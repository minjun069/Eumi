# AI 코드 작업 지침

공통 실행기와 연결 코드의 작성·수정·리뷰 전에 읽는다. 이 문서는 작업 방식과 판단 기준을 정한다. 특정 폴더명·클래스·프레임워크 선택을 영구 규칙으로 고정하지 않는다.

## 1. 사용자 의도와 구현 선택 구분

- 전체 구현에 대한 요청은 실행기·설정·모델 연결·데이터·검증·데모 전체에 적용한다. 언급된 파일이나 타입은 예시일 수 있으므로 그 요소만 정리하고 전체 요구를 처리했다고 말하지 않는다.
- 사용자 요구, 설계 문서의 명세, 현재 코드의 사실, 구현자가 제안한 선택을 구분해서 기록한다. 구현자의 해석을 ‘사용자가 정한 기준’이나 ‘합의된 구조’로 설명하지 않는다.
- 최신 사용자 결정이 이전 문서보다 우선한다. 의미가 불분명하면 이전 발언 일부로 의도를 단정하지 말고 질문한다.
- ‘최소 구조’는 파일·클래스 수만 줄이는 뜻이 아니다. 현재 동작에 필요한 책임·상태·검증만 남기고 전달·변환·동기화 비용을 줄인다.
- 이번 작업의 기준 흐름은 요청 → 행동 선택 → 호출 → 결과 검증 → 완료 또는 질문·재개다. 임시 Agent·도구·프롬프트는 이 흐름을 확인하는 데 필요한 만큼 둔다.
- 기존 폴더, 빈 파일, API 초안에 항목이 있다는 이유로 이번 구현 범위를 자동으로 넓히지 않는다.
- 초안에서 현재 타입을 참조한다는 이유만으로 호환성 요구를 만들지 않는다. 외부 입출력도 전체 구조와 함께 필요성을 검토한다. 호환성 질문은 실제 사용 중인 연동이나 사용자가 정한 유지 조건이 확인됐을 때 한다.

## 2. 질문할 시점과 방식

- 작업 시작 때 목표·범위·유지할 동작을 짧게 재진술하고, 확정된 요구와 확인이 필요한 부분을 구분한다.
- 다음 사항이 미확정이고 사용자 결정이 필요하면 그 결정에 의존하는 코드를 만들기 전에 질문한다: 요구 범위 해석, 실제 연동에 영향을 주는 입출력 변경, 기능 제거, 프레임워크 변경, 설정 입력 방식, 대기·재개·취소 정책, 새 공통 계층이나 연결 규격 도입. 전체 구조 재검토가 이미 요청됐으면 현재 자료형을 그대로 유지할지 다시 묻는 것으로 구현 판단을 미루지 않는다.
- 질문은 불확실성을 발견한 시점에 한다. 구현·문서화·커밋을 끝낸 뒤 사용자에게 확인받는 방식으로 진행하지 않는다.
- 저장소와 이전 결정을 먼저 확인하되, 추측을 사실처럼 써서 질문을 생략하지 않는다. 이미 정해진 사항을 다시 묻지는 않는다.
- 사용자의 선택이 필요한 질문에는 번호나 이름을 붙인 구체적인 선택지를 함께 제시한다. 질문에 쓰는 용어와 결정할 대상을 먼저 쉬운 말로 설명하고, 현재 근거와 결정이 필요한 이유를 밝힌다. ‘어떻게 할까요?’만 묻거나 전문 용어만 나열하지 않는다.
- 선택지는 항상 같은 결정 축으로 비교하며, 각 선택의 장점·단점과 실제 동작·구조에 미치는 영향을 설명한다. 추천안이 있으면 추천 이유를 함께 적되 사용자의 결정으로 간주하지 않는다.
- 사용자가 질문의 의미를 되물으면 설명한 뒤 선택지를 다시 제시한다. 이전 질문이나 별도 입력창을 찾아야 답할 수 있게 하지 않는다.
- 답이 필요한 결정은 무응답을 동의로 취급하지 않는다. 답변을 기다리는 동안 사용처 조사·테스트 확인·독립적인 문서 정리는 계속할 수 있다.
- 명칭·지역 변수·동작을 바꾸지 않는 단순 중복 제거까지 모두 질문하지 않는다. 사용자가 결정해야 할 제품 동작과 구현자가 판단할 수 있는 세부 구현을 구분한다.
- 질문에 대한 답변이 도착하면 관련 가정·계획·문서를 함께 갱신하고, 답변과 다른 구조를 조용히 채택하지 않는다.

## 3. 전체 구조 점검 순서

1. 현재 작업의 실행 흐름과 유지할 동작을 확인한다.
2. 설정 읽기, 모델 호출, 실행 제어, 데이터 정의, 검증, 하위 호출, 임시 데모의 실제 사용처를 전수 조사한다.
3. 각 구성을 다음 형식으로 평가한다.

   **현재 구성 → 소유하는 상태·책임과 실제 사용처 → 중복·불필요 여부 → 유지·통합·제거 제안 → 동작 영향**

4. 형식 검사, 실행 제한 검사, 결과 타당성 검사를 구분하고 각 규칙의 소유자를 정한다.
5. 남길 책임과 데이터를 기준으로 파일 배치·이름을 정한다. 폴더명이나 파일 이동부터 시작하지 않는다.
6. 구조나 동작에 대한 미확정 선택을 확인한 뒤 구현·검증·문서를 반영한다.

점검 결과에는 유지 근거도 포함한다. ‘이미 존재하므로 유지’, ‘메서드가 없으므로 제거’, ‘나중에 확장할 수 있으므로 추가’는 충분한 근거가 아니다.

## 4. 책임·검증·데이터 판단 기준

| 검토 대상 | 확인할 사항 |
| --- | --- |
| 설정 | 어디서 읽고 누가 사용하는가? 필드·검증·기본값이 중복되는가? 환경변수 허용 범위와 실제 동작이 일치하는가? |
| 모델 연결 | 요청 구성·응답 변환에 필요한 처리인가? 공통 실행 정책이나 업무 판단을 모델 어댑터에 넣었는가? |
| 실행 제어 | 횟수·시간의 원본은 어디인가? 같은 한도를 여러 객체가 복사·판단하는가? |
| 데이터 타입 | 실제 생산자·소비자와 검증 이점이 있는가? 같은 데이터를 별도 객체로 다시 포장하는가? |
| Agent·도구 연결 | 현재 다른 구현을 연결하는 데 필요한 규격인가? 미래용 범용 계층이나 전달용 객체인가? |
| 상태 | 각 복사본의 수명과 사용처가 다른가? 변경되지 않는 값을 여러 곳에 보관하는가? |
| 형식 검사 | 외부 요청·모델 응답·도구 입력 등 어느 경계에서 무엇을 거부해야 하는가? 내부 값을 근거 없이 반복 검증하는가? |
| 제한 검사 | 규칙은 한곳에서 정의하고 실제 호출·재시도·재개 직전에 적용하는가? |
| 결과 타당성 | 업무별 완료 판단과 공통 실행 상태 판단을 구분했는가? 검증 결과를 오류로 바꾸는 등 불필요한 변환이 있는가? |
| 임시 구현 | 실행 흐름 검증에 필요한가? 임시 도구·모델 연결이 공통 코드를 거꾸로 지배하는가? |

- 계산, 실행 중단, 모델 요청 timeout은 역할이 다르다. 같은 숫자를 사용한다는 이유로 합치지 않는다.
- 외부 입출력, 내부 상태, 도구별 데이터는 사용처를 이해하기 위한 구분이다. 각 범주마다 반드시 폴더·기반 클래스·변환 계층을 만들 필요는 없다.
- 입출력 규칙을 한곳에서 점검하는 관리 목적을 존중한다. 현재는 실행기·Agent·도구의 자료형과 데이터만으로 판단할 수 있는 검증을 `contracts/`에 모으고, 각 호출 지점이 이를 사용하도록 연결한다. 기능이 다르다는 이유만으로 분산 배치가 더 낫다고 단정하지 않는다.
- `Contract` 같은 공통 기반 클래스의 허용·금지를 절대 규칙으로 삼지 않는다. 공통 검증 정책을 실제로 공유하는 이점과 결합 비용을 비교한다. 제거할 때 검증이 약해지지 않는지 확인한다.
- 작은 자료형도 중첩 구조·필수값 검증·실제 재사용에 도움이 되면 유지할 수 있다. 클래스 수를 줄이려고 같은 검증을 수동으로 반복하지 않는다.
- 공개 결과, 모델 입력, 체크포인트의 목적을 구분한다. 비밀키가 포함된 설정 전체를 상태나 모델 입력에 넣지 않는다.
- 원본 상태와 외부에 전달하는 스냅샷을 구분한다. 격리에 필요한 복사는 유지하고, 변경할 소비자가 없는 중복 저장·동기화는 줄인다.
- 규칙의 정의 위치와 검사 시점을 구분한다. 허용 필드·필수값·자료형·값 범위·필드 간 일관성은 자료형과 함께 정의한다. 현재 질문·버전·누적 사용량 등 실행 상태가 필요한 검사는 해당 실행 지점에서 수행한다.
- 규칙을 중앙화했다고 실제 오류까지 한곳에서 관찰할 수 있다고 설명하지 않는다. 입력 경계가 검증을 거치는지와 실패가 어떤 오류 형식·코드로 전달되는지 테스트한다. 오류 수집·모니터링을 별도로 구현하지 않았다면 그 한계도 명시한다.

## 5. 근거와 문서 관리

- [프로젝트 명세](../../docs/README.md)와 현재 사용자 결정을 확인한다. 문서의 제안·미확정 사항을 구현 요구로 승격하지 않는다.
- 현재 코드 설명과 앞으로 적용할 제안을 구분한다. 아직 구현하지 않은 내용을 동작한다고 쓰지 않는다.
- 명세 충돌은 관련 문장과 동작 영향을 제시한다. 최신 문서에서 이미 해소된 충돌을 계속 미확정으로 남기지 않는다.
- 코드 작업 지침에는 재사용 가능한 판단 기준을 적는다. 현재 구현의 파일 배치·타입 선택을 정당화하기 위한 금지 규칙을 쌓지 않는다.
- 구조 검토 결과와 선택 근거는 별도 검토 기록이나 구현 README에 둔다. 확정된 동작과 미결정 항목을 구분한다.

## 6. 구현·검증·커밋

- 변경 전에 Git 상태와 사용자 수정분을 확인하고 보존한다. 다른 작업의 파일을 임의로 되돌리거나 커밋하지 않는다.
- 확정한 최소 구조로 구현한다. 기존 구현을 보호하기 위해 새 래퍼·변환 계층을 덧붙이지 않는다.
- 테스트는 현재 타입·파일 이름을 정당화하는 수단이 아니다. 요청, 호출, 검증 재작업, 질문·재개, 취소, 누적 한도, 상태 격리, 확보한 결과 보존을 검증한다.
- 구조 변경으로 import·타입 표현이 바뀌면 테스트도 조정하되, 기존 동작 검증을 단순 삭제해 통과시키지 않는다.
- 이번 변경에 맞는 테스트·정적 검사와 diff 확인을 수행한다. 기존 사용자 수정으로 생긴 문제와 이번 변경의 문제를 구분한다.
- 커밋은 하나의 책임이나 기능을 담는 최소 작업 단위로 구성한다. 파일 하나에 서로 다른 작업이 섞여 있으면 부분별로 나눈다.
- 기존 구현을 고치는 작업은 해당 구현 커밋에 흡수한다. 별도 ‘수정·리팩터링·재작업’ 커밋을 누적하지 않는다. 히스토리를 바꾸기 전에 사용자 작업을 보존하고 최종 결과와 중간 커밋의 의존성을 확인한다.
- 완료 보고에는 실제 변경, 유지·통합·제거의 근거, 검증 결과, 남은 결정 사항을 적는다. 구현자의 선택을 사용자 요구로 표현하지 않는다.
