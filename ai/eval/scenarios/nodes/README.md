# 기본 노드 시나리오 데이터셋

수정일: 2026-11-13. 상태: 기본 21개 경로 생성·입력 검증 완료, 오류 0개. 역할·보고서 전체 실행 입력 연결 지원. GMS로 독립 노드 131개 실행·원문 수집 완료. 작업 목적 파악 15개만 기존 채점 파일이 있으며 나머지 116개는 채점 미실행이다. 저장된 최근 판정은 실패 12개·미판정 3개다. LLM 기대답안을 제거하고 실행 당시 입력 전체를 제공하도록 변경한 뒤 재채점은 실행하지 않았다.

여섯 에이전트 역할의 정상적인 진입부터 반환까지를 구성하고, 그 안의 노드를 독립적으로 평가하는 자료다. 사용자 요청 계열은 세 역할에 대화 조건 네 가지를 적용한 12개, 보고서는 세 역할에 실제 지역 세 곳을 적용한 9개 경로로 구성한다.

이번 묶음은 정상 기본 동작을 확인한다. 호출 실패·정보 부족·검토 부적합에 따른 재작성·부분 노드 사례는 [확장 시나리오 보관본](../nodes-extended-v2/archive.md)에서 따로 관리한다. 보관본의 전체 경로 23개·고유 노드 사례 375개·노드 등장 320회·부분 그룹 81개는 현재 수량과 검증 결과에 합산하지 않는다.

검사 기준은 [노드 평가](../../docs/nodes/README.md)에 연결된 JSON을, 실행·채점 절차는 [평가 실행 안내](../../README.md)를 따른다.

각 시나리오의 시작 조건과 노드 순서는 [시나리오별 노드 흐름](flows.md)에서 확인한다.

## 1. 구성과 평가 단위

모든 경로는 담당 역할이 결과를 반환하는 완료 상태(`completed`)까지 이어진다. 사용자 요청 처리 경로에는 위임한 하위 에이전트의 실행도 포함한다. 해석·시각화의 독립 경로는 상위 요청 처리의 실제 호출로 만들어진 State에서 시작하고 상위로 반환하는 시점에 끝난다. 보고서 경로는 선정·설명·인사이트를 각각 한 에이전트의 진입·반환으로 나누며, 세 역할을 합친 보고서 전체 생성 경로로 세지 않는다.

고유 노드 사례와 평가 경로 내 노드 등장은 각각 131개다. 사용자 요청 계열이 95개, 보고서가 36개다. 하위 진입을 만드는 상위 준비는 별도로 24회다. 공유 사례는 0개이며, 실행 입력·역할·평가 기준이 모두 같은 사례가 없기 때문이다. 동일 사례의 식별자를 공유하는 기능은 유지한다. 부분 그룹과 모델 호출 없는 종료 사례도 0개다. 보완 답변은 이미 충분한 정보를 제공한 조건이므로 추가 질문 노드는 실행하지 않는다.

## 2. 어떤 상황을 확인하는가

### 사용자 요청 계열

세 역할마다 아래 네 조건을 적용한다. 이전 대화는 평가를 위해 작성했으며, 현재 요청의 지역·기간과 해석 근거는 고정 자료를 사용한다.

| 대화 조건 | 입력 상황 | 기대 동작 |
| --- | --- | --- |
| 이전 대화 없음 | 대상·기간·목적이 명확한 새 요청 | 현재 요청만으로 목표를 파악하고 필요한 작업 수행 |
| 이전과 다른 새 주제 | 앞 대화 뒤에 별개의 요청 | 새 목표를 적용하고 무관한 이전 조건을 이어 쓰지 않음 |
| 기존 응답 수정 | 앞 답변의 문장 수정, 비교 근거 추가, 기존 지도 기간 변경 | 직접 답변할 작업과 전문 역할에 위임할 작업을 구분 |
| 추가 질문에 충분한 답변 | AI가 물은 지역·월을 모두 제공 | 이전 목적과 보완 정보를 결합해 작업 완료 |

| 역할 | 이전 대화 없음 | 이전과 다른 새 주제 | 기존 응답 수정 | 추가 질문에 충분한 답변 |
| --- | --- | --- | --- | --- |
| 사용자 요청 처리 | 도곡1동 두 달 점수 비교를 해석 역할에 위임 | 상세 지도 요청을 시각화 역할에 위임 | 이전 점수 정의·한계를 짧게 고쳐 직접 답변 | 확인된 지역·월로 두 달 비교를 해석 역할에 위임 |
| 데이터 분석 결과 해석 | 두 달 점수 조회·차이 계산 | 현재 월 점수만 조회·설명 | 이전 정의·한계를 유지하며 실제 두 달 비교 근거 추가 | 확인된 지역·월로 두 달 조회·차이 계산 |
| 데이터 시각화 | 도곡1동 상세 지도 설정 검사 | 강남구 전체 배경 취약성 지도 설정 검사 | 같은 동의 지도 월을 변경해 설정 재검사 | 확인된 지역·월의 상세 지도와 행동 지표 기여도 차트 설정 검사 |

먼저 현재 요청과 대화에 있는 정보, 새로 확보할 결과를 정한 뒤 그에 맞는 기대 경로를 작성한다. 앞 답변의 문장만 고치는 요청은 사용자 요청 처리 역할이 조회·위임 없이 작성한다. 해석 역할의 수정 사례는 실제 비교 근거를 추가해야 하므로 상위가 전문 작업을 위임한다. 현재 월만 묻는 사례는 전월 조회·차이 계산을 하지 않으며, 시각화 두 개를 요청한 사례는 두 설정을 모두 검사한다. 같은 비교 요청을 완성한 보완 답변은 대화가 없는 비교 요청과 같은 작업 수를 가질 수 있다. 도시 지도와 상세 지도도 호출 수는 같지만 선택 뷰·지역 범위·입력 조건이 다르다.

경로 식별자는 `basic-<역할>-<대화 조건>`이다. 예를 들어 `basic-request-none`은 이전 대화가 없는 사용자 요청 처리 경로다. 보완 답변도 새 실행으로 시작하며, 이전 실행의 내부 결과나 공개 응답 상태를 복원하지 않는다. 이전 답변의 내용은 대화에 있으므로 판단·작성에 사용할 수 있다. 시각화의 정상 반환은 표시 설정을 제공했다는 뜻이며, 실제 Tableau 화면 표시 성공을 뜻하지 않는다.

해석·시각화의 네 가지 대화 조건은 **상위가 받은 사용자 대화의 조건**이다. 사용자가 전문 역할을 직접 호출한다는 뜻이 아니다. 각 사례를 생성할 때 사용자 요청 처리의 목적 파악 → 진행 판단 → 전문 역할 호출을 실제 노드로 실행하고, 호출 함수가 만든 하위 State를 시작 입력으로 받는다. 목표는 호출 인자에서, 조건·대화·이벤트·버전·누적 예산은 상위 State에서 이어받는다. 하위의 내부 작업 이력과 응답은 비우며 실행 ID는 새로 만든다. 이 규칙은 [하위 호출과 공유 예산](../../../docs/agent/state.md#실행-예산)을 따른다.

위임 준비 3개 노드는 8개 전문 역할 사례마다 `entry_transition`에 보관한다. 준비 기록 24회는 평가 경로의 노드 실행 수와 고유 노드 사례 수에 넣지 않는다. 하위 반환을 실제 상위 호출 결과에 기록하고 누적 사용량을 반영한 상태도 준비 기록에서 확인한다. 상위의 최종 답변 작성은 이 독립 하위 평가의 범위에 포함하지 않는다.

### 보고서 생성

| 지역 | 코드 | 선정 경로 | 설명 경로 | 인사이트 경로 |
| --- | --- | --- | --- | --- |
| 도곡1동 | `1168065500` | 1개 | 1개 | 1개 |
| 대치4동 | `1168063000` | 1개 | 1개 | 1개 |
| 효자1동 | `5111062000` | 1개 | 1개 | 1개 |

기준 월은 2025년 12월이다. 선정 입력은 기간과 서로 다른 상세 뷰 세 개를 요구한다. 조회한 점수 변화, 현재 최고 기여 지표와 전월 값, 실제 격자 예시의 차이를 근거로 세 뷰와 설명 범위를 선정한다. 입력에 특정 세 종류의 뷰를 정답으로 지정하지 않는다. 설명 역할은 승인된 선정 범위의 설명 세 개를, 인사이트 역할은 승인된 설명에 근거한 핵심 관측과 한계 네 문장을 작성·검토한다. 각 역할은 작업 진행 판단(`decide`)으로 진입한다.

세 동은 같은 종류의 자료가 제공되고 추가 보완 없이 세 뷰를 승인할 수 있어 선정 경로가 각각 8개 노드다. 설명·인사이트는 승인된 앞 단계 결과만으로 작성할 수 있어 각각 2개 노드다. 노드 수가 같아도 판단에 인용한 지역별 관측값과 최종 설명 방향은 다르다. 작성 노드 내부의 후속 작성·검토 모델 호출은 별도 노드로 세지 않는다.

경로 식별자는 `basic-<보고서 역할>-<지역 코드>`다. 예를 들어 `basic-report_selection-1168065500`은 도곡1동의 선정 역할이다. 후속 역할의 `upstream_scenario_id`는 앞 역할의 경로를 가리킨다. `entry_transition`에는 앞 역할의 실제 반환 상태와 단계 진입 기록을 추가한 상태를 보관한다. 기존 `report_stage_state`로 전환하며, 승인 결과·응답·메시지·누적 예산을 보존한다. 이 연결 정보는 업무 State 밖의 평가 메타데이터다.

보고서의 대화 조건은 모두 사용자 대화 없음(`none`)이다. 최초 선정 입력에 사용자 발화를 만들지 않는다. 후속 역할에는 현재 런타임에 따라 앞 역할이 남긴 내부 AI 응답 이력이 이어질 수 있으며, 이를 이전 사용자 대화로 분류하지 않는다.

## 3. 입력·기대 결과·실행 경로

[scenarios.json](scenarios.json)은 `node-scenarios-v4` 형식의 공통 색인이다. 생성·자료원 정보, 고유 노드 사례 색인(`case_index`), 집계(`summary`)와 시나리오별 `id`·`title`·`file`을 보관한다. 각 시나리오의 시작부터 반환까지의 본문은 `scenarios/` 아래 별도 JSON 파일에 있다. 파일명은 시나리오 ID의 밑줄을 하이픈으로 바꾸며, 본문의 ID는 유지한다.

| 저장 위치 | 자료 | 내용 |
| --- | --- | --- |
| 노드 파일 | `initial` | 해당 노드 직전의 요청·대화·작업 이력·응답·실행 상태 |
| 노드 파일 | `assessment` | 실행 전에 정한 검사·호출 범위와 규칙 검사 비교 조건. LLM은 항목 식별·선택 정보만 사용 |
| 개별 시나리오 파일 | `scope`, `agent_role` | 평가 범위 `agent`와 담당 역할 |
| 개별 시나리오 파일 | `start_state`, `terminal` | 에이전트 진입 상태와 최종 반환 |
| 개별 사용자 시나리오 파일 | `task_rationale` | 현재 요구, 시작 시 가용·부족 정보, 필요한 작업과 제외할 작업 |
| 개별 시나리오 파일 | `steps` | 노드·역할, 실행 전후 상태, 사례 참조와 고정 모델 응답 |
| 개별 해석·시각화 시나리오 파일 | `entry_transition` | 상위의 준비 3단계, 실제 하위 진입 State, 상위 호출 기록에 보존된 하위 반환 |
| 개별 보고서 시나리오 파일 | `entry_transition` | 앞 역할 반환에서 다음 역할 진입까지의 상태 전달 |
| 개별 보고서 시나리오 파일 | `decision_basis` | 진행 판단 시점에 확보한 근거 기록 ID와 그 판단 이유 |
| 공통 색인 | `case_index`의 `usages` | 고유 사례를 사용하는 경로와 단계의 연결 |

`step_id`는 경로 안의 위치이고 `case_id`는 독립 노드 사례의 식별자다. `input_ref`·`expectation_ref`와 `evidence_refs`의 스냅샷 경로는 데이터셋 루트인 `nodes/`를 기준으로 한다. 시각화 근거의 `catalog` 경로인 `src/tools/tableau_catalog.json`은 `ai/`를 기준으로 한다. 개별 시나리오 파일의 위치에 맞춰 이 참조들을 다시 해석하지 않는다. 같은 실행 입력과 기준이면 식별자를 공유할 수 있지만 역할·이력·누적 예산이 다른 사례를 같은 사례로 합치지 않는다.

### 노드 입력과 경로 생성

경로 생성은 입력별 기대 판단과 고정 모델 응답을 작성한 뒤 현재 `build_nodes`·`run_node`와 실제 도구를 실행한다. `before_state`·`after_state`는 그 실행 전후 상태다. 사용자 요청 처리 경로 안의 하위 호출·반환은 `frame`과 `boundary_before`로 연결하고, 독립 전문 역할의 진입 출처는 `entry_transition`으로 연결한다. 시작 예산에 숫자를 주입하거나 다른 사례의 노드를 잘라 붙이지 않는다. `model_outputs`는 평가 시점을 구성하는 고정 응답이며 품질 기준인 `assessment`와 구분한다. 모델이 입력을 보고 자율적으로 이 경로를 선택한 기록은 아니며, 외부 모델 호출은 0회다.

`initial.execution`은 상태·버전·예산·오류를 보존한다. 독립 평가에서는 이를 복원하고 `run_id`만 새 실행 식별자로 바꾼다. 분류·경로 연결 정보와 기대 결과는 모델 업무 입력에 섞지 않는다.

| 노드 | 실행 파일 | 사례 수 |
| --- | --- | ---: |
| 작업 목적 파악 | [interpret.json](interpret.json) | 15 |
| 작업 진행 판단 | [decide.json](decide.json) | 58 |
| 작업 선택·실행 | [act.json](act.json) | 34 |
| 응답 작성 | [compose.json](compose.json) | 24 |
| 사용자 정보 요청 | [ask.json](ask.json) | 0 |

`ask.json`은 이번 범위에 해당 사례가 없는 빈 묶음으로 유지한다.

## 4. 실제 근거와 자료 제약

[스냅샷](snapshots/data.json)은 2026-11-11에 설정된 서비스 DB `eumi`에서 읽기 전용으로 확보했다. 합성 평가 DB `eumi_eval`의 자료와 구분하며, 생성·검증 때 DB를 다시 읽거나 쓰지 않는다.

| 자료원 | 내용 | 스냅샷 지역 수 | 행 수 |
| --- | --- | ---: | ---: |
| `public.region_result` | 월별 분석 점수 | 47 | 235 |
| `analysis.bh_region_contribution` | 행동 지표별 점수 기여도 | 47 | 2,820 |
| `analysis.bh_grid_anomaly` | 격자별 행동 이상 점수 | 4 | 12,892 |
| `analysis.flow_detail` | 활동 상세값 | 0 | 0 |

위 수량은 전체 스냅샷 기준이다. 현재 보고서 사례는 그중 세 지역과 필요한 기간을 조회한다. [원본 조회 결과](snapshots/raw-query-results.json)는 소수를 정확한 문자열로 보존하고, 스냅샷에는 조회 조건·시각·변환·출처·해시를 기록한다. [수집 스크립트](capture_snapshot.py)로 다시 수집할 때는 새 출력 경로를 지정한다.

V01의 요청 범위는 2025년 7~12월의 최근 6개월이지만 실제 자료는 8~12월의 5개월이다. 도시 중앙 50% 범위의 계산 근거도 없다. 제공된 월의 점수만 설명하고 빠진 월과 중앙 범위 비교를 제외한 상태로 세 뷰의 승인 범위를 완성한다. 따라서 정상 완료는 완전한 6개월 자료를 확보했다는 뜻이 아니다. 활동 상세값·배경 취약성 요인별 기여도도 관측값을 만들어 채우지 않는다.

## 5. 현행 평가 기준과의 연결

[coverage.json](coverage.json)의 `criterion_rows`는 현행 공통·노드별 JSON의 검사 행 57개를 원문·위치·해시와 함께 보관한다. 각 행은 실제 `assessment`의 평가 항목과 경로 사용 위치에 연결한다. 규칙 검사는 항목의 비적용 선언을 반영하며, LLM 검사는 실제 호출 조건에 맞는 행을 연결한다. 과거 Markdown의 시험 번호·분기 태그를 현재 연결 수로 사용하지 않는다.

| 상태 | 뜻 | 검사 행 수 |
| --- | --- | ---: |
| `mapped` | 이번 사례의 실제 평가 항목에 연결됨 | 49 |
| `uncovered` | 해당 호출 조건의 사례가 있으나 필요한 평가 항목이 빠짐 | 0 |
| `out_of_scope` | 이번 기본 묶음에 평가 항목이 필요한 호출 조건이 없음 | 8 |

검사 ID 30개 중 실제 평가 항목에 연결된 검사는 26개다.

모든 노드 LLM 검사는 [평가 자료 계약](../../README.md#평가-자료-준비)에 따라 실행 당시 모델 호출 입력 전체·실제 출력과 현행 검사 기준으로 판정한다. 저장된 메시지의 순서·역할·본문·업무 지침·도구 명세·작업 이력과 당시 응답 스키마를 그대로 제공한다. `expected.items`의 ID·검사 ID·호출 범위는 선택과 결과 연결에 사용하며, 별도 기대답안·비교 조건은 프롬프트에 제공하지 않는다. 규칙 검사의 독립 기대값과 자료는 기존 용도로 유지한다.

현재 `unit=node` 평가는 해당 시점의 최초 모델 응답 한 건을 수집·채점한다. 도구·하위 호출·상태 반영·후속 노드 전이는 실행하지 않는다. 보고서 경로 생성에는 작성 뒤 검토 호출이 포함되지만, 이번 독립 노드 사례에는 그 후속 검토와 나머지 설명 작성 호출을 별도로 연결하지 않았다. 이 호출들의 품질을 검사한 것으로 집계하지 않는다. 독립 검토 평가에는 검토 대상 초안과 `model_call`을 지정한 별도 입력이 필요하다.

하위 목표를 전달하는 사례는 해당 요청의 대상·기간·목적·결과 범위를 보존하는 동등한 표현을 허용한다. 현재 규칙 평가는 이 의미 동등성을 판정하지 못하므로 해당 인자 검사(`N02-O.3`)를 비적용이 아닌 미판정으로 남긴다. 보고서 조회 인자의 자동 규칙은 자료원만 대조하며, 지역·기간을 포함한 전체 인자는 `reference`의 독립 기준과 직접 대조한다. 필터 순서는 정답으로 고정하지 않는다.

연결 수는 준비 범위이며 모델 통과 수가 아니다. 분모·미실행·미판정·합격 조건은 [노드 평가](../../docs/nodes/README.md)를 따른다.

## 6. 생성과 평가 실행

명령은 `Eumi/ai`에서 실행한다. [생성기](../../scripts/build_node_dataset.py)는 고정 스냅샷으로 현재 역할 경로를 새로 실행해 입력을 만들며, 보관본의 중간 사례를 잘라 쓰지 않는다. [입력 검사기](../../scripts/validate_node_dataset.py)는 모델 호출 없이 입력·경로·기준 연결과 원자료를 대조한다.

```powershell
uv run python -m eval.scripts.build_node_dataset
uv run python -m eval.scripts.validate_node_dataset
uv run python -m eval validate eval/scenarios/nodes/interpret.json
```

에이전트 단위 실행은 기존 색인을 그대로 읽으며 별도 실행용 파일을 생성하지 않는다. 단위를 생략하면 21개 역할 사례를 실행한다. 보고서 전체는 선정 시나리오의 역할 진입 전 상태에서 시작한다. 업무 모델 연결 설정이 필요하며 아래 채점에는 평가 모델을 사용하지 않는다.

```powershell
uv run python -m eval validate eval/scenarios/nodes/scenarios.json
uv run python -m eval run eval/scenarios/nodes/scenarios.json --unit agent --case basic-request-revision --repeat 3
uv run python -m eval run eval/scenarios/nodes/scenarios.json --target interpretation
uv run python -m eval run eval/scenarios/nodes/scenarios.json --unit workflow --target report --case basic-report_selection-1168065500
uv run python -m eval score-executions <실행묶음경로>
```

역할 시작 상태의 대화·앞 단계 승인 결과·누적 예산을 보존하고, 이후 단계 결과·예시 답변·고정 응답·노드 품질 기준은 새 실행에 주입하지 않는다. 실제 실행 결과를 다음 시나리오에 자동 전달하지 않는다. `score-executions`는 모든 역할의 시간·호출량·토큰·비용을 집계하고 사용자 요청 전체·보고서 전체에는 기존 EX 규칙을 적용한다. 다른 역할 단독 실행의 EX 기능 판정은 제공하지 않는다. 실제 최종 답변·보고서의 품질은 같은 실행 묶음에 `score-outputs`를 적용해 [응답 작성 기준으로 별도 평가](../../docs/runner.md#9-최종-출력-품질)한다. 선택·출처 보존·단가 설정은 [실행기 안내](../../docs/runner.md#기존-시나리오-직접-실행)를 따른다.

독립 노드의 실제 모델 평가는 노드 파일에서 사례 식별자를 골라 실행한다. 업무 모델과 평가 모델의 연결 설정이 필요하다.

```powershell
uv run python -m eval run eval/scenarios/nodes/interpret.json --case <노드 사례-ID> --repeat 3
uv run python -m eval score-nodes eval/outputs/evaluations/<노드명>/<묶음-ID> --method all --judge-model <평가 모델 이름>
```

독립 노드 평가의 출력은 다음 사례에 자동으로 전달하지 않는다. 노드 파일을 사용한 위 명령의 평가 단위는 개별 노드의 모델 응답이다.

## 7. 검증과 남은 평가

아래 실행·채점 기록은 로컬 생성 산출물이며 Git에 포함하지 않는다. 경로는 해당 결과가 있는 작업 환경에서 확인한다.

2026-11-13에 `interpret.json`의 작업 목적 파악 사례 15개를 GMS의 `gpt-6-luna`로 각각 1회 실행했다. 15개 모두 HTTP 200으로 응답했고 요청·응답 모델명, 원본 응답 15건과 실행 기록 저장을 확인했다. 로컬 결과는 `eval/outputs/evaluations/interpret/노드평가_2026-11-13_실행01`에 보관한다.

이어서 작업 목적 파악을 제외한 116개도 같은 GMS 모델로 각각 1회 실행했다. 모두 HTTP 200으로 응답했고 요청·응답 모델명 `gpt-6-luna`, 원본 응답 116건, 사례 누락·중복 없음, 입력 파일 3개의 해시 유지와 채점 미실행을 확인했다. 추가 질문은 사례가 0개다. 결과는 아래 노드별 폴더에 보관한다.

| 실행한 노드 | 원문 저장 수 | 저장 묶음 |
| --- | ---: | --- |
| 작업 진행 판단 | 58 | `eval/outputs/evaluations/decide/노드평가_2026-11-13_실행01` |
| 작업 선택 및 실행 | 34 | `eval/outputs/evaluations/act/노드평가_2026-11-13_실행02` |
| 응답 작성 | 24 | `eval/outputs/evaluations/compose/노드평가_2026-11-13_실행03` |

작업 목적 파악 15개의 저장 결과를 GMS의 `gpt-6-sol`로 규칙·LLM 채점했다. 첫 채점에서 제공한 표식의 대괄호 표기 차이로 14개가 미판정이 되어, 허용된 표식의 정확한 표기 차이만 처리하도록 수정하고 재채점했다. `assessments`의 `채점01`은 보존하며 당시 재채점 결과는 `노드평가_2026-11-13_실행01_채점02/manifest.json`에 보존한다. 재채점의 모델 호출 15회는 모두 HTTP 200으로 응답했다.

| 당시 채점 범위 | 자동 판정 |
| --- | --- |
| 출력 형식 | 15개 통과 |
| 목표·조건 포함 | 12개 실패, 3개 미판정 |
| 자료 사용 범위·자료 속 지시 배제·목표와 조건 해석 | 선행 실패·미판정으로 각 15개 미실행 |
| 사례별 종합 | 실패 12개, 미판정 3개 |

미판정 3개는 평가 모델이 별도의 기대 내용이 제공되지 않아 전체 필수 항목과 대조할 수 없다고 판단했다. 일부 실패는 업무 모델의 원래 지침에 있는 `process_data` 계산 기록 요구를 평가 입력에서 확인하지 못해 요청 밖 조건의 추가로 판정한 것이므로, 자동 실패를 확정된 업무 모델 결함으로 해석하기 전에 평가 입력 범위를 검토해야 한다. `채점02`에서는 기준·기대 항목·입력 범위를 변경하지 않았다. 사례의 필수 여부와 운영 목표가 지정되지 않아 필수 사례 전체·운영 목표의 종합 통과도 판정하지 않는다.

`채점02` 뒤에는 기존 `reference`의 목표·조건과 동등 표현 허용 기준을 두 검사의 기대값 30개에 연결하고, 실제 저장 응답으로 평가 입력 30개의 전송·인용 경로를 확인했다. 당시의 연결 검증 기록 (`eval/outputs/evaluations/interpret/노드평가_2026-11-13_실행01/expected-answer-linkage-validation.json`)은 과거 작업 기록으로 보존한다. 원본 사례·실행 응답·이전 채점 등 기존 파일 65개도 그 단계에서 보존했다.

이후 사용자 결정에 따라 모든 노드 LLM 검사에서 기대답안 연결·비교 절차와 기대값 누락에 따른 호출 차단을 제거했다. 생성기·`interpret.json`과 저장 실행의 `suite.json`에 추가했던 기대값 30개도 제거했다. 저장 실행에서는 삭제 전 값이 앞서 추가한 내용과 같은지 확인했으며, 나머지 기존 파일 66개의 해시가 유지됐다. 이전 연결 기록을 포함한 보존 결과는 제거 검증 기록 (`eval/outputs/evaluations/interpret/노드평가_2026-11-13_실행01/expected-answer-removal-validation.json`)에 남겼다.

기대값을 연결했던 단계의 관련 9개 테스트 파일에서는 270개 검사가 통과했다. 그 단계에서 생성 기록과 문서의 해시 차이로 실패한 3개는 메타데이터 갱신 후 재검증했고, 데이터셋 입력 검증·Ruff 검사·포맷 검사·문서 참조 검사도 통과했다. 이는 현재 기대답안 제거 이후의 검증 수가 아니다.

기대값 제거 이후 모든 노드 LLM 검사의 입력 범위를 실행 당시의 전체 메시지와 응답 스키마로 바꿨다. 업무 지침·자료 본문·실패·검토 이력도 원문대로 제공하며, 승인된 자료 등 사용할 수 있는 근거의 범위는 기존 검사 기준으로 판정한다. 업무 역할·State·검사 단계 순서·평가 대상 출력의 선택 범위는 유지한다.

저장된 작업 목적 파악 15개에 두 검사를 적용해 평가 프롬프트 30개를 구성했다. 원래 메시지와 응답 스키마가 보관 구조·전송 JSON·인용 경로에서 동일하게 복원되고, `process_data` 계산 기록 요구와 행동 이상 점수 정의가 모두 제공되는지 확인했다. 기대답안·비교 자료를 바꿔도 전송 프롬프트는 같았다. 전체 LLM 검사 37개 행의 입력 선언도 대조했다. 모델 호출 없이 수행한 전체 입력 전달 검증 (`eval/outputs/evaluations/interpret/노드평가_2026-11-13_실행01/full-model-input-validation.json`)에 결과와 기존 69개 파일의 해시 보존을 기록했다.

위 표는 전체 입력 제공 변경 이전의 평가 방식으로 얻은 결과다. 원본 업무 모델 응답과 이전 채점은 보존하며, 최신 재채점 결과는 각 노드 실행 폴더의 `assessments`에서 확인한다.

같은 범위를 다시 실행하려면 GMS 키를 [설정 예시](../../../.env.gms.example)에 따라 `.env.gms`에 준비한 뒤 다음 명령을 사용한다. 새 실행 묶음이 생성된다.

```powershell
uv run python -m eval run eval/scenarios/nodes/interpret.json --env-file .env.gms --model gpt-6-luna --repeat 1 --output eval/outputs/evaluations
```

기존 결과만 다시 채점하려면 다음 명령을 사용한다. 업무 모델은 다시 실행하지 않으며 새 채점 번호로 저장한다.

```powershell
uv run python -m eval score-nodes "eval/outputs/evaluations/interpret/노드평가_2026-11-13_실행01" --method all --judge-model gpt-6-sol --env-file .env.gms
```

최종 생성본의 [입력 검증 결과](validation.json)는 `valid=true`, 오류 0개다. 검증 결과에 기록한 자료 30개와 현재 파일의 해시가 일치한다. 보관본의 375개 통과 결과와 테스트 수는 현재 기본 묶음에 합산하지 않는다.

표의 조회·가공 건수는 검사 수행 수이며 경로상 도구 호출 수와 구분한다. 자연어 의미 검토 대상 710개는 근거·기준을 연결한 수량이며 자동으로 품질 통과를 판정한 수량이 아니다.

관련 테스트 8개 파일의 134개 검사가 통과했다. 저장한 검증 해시, 동일 자료의 재생성 결과, 시나리오 파일 분리와 참조, 입력별 필요한 작업, 실제 상위 준비에서의 하위 진입, 보고서 단계 전달, 하위 호출·산출물 보존, 잘못된 예산 전달의 검출, 보관본 무결성을 포함한다.

색인을 직접 받는 실행은 [입력 연결](../../tests/test_scenario_input.py)·[명령 연결](../../tests/test_scenario_cli.py)·[실제 그래프와 채점](../../tests/test_scenario_execution.py)의 45개 검사가 통과했다. 기존 상태·자료원·예산 보존과 평가 자료 분리를 확인하고, 모델 응답만 대체한 실행의 저장 증거로 EX 기능 검사와 운영 집계까지 대조한다. 전체 사용법과 지원 범위는 [시나리오 직접 실행](../../docs/runner.md#기존-시나리오-직접-실행)을 따른다.

입력별 검토에서는 상위에서 직접 처리할 문장 수정과 전문 역할에 위임할 근거 추가를 구분하고, 새 주제에 맞는 하위 역할·뷰 선택, 현재 월 단독 조회, 두 산출물 요청의 완료 범위를 확인했다. 전문 역할 8개는 상위 준비 기록 삭제, 상속 예산 초기화, 대화·조건·호출 목표·반환값 변조를 검출한다. 같은 역할이라는 이유만으로 같은 작업을 요구하지 않으며, 정상 비교 작업은 대화 조건이 달라도 같은 경로를 허용한다. 이 기대 경로의 직접 검토와 회귀 검사는 일반적인 자연어 요청에 대한 최적 판단을 자동으로 증명하지 않는다.

보고서에서는 조회 전에는 아직 확보하지 않은 수치·지표·격자를 판단 이유에 넣지 않고, 조회 후 실제 관측과 선정 이유를 대조한다. 보고서 세 지역의 점수 설명과 인사이트에서 확인한 값은 다음과 같다.

| 지역 | 11월 점수 | 12월 점수 | 설명 방향 | 현재 최고 기여 지표 |
| --- | ---: | ---: | --- | --- |
| 도곡1동 | 47.82 | 53.06 | 증가 | `h29_senior_gender_change_gap` |
| 대치4동 | 58.56 | 54.31 | 감소 | `h19_age_entropy` |

점수 설명은 관측된 5개월의 값과 전체·전월 방향을, 기여도 설명은 같은 지표의 전월·현재 값을 담는다. 격자 설명은 중복 없는 실제 두 격자의 서로 다른 점수를 예시로 제시하며 전체 범위나 위치 집중으로 일반화하지 않는다. 이 값들과 실제 조회 기록 참조를 독립 기준에 남겼다. 보고서 설명의 자동 수치 대조는 첫 설명의 현재 월 점수에 한정한다.

인사이트는 승인된 점수 변화·최고 기여 지표의 변화·두 격자 예시의 차이·해석 한계를 중복 없는 네 문장으로 요약한다. 이 직접 대조와 고정 응답으로 실행한 경로 검사는 외부 모델의 출력 품질 평가를 대신하지 않는다.

독립 노드 131개의 업무 모델 실행은 완료했으며, 위 작업 목적 파악 15개 외의 평가 모델 판정과 반복 평가·별도 사람 검수는 미실행이다. HTTP 접수·DB 저장·완료 알림·실제 Tableau 표시와 운영 자료 최신성도 이번 검증 범위에 포함하지 않는다.
