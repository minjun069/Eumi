# 노드 시나리오 데이터셋

수정일: 2026-11-12. 상태: v2 사례 생성·입력 검증 완료, 모델 평가 미실행.

사용자 요청과 보고서 생성 상황에서 노드가 적절한 목표·선택·판단·응답·질문을 출력하는지 확인하는 평가 자료다. 시작부터 반환까지 이어지는 전체 경로 23개와, 특정 조건만 따로 확인하는 부분 사례를 제공한다. 같은 입력과 평가 기준을 쓰는 노드는 여러 경로에서 하나의 사례 식별자를 공유한다.

이 문서는 사례 구성·자료 출처·사용법·준비 상태를 설명한다. 검사 항목과 판정 기준은 [노드 평가](../../../docs/eval/nodes/README.md), 입력 형식과 채점 절차는 [평가 실행 안내](../../README.md)를 따른다.

## 1. 데이터셋 구성

시나리오는 실행을 시작한 이벤트로 나눈다. 사용자 요청에서 하위 에이전트를 호출해도 하위 실행은 같은 시작 이벤트에 속한다. 전체 경로는 해당 요청의 반환까지 기록했다는 뜻이며, 성공뿐 아니라 부분 완료·실패·사용자 답변 대기로 끝나는 경로도 포함한다.

| 시작 이벤트 | 전체 경로 수 | 경로 내 노드 등장 수 | 부분 사례 그룹 수 | 부분 노드 사례 수 |
| --- | ---: | ---: | ---: | ---: |
| 사용자 요청 | 15 | 140 | 36 | 61 |
| 분석 완료 | 8 | 180 | 45 | 64 |
| 합계 | 23 | 320 | 81 | 125 |

전체 경로의 320개 노드 등장은 고유 사례 250개를 참조하며, 그중 27개 사례가 둘 이상의 경로에서 공유된다. 기존 부분 사례 125개를 더하면 고유 노드 사례는 375개다. 기존의 81개 그룹은 중간 시점의 입력을 묶은 부분 사례이며, 시작부터 종료까지 실행한 전체 경로 수에 포함하지 않는다.

실행 파일은 노드별로 분리했다. 응답 작성에는 일반 답변과 보고서의 작성·검토가 포함된다.

| 노드 | 실행 파일 | 고유 사례 수 | 평가 기준 |
| --- | --- | ---: | --- |
| 작업 목적 파악 | [interpret.json](interpret.json) | 39 | [목적 파악 검사](../../../docs/eval/nodes/interpret.md) |
| 작업 선택·실행 | [act.json](act.json) | 110 | [작업 선택 검사](../../../docs/eval/nodes/act.md) |
| 작업 진행 판단 | [decide.json](decide.json) | 123 | [진행 판단 검사](../../../docs/eval/nodes/decide.md) |
| 응답 작성 | [compose.json](compose.json) | 97 | [응답 작성 검사](../../../docs/eval/nodes/compose.md) |
| 사용자 정보 요청 | [ask.json](ask.json) | 6 | [정보 요청 검사](../../../docs/eval/nodes/ask.md) |

보고서에 사용할 승인 산출물이 없는 경우 모델 없이 단계를 종료하는 응답 작성 사례가 2개 있다. 이 사례는 `model_call_count=0`, `assessment.required=false`로 표시한다. 따라서 모델 평가 대상은 고유 사례 373개이고, 전체 경로에서 모델을 호출하는 노드 등장은 318개다. 보고서 응답 작성은 한 노드 안에서 작성·검토를 여러 번 호출할 수 있으므로 노드 등장 수와 모델 호출 수는 다르다.

## 2. 경로와 공유 사례 읽기

[scenarios.json](scenarios.json)의 형식은 `node-scenarios-v2`다. 경로에는 업무 상황과 실행 순서를, 노드 파일에는 독립 실행에 필요한 입력과 평가 기준을 둔다.

| 구성 | 내용 | 저장 위치 |
| --- | --- | --- |
| 전체 경로 | 시작 상황, 조건, 실행 중 사건, 시작 상태와 최종 반환 | `scenarios` |
| 경로의 한 단계 | 노드·역할, 실행 전후 상태, 사례 참조, 구성에 쓴 모델 응답 | 경로의 `steps` |
| 하위 호출·반환 경계 | 상위와 하위 실행의 진입·반환 연결 | 단계의 `boundary_before` |
| 보고서 단계 경계 | 역할 전환과 최종 산출물 구성 | 경로의 `boundaries` |
| 부분 사례 그룹 | 특정 조건과 준비한 평가 시점의 연결 | `partial_groups` |
| 전체 경로에서의 사용 위치 | 같은 사례를 사용하는 경로와 단계 | `case_index`의 `usages` |
| 부분 그룹에서의 사용 위치 | 같은 사례를 사용하는 부분 그룹과 단계 | `case_index`의 `partial_usages` |
| 실행 입력 | 요청·대화·작업 이력·기존 응답·실행 상태 | 노드 사례의 `initial` |
| 평가 기준 | 적용 검사, 필수 내용, 허용 대안, 기준 수치와 근거 | 노드 사례의 `assessment` |

`step_id`는 경로 안의 위치이고 `case_id`는 여러 경로에서 재사용할 노드 사례다. 단계의 `input_ref`와 `expectation_ref`는 해당 사례의 입력과 평가 기준을 가리킨다. 사용 위치는 사례의 설명이나 태그를 나누어 읽는 대신 `case_index`에서 확인한다. 기존 부분 사례의 식별자는 유지하고, 중복을 통합한 경우 다른 식별자를 `aliases`에 보존한다.

예를 들어 정상 보고서 경로 `report-path-three`와 선정 재작성 경로 `report-path-selection-rewrite`는 최초 조회 단계 `s001`에서 같은 사례 `path-act-b592d3b3acfe09e173b4`를 사용한다. 분기 전 입력·기준이 같으면 공유하고, 초안 결함이나 검토 결과로 이후 입력이 달라지면 별도 사례가 된다.

### 실행 이력과 평가 기준

전체 경로는 미리 작성한 모델 응답을 넣고 실제 `build_nodes`·`run_node`를 실행해 만들었다. 조회·가공은 고정 스냅샷에 실제 도구 구현을 적용한다. `before_state`와 `after_state`는 이 실행의 전후 상태이며, 외부 업무 모델이나 평가 모델 호출은 0회다.

`model_outputs`는 평가 시점을 만들기 위한 고정 응답이다. 품질의 정답은 별도로 작성한 `assessment`다. 재작성 분기는 의도적으로 잘못된 초안과 부적합 검토를 넣어 만들었고, 결함·검토·보완 사건을 `events`에 기록한다. 잘못된 고정 응답이 해당 노드가 따라야 할 정답으로 바뀌지는 않는다. 이 이력은 실제 모델의 성공률이나 운영 중 관측한 실행 기록을 뜻하지 않는다.

전체 경로에서 추출한 `initial.execution`은 상태·버전·예산·오류를 보존한다. 단독 평가에서는 이를 복원하되 `run_id`만 새 실행의 식별자로 바꾼다. 기존 부분 사례는 이전 입력 형식을 유지하며, 실행 상태를 생략하면 평가 실행기의 기본값을 사용한다. 분류 정보와 평가 기준은 모델 업무 입력에 섞지 않는다.

### 호출과 단계 전환

각 사례의 노드 평가는 준비된 입력에서 모델 원본 응답 한 건을 수집한 뒤 멈춘다. 앞 사례의 평가 출력을 다음 사례에 넘기지 않는다. 작업 선택의 도구·하위 에이전트 호출, 응답의 산출물 조립·렌더링, 상태 반영·전이·완료는 실행하지 않는다. 사례에 남아 있는 고정 하위 응답 설정은 노드 단독 평가에서 사용하지 않으며, 전체 경로 생성과 에이전트·생성 흐름의 실행 평가에서 사용한다.

저장된 전체 경로의 상위 작업 선택 단계는 하위 호출 완료까지 포함한다. `expected_next_nodes`는 이 실행 경로의 다음 노드이며 모델 원문 채점의 필수 조건이 아니다. 하위 진입·반환은 실행 구간을 나타내는 `frame`과 경계 기록으로 구분한다. 부분 그룹은 다음 준비 사례를 연결하며, 중간 실행이 생략될 수 있다.

보고서는 작업 선택으로 진입해 선정 → 설명 → 인사이트를 같은 실행 상태와 누적 예산으로 진행한다. 역할 전환은 하위 에이전트 호출이 아니다. `report_handoff`는 단계 전환, `publish_report`는 검토된 결과와 미완성 항목으로 최종 보고서를 구성하는 실행 경계다. 모델 없이 단계를 종료하는 2개 사례와 이 경계는 모델 품질 평가와 분리해 확인한다.

보고서 노드에서 여러 모델 호출을 포함하도록 작성한 기존 사례는 독립 호출별 입력과 기대 범위로 나누어 사용한다. `model_call`로 선정·작성·검토를 지정하고, 검토 대상 선정·초안은 `initial.results`에 미리 제공한다. 새로 받은 작성 결과로 검토 입력을 만들거나 후속 검토를 자동 실행하지 않는다. 단독 호출의 `call_index`는 1이며, 과거 전체 실행 기록을 채점할 때는 그 기록의 원래 호출 번호를 유지한다. 지정 방법은 [평가 자료 준비](../../README.md#평가-자료-준비)를 따른다.

## 3. 전체 경로 목록

각 경로의 목적은 **어떤 요청과 자료 조건에서, 어떤 판단과 결과를 확인하는가**로 읽는다. 아래 표는 현재 입력·발생 상황과 기대 동작을 나눠 설명한다. [경로 파일](scenarios.json)의 `title`은 짧은 이름이며, 같은 식별자의 아래 설명에서 구체적인 조건과 목적을 확인할 수 있다.

종료 상태는 고정 응답으로 구성한 경로의 결과다. 요청한 범위를 제공하면 완료(`completed`), 일부 결과만 제공하면 부분 완료(`partial`), 제공할 결과가 없으면 실패(`failed`), 필요한 정보를 사용자에게 물으면 답변 대기(`waiting_input`)로 표시한다. 실패 경로도 조회 오류나 근거 부족을 정확히 알리는 것이 기대 동작일 수 있다. 이 상태는 평가의 통과·실패 판정과 다르다. 노드 수는 공유 사례도 해당 경로에 나타날 때마다 센 값이다.

### 사용자 요청

U1~U7은 현재 사용자 발화가 이전 대화와 어떻게 이어지는지를 구분한다. ‘충분한 답변’과 ‘불충분한 답변’은 사용자의 설명 수준이 아니라, 원래 작업에 필요한 지역·기간 등의 정보가 모두 확보됐는지를 뜻한다.

U5·U6은 보완 답변을 받은 시점부터 평가한다. 이전 요청·AI 질문·현재 답변을 포함하되 새 실행과 예산으로 시작하며, 이전 실행의 내부 도구 결과나 응답 상태를 복원하지 않는다. 답변 대기는 이번 요청의 종료이고 이후 답변은 별도 요청이다.

지도 대안 사례의 허용 뷰는 상세 지도 `EmbedDetailMap`과 격자 분포 뷰 `EmbedDetailV08`이다. 기록된 기준 경로는 상세 지도를 사용한다. 두 뷰를 모두 실행한 경로라는 뜻은 아니며, 노드 평가 기준에서 같은 표현 목적을 충족하는 대안을 허용한다. 차트 설정을 반환하는 사례의 완료는 등록 조건에 맞는 설정을 구성했다는 뜻이며, 실제 화면 표시 성공을 뜻하지 않는다.

기존 차트 사례는 차트와 표시 조건을 입력에 직접 제공한다. 현행 API의 화면 문맥은 동·월이며, 선택 차트의 전달·보관 계약은 [컨텍스트의 남은 결정](../../../docs/agent/context.md#3-현재-구성과-남은-결정)에 해당한다. 하위 실행에 제공하는 정보는 [하위 에이전트 전달](../../../docs/runtime/prompts.md#5-이력-가공과-하위-에이전트-전달)을 따른다.

### 보고서 생성

8개 경로는 도곡1동의 2025년 12월 보고서를 대상으로 한다. **뷰**는 보고서에 넣을 등록 시각화이며, 기본 경로는 월별 행동 이상 점수 추세(V01), 행동 지표별 점수 기여도(V02), 격자별 행동 이상 점수 분포(V08)를 사용한다. **선정**은 사용할 뷰·이유·근거·설명 범위를 정하는 단계, **설명**은 선정한 뷰별 해설을 쓰는 단계, **퀵 인사이트**는 검토를 통과한 설명의 핵심을 3~4문장으로 요약하는 단계다. 각 역할의 책임은 [보고서 생성 명세](../../../docs/agent/report.md#3-행정동별-생성-흐름)를 따른다.

추세 표시 범위는 요청 월을 포함한 최근 6개월인 7~12월이고, 스냅샷에는 8~12월 자료만 있다. 따라서 ‘보고서 완성’은 제공된 자료로 설명 범위를 정해 뷰·설명·인사이트를 완성했다는 뜻이다. 누락된 7월이나 도시 중앙 50% 범위와의 비교까지 제공한다는 뜻은 아니다.

각 경로는 세 역할을 거쳐 최종 보고서 산출물을 구성하는 지점까지 포함한다. 실제 DB 저장·완료 알림·Tableau 화면 표시는 포함하지 않는다. 수정은 결함이 발생한 역할에서 진행하고, 후속 역할은 검토를 통과한 앞 단계의 범위를 유지한다.

| 표현 | 의미 | 이 데이터셋의 구체적인 경우 |
| --- | --- | --- |

보고서의 **근거 자료 조건**은 무엇을 확인·설명할 수 있는지를, **앞 단계 산출물의 상태**는 이번 역할에 어떤 검토 결과와 설명 범위가 전달됐는지를 나타낸다. 두 분류는 서로 독립적이다. 부분 그룹의 `axes`에는 다음 축을 구분해 기록한다.

| 분류 | 축 | 구분하는 내용 |
| --- | --- | --- |
| 근거 자료 | 필요한 자료의 제공 범위 | 요청에 필요한 지역·기간·지표의 자료가 모두 있는지, 일부만 있는지, 전혀 없는지 구분한다. |
| 근거 자료 | 비교 조건의 일치 여부 | 지역·기간·단위 등이 맞아 그대로 비교할 수 있는지, 허용된 변환 후 가능한지, 비교할 수 없는지 구분한다. |
| 근거 자료 | 부족한 정보를 보완할 경로 | 이미 가진 자료를 가공할지, 추가 조회할지, 허용된 보완 경로가 없는지 구분한다. |
| 근거 자료 | 자료에서 관측된 패턴 | 비교한 값이 증가·감소·유지되는지, 지표마다 방향이 다른지 구분한다. 점수의 방향을 실제 활동량의 방향으로 바꾸어 해석하지 않는다. |
| 앞 단계 산출물 | 전달된 항목 수 | 설명 역할에는 선정 뷰가, 인사이트 역할에는 작성된 설명이 몇 개 전달됐는지 구분한다. |
| 앞 단계 산출물 | 항목별 검토 상태 | 전달된 각 항목이 미검토인지, 적합 판정을 받았는지, 부적합 판정을 받았는지 구분한다. 항목 수와 별개다. |
| 앞 단계 산출물 | 확정된 설명 범위 | 앞 단계에서 정한 대상·기간·허용 비교와 제외할 비교를 확인한다. 예를 들어 월별 변화는 허용하고 도시 분포와의 비교는 제외한다. |
| 앞 단계 산출물 | 전달된 내용의 구성 | 서로 다른 핵심 관측이 있는지, 같은 관측이 반복되는지, 필요한 핵심 내용이 빠졌는지 구분한다. |

선정 역할에는 앞 단계 산출물의 네 축을 적용하지 않는다. 설명은 승인된 선정 범위를, 인사이트는 승인된 설명을 사용한다. 예를 들어 승인된 뷰가 두 개라는 조건만으로 근거 충분성이나 요약 가능성을 정하지 않는다.

전체 보고서 경로의 `axes`는 선정 뷰 수와 현재 사건 등을 요약한다. 역할별 실제 자료·승인 범위는 단계의 `before_state`에서, 현재 초안의 검토·보완 사건은 `events`와 전후 상태에서 확인한다. 분류 정보가 실행 상태를 대신하지 않으며, 앞 단계의 검토 상태와 현재 역할에서 발생한 검토 결과도 구분한다.

### 부분 사례와 변형

81개 부분 그룹은 필수 정보 누락, 자료 일부 제공, 비교 조건 불일치, 실패·취소·거절 이력, 미승인 산출물, 무관한 자료와 자료 속 지시 등의 조건을 추가로 확인한다. 시작부터 재현한 경로로 확대 해석하지 않는다.

실제 지역·기간·지표를 선택해 증가·감소·유지·방향 상이 조건을 구성하고, 대화·자료 제공 범위·호출 결과·검토 상태를 바꿔 판단 차이를 확인한다. 원자료 수치를 임의로 만들지 않으며 의도적으로 만든 실패나 초안 결함은 변형 내역에 기록한다. 역할별로 가능한 조합을 골랐으며, 모든 조건의 조합이나 표현·제시 순서만 바꾼 전용 변형을 생성한 것은 아니다.

## 4. 근거 자료

[조회 스냅샷](snapshots/data.json)은 2026-11-11에 설정된 서비스 DB `eumi`에서 읽기 전용으로 확보했다. 별도 합성 평가 DB `eumi_eval`의 자료와 구분한다. 공통 조회 기간은 2025년 8~12월이며, 사례 생성과 실행에서는 이 스냅샷을 고정 자료로 사용한다.

| 자료원 | 내용 | 확보 지역 수 | 행 수 |
| --- | --- | ---: | ---: |
| `public.region_result` | 월별 분석 점수 | 47 | 235 |
| `analysis.bh_region_contribution` | 행동 지표별 점수 기여도 | 47 | 2,820 |
| `analysis.bh_grid_anomaly` | 격자별 행동 이상 점수 | 4 | 12,892 |
| `analysis.flow_detail` | 활동 상세값 | 0 | 0 |

지역 수는 자료에 포함된 읍면동 수다. 격자 자료는 선택한 4개 지역에 한정했고, 나머지 자료는 지역을 제한하지 않았다. 대표 비교는 도곡1동의 2025년 11월 47.82점과 12월 53.06점, 차이 5.24점이다.

[원본 조회 결과](snapshots/raw-query-results.json)는 소수를 정확한 문자열로 보존한다. 조회문·조건·수집 시각·수치 변환·출처·버전·해시는 스냅샷에 기록했다. [수집 스크립트](capture_snapshot.py)로 다시 수집할 때는 새 출력 경로를 지정한다. 사례 재생성은 DB를 다시 읽거나 쓰지 않는다.

날짜 변형은 부분 그룹 2개의 노드 사례 4개에 적용했다. 실제 수치는 유지하고 2025년 8~12월을 2025년 10월~2026년 2월로 옮겼다. 이동 전 원본과 변형 위치를 연결했으며, 자료는 여전히 5개월이다. 변형된 날짜는 실제 관측 시점과 구분하고, Tableau 등록 범위 밖 기간을 정상 뷰 설정으로 사용하지 않는다.

활동 상세값, 배경 점수의 요인별 기여도, 도시 중앙 50% 범위의 계산 근거는 제공되지 않는다. 해당 근거가 필요한 경우 가능한 설명과 제외할 비교를 구분하도록 평가 기준을 구성했다.

## 5. 평가 문서와의 연결

[coverage.json](coverage.json)은 기존 Markdown의 시험 사례 행과 정형 평가 JSON의 검사 정의를 데이터셋·분기에 연결한 기록이다. 각 원본의 위치·해시와 연결한 사례를 보관한다. 시험 사례 행의 연결과 아래 준비 현황은 평가 문서에서 사례 표를 삭제하기 전 기준이며, 현재 문서의 사례 목록이나 모델의 통과 수를 뜻하지 않는다.

| 연결 대상 | 전체 수 | 연결 수 | 부분 연결 수 | 미연결 수 |
| --- | ---: | ---: | ---: | ---: |
| 시험 사례 표의 행 | 57 | 54 | 2 | 1 |
| 검사 항목 | 30 | 30 | 0 | 0 |
| 별도 분기 목록의 항목 | 50 | 50 | 0 | 0 |

시험 사례 행에 여러 조건이 있으면 일부만 준비된 행은 부분 연결로 표시한다. 분기 목록의 연결은 모든 조건 조합의 포함 여부를 뜻하지 않는다.

| 시험 사례 | 준비 상태 | 남은 조건 | 부족한 자료 |
| --- | --- | --- | --- |
| 응답 작성 사례 02 | 부분 연결 | 점수와 실제 활동이 상반된 방향일 때의 설명 | 실제 활동 상세값 |
| 응답 작성 사례 13 | 미연결 | 네 후보 중 세 뷰를 고르는 복수 허용 조합 | 네 번째 후보를 설명할 근거 |
| 응답 작성 사례 15 | 부분 연결 | 활동 추세 뷰(V07)의 정상 설명과 연도를 넘는 완전한 6개월 비교 | 실제 활동값과 전체 기간 자료 |

수치 서술이 필수인 사례에는 독립 계산값과 수치 추출 규칙을 연결했다. 자유 서술에서 모델이 예정에 없던 수치를 추가하면 비적용 선언과 충돌해 현재 채점기가 해당 조건을 미판정으로 남길 수 있다. 기대 내용·허용 대안·추출 규칙의 사람 검수는 별도로 필요하다.

검사 순서는 [노드 검사의 세 축](../../../docs/eval/nodes/common.md#노드-검사의-세-축), 지표·합격·보류 조건은 [노드 평가](../../../docs/eval/nodes/README.md)를 따른다. 공유 사례의 평가 결과는 고유 `case_id`를 기준으로 집계하고, 경로별 표시는 사용 위치로 연결한다. 동일 결과를 경로마다 독립 평가한 것으로 중복 집계하지 않는다.

## 6. 생성과 실행

명령은 `Eumi/ai`에서 실행한다. [생성기](../../../scripts/build_node_dataset.py)는 고정 스냅샷으로 사례·전체 경로·부분 그룹·공유 색인·범위 추적 파일을 만든다. [입력 검사기](../../../scripts/validate_node_dataset.py)는 입력·평가 기준·경로 연결과 원자료를 대조한다. 두 명령은 DB나 외부 모델에 접속하지 않는다.

```powershell
uv run python -m scripts.build_node_dataset
uv run python -m scripts.validate_node_dataset
uv run python -m evaluation validate evaluation/scenarios/nodes/interpret.json
```

각 노드 파일의 평가 단위는 `unit=node`이며, 공통 자료는 파일의 `datasets`에 보관한다. 모델 호출이 없는 종료 사례는 노드 모델 평가에서 제외하고 실행 평가에서 확인한다. 사례 하나를 세 번 실행하고 채점하는 예는 다음과 같다. 업무 모델과 평가 모델의 연결 설정이 필요하며, 실행 후 생성된 묶음 ID를 채점 명령에 넣는다.

```powershell
uv run python -m evaluation run evaluation/scenarios/nodes/act.json --case path-act-b592d3b3acfe09e173b4 --repeat 3
uv run python -m evaluation score-nodes outputs/evaluations/<묶음-ID> --method all --judge-model <평가 모델 이름>
```

반복 실행·채점 옵션과 결과 확인 방법은 [평가 실행 안내](../../README.md)를 따른다. 전체 경로 기록은 노드 사례의 업무 맥락과 상태 연결을 확인하는 자료이며, 위 명령의 평가 단위는 개별 노드다.

## 7. 검증 상태

2026-11-12의 [입력 검증 결과](validation.json)는 v2의 375개 고유 사례에서 오류 0건이다. 결과에 기록한 파일 해시는 현재 노드 파일·경로·범위 추적 파일·스냅샷과 일치한다.

이 저장 결과는 현재 코드로 대조한 경로와 입력의 검증 기록이다. 원본 응답 한 건에서 멈추는 실행기의 동작 검증은 [평가 실행 안내](../../README.md#구현-검증-범위)를 따르며, 기존 다중 호출 사례를 독립 호출로 나눈 결과의 검증을 대신하지 않는다.

| 확인 내용 | 확인 수 | 단위 |
| --- | ---: | --- |
| 입력 스키마와 평가 대상 | 5 | 노드 파일 |
| 사례·색인의 양방향 연결과 평가 메타데이터의 입력 분리 | 375 | 고유 사례 |
| 전체 경로·부분 그룹의 사례·역할·입력·평가 기준 연결 | 445 | 단계 참조 |
| 전체 경로의 실행 전 상태 복원 | 320 | 노드 등장 |
| 실제 노드의 최초 모델 호출 직전 입력 구성 | 373 | 고유 사례 |
| 모델 호출 없는 단계 종료 | 2 | 고유 사례 |
| 조회 결과와 원자료·출처 대조 | 44 | 조회 기록 |

시작·종료, 하위 호출·반환, 보고서 역할 전환의 상태 연결과 역할·하위 경로 누락도 확인했다. 전체 수량과 평가 문서 연결은 저장된 집계를 다시 계산해 대조했다. 모델 입력 검사는 첫 호출 직전까지 진행하며, 보고서 노드 안의 후속 작성·검토 입력을 모두 독립 재검사한 것은 아니다.

생성·입력 검증·평가 실행기·전체 경로·경계 변조 관련 고유 테스트 116개를 통과했다. 노드 파일 5개와 경로·범위 추적 파일을 다시 생성해 현재 파일과 내용이 같음을 확인했고, 기존 부분 사례 125개의 식별자·입력·평가 기준·의존 설정도 유지했다.

업무 모델의 출력 품질, 평가 모델의 의미 판정, 예정 반복 평가, 기대 결과의 사람 검수는 미실행 상태다. 원자료 수집 과정·최신성, 연산 선택과 직접 작성한 설명의 의미 정확성도 이 입력 검증으로 판정하지 않는다. DB 재접속·HTTP 접수·저장·알림·화면 표시를 포함한 서비스 연동 검증은 별도로 수행한다.

## 8. 구성 방법의 참고자료

외부 자료는 시나리오 구성 방법을 참고하는 데 사용했다. 서비스의 기능·입출력·평가 기준은 현행 프로젝트 명세를 따른다. 참고자료가 이 데이터셋의 정확한 사례 수를 정한 것은 아니다.
