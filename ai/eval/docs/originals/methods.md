# 평가 방법

상태: 검토용 명세. 수정일: 2026-11-12.

내부 평가를 준비하고 결과를 기록·판정하는 공통 지침이다. 이 문서와 평가할 단위의 문서를 함께 사용한다. 실제 검사 항목, 측정 방법, 지표, 합격 기준은 해당 단위 문서를 따른다.

노드 평가기의 프롬프트·판정 로직이 읽는 공통 원칙의 단일 원본은 [노드 공통 정형 평가 정의](nodes/common.json)다. 이 문서는 평가 절차와 원칙의 논리를 설명하며, 노드 평가기는 Markdown 본문을 기준 입력으로 추출하지 않는다.

검사 내용, 판정 수단과 절차, 판정 결과, 결과를 집계하는 지표를 구분한다.

| 구분 | 의미 |
| --- | --- |
| 검사 항목 | 검사 대상과 주제를 요약한 이름 |
| 검사 내용 | 해당 검사가 무엇을 대상으로 어떤 성질·동작을 확인하는지 설명한 내용 |
| 적용 조건 | 해당 검사 전체가 필요한 입력 상황·작업·출력의 조건 |
| 평가 방식 | 검사 결과를 결정하는 수단.<br>종류와 선택 기준은 아래 검사 방식에서 정의한다. |
| 평가 입력 | 판정에 제공하는 실행 당시 입력·검사 대상 결과·별도 평가 자료 |
| 측정 방법 | 상황별로 사용할 평가 입력의 부분·필드를 정하고 확인·대조해 근거를 기록하는 절차 |
| 성공 기준 | 해당 검사를 통과하려면 충족해야 하는 조건 |
| 판정 결과 | 검사 대상이 기준을 통과했는지 실패했는지 확인한 결과.<br>판단할 수 없으면 미판정으로 남긴다. |
| 평가 지표 | 판정 결과를 집계하거나 호출의 기술적 실패·응답시간 등을 측정한 값. |

## 1. 평가 절차

| 순서 | 수행 내용 | 완료 조건 |
| --- | --- | --- |
| 1 | 평가할 단위와 범위를 정한다. | 대상 문서와 필수 사례가 정해짐 |
| 2 | 입력과 기대 결과를 준비한다. | 평가 결과와 독립된 기준 자료가 있음 |
| 3 | 사례를 실행하고 증거를 수집한다. | 검사별 실제 결과를 확인할 수 있음 |
| 4 | 해당 단위의 기준과 평가 방식으로 검사한다. | 검사별 판정과 근거가 기록됨 |
| 5 | 해당 단위의 지표를 집계한다. | 집계값과 제외 사유를 확인할 수 있음 |
| 6 | 문제의 원인을 구분해 보고한다. | 구현 수정과 평가 체계 보완이 구분됨 |

사례별 적용 검사·기대 결과·목표값은 실행 전에 정한다. 해석 허용 범위·수치 오차·표현 조건은 사례 작성 전에 확정한다. 결과를 본 뒤 기준을 완화하지 않는다. 기준이 미확정이면 그 부분을 미판정으로 남긴다.

### 평가 단위와 책임

내부 평가는 도구·노드·에이전트 실행의 세 분류로 구성한다. 노드는 주어진 입력에서 판단·작성·호출·상태 갱신·이력 기록을 수행하며, 에이전트는 노드 사이의 순서·전달·공유 한도와 전체 반환·종료를 맡는다. 에이전트 실행 평가에서는 노드가 맡은 처리의 판정·증거를 연결하고 전체 성능·안정성을 측정한다.

| 단위 | 확인할 내용 | 평가 문서 |
| --- | --- | --- |
| 도구 | 한 호출의 입력 처리·계산·조회·반환 결과 | [도구](tools.md) |
| 노드 | 주어진 입력에 따른 판단·작성·도구와 하위 에이전트 호출, 담당 상태 갱신과 이력 기록 | [노드](nodes/README.md).<br>현재 N 정형 검사는 이 중 모델 출력의 형식·내용을 정의 |
| 에이전트 실행 | 노드 간 순서·입력과 결과 전달·공유 한도, 전체 반환·종료와 시간·호출량·토큰·비용 | [에이전트 실행](execution/README.md).<br>사용자 요청 1회와 한 동·월의 보고서 작성 1회를 구분 |

작업 중 도구로 수행한 DB 조회는 에이전트 실행의 측정 구간에 포함한다. 도구 호출과 반환 처리는 담당 노드, 조회 결과의 정확성은 도구 평가에서 확인한다. 서비스의 요청 접수·입력 준비, 여러 동의 배정·전체 완료 집계, 반환 결과의 DB 저장·알림·화면 표시는 에이전트 실행 평가에서 제외한다. 호출자에게 반환한 뒤 다시 진입하면 별도 실행으로 평가하며, 기존 이력·예산의 보존과 이번 실행의 사용량 집계를 구분한다. 구체적인 측정 경계는 [공통 실행 기준](execution/common.md)을 따른다.

실제 사용자의 근거 탐색·이해와 사용 부담은 내부 평가와 구분한 [서비스 검증](service-validation.md)에서 다룬다. 평가 대상·범위만 정하며 세부 방법과 기준은 미정이다.

### 노드 출력과 에이전트 실행

노드 평가는 주어진 입력에 따른 판단·작성과 노드가 수행한 호출·상태 갱신·이력 기록을 담당한다. 에이전트 실행 평가는 노드에 올바른 입력을 전달하고, 노드가 반환한 상태·결과를 다음 단계와 전체 반환·종료에 연결했는지 확인한다. 현재 N 정형 검사는 노드 책임 중 모델 출력의 형식·내용을 다루며, 내부 실행 검사의 정의와 자동 판정은 별도 정비가 필요하다.

이 구분은 코드 파일이나 함수의 위치가 아니라 처리 경계를 기준으로 한다. 노드가 공통 실행 함수를 사용해 수행한 호출·담당 상태 갱신·이력 기록도 해당 노드의 책임이다. [노드별 쓰기 범위](../agent/state.md#2-노드별-쓰기-범위)는 이 책임의 논리적 범위를 정하며, 모델이 그 필드 전체를 직접 반환해야 한다는 뜻은 아니다.

| 상황 | 노드 평가 | 에이전트 실행 평가 |
| --- | --- | --- |
| 노드가 잘못된 지역을 호출 인자로 선택하고 그대로 실행함 | 선택한 값이 요청과 다르면 실패 | 해당 노드의 입력 전달·실행 순서와 전체 반환만 별도 확인 |
| 노드가 올바른 호출 인자를 선택했으나 내부 호출 과정에서 값이 바뀜 | 선택 판정과 구분해 실제 호출 처리는 실패 | 해당 호출 처리를 에이전트 검사로 다시 판정하지 않음 |
| 노드가 응답을 담당 상태에 누락한 채 반환함 | 작성 내용과 구분해 상태 갱신은 실패 | 받은 상태의 단계 간 전달을 별도 확인하며 누락을 재판정하지 않음 |
| 노드는 올바른 상태·다음 단계를 반환했으나 다음 노드의 입력이나 실행 순서가 달라짐 | 노드가 반환할 때까지의 해당 처리는 통과 | 노드 간 전달·전이는 실패 |

호출·상태 갱신이나 노드 간 전이·공유 한도를 코드가 처리한다고 해서 모델의 필수 출력에 추가하지 않는다. 모델 출력의 적절성, 노드 내부 처리, 에이전트의 단계 연결은 각각 담당 범위의 증거로 확인한다. 현재 N 검사 통과만으로 노드 내부 실행 검증을 완료했다고 표시하지 않는다.

## 2. 사례 기록

사례마다 실행 전에 다음 내용을 기록한다. 실행 결과는 사례 ID로 연결한다.

| 기록 항목 | 기록할 내용 |
| --- | --- |
| 사례 ID | 사례를 구분하는 식별자 |
| 평가 단위 | 도구·노드·에이전트 실행 중 해당 분류와 평가할 호출·역할·실행 흐름 |
| 평가 목적 | 확인하려는 요구사항 |
| 입력 | 평가 대상 실행에 제공할 요청·상태·자료.<br>평가용 기준과 구분한다. |
| 기준 자료 | 정답이나 기대 행동을 판단할 독립 자료 |
| 기대 결과 | 입력 조건에서 나와야 할 결과 |
| 허용 범위 | 인정할 대안이나 오차 |
| 적용 검사 | 수행할 검사 ID |
| 평가 방식·채점 기준 | 검사별 규칙 또는 LLM의 판정 방법, 의미 일치·허용 표현·실패 조건 |
| 필수 여부 | 합격 판정에 포함할 사례인지 여부 |
| 시험 조건 | 결과 비교에 필요한 실행 조건 |

정상 사례와 예외 사례를 구분한다. 결함을 넣는 시험은 결함 위치와 기대 탐지 결과를 기록한다. 모의 자료를 사용하면 실제 연동까지 확인한 것으로 확대하지 않는다.

- 반복이 필요한 사례는 같은 입력·자료·지침·권한·모델·환경과 반복 횟수를 시험 전에 정한다.
- 운영 판정에 필요한 대상 지표·평가 대상·대표 입력 규모·반복 횟수·모델·실행 환경·판정 통계값과 목표값을 시험 전에 확정한다.

### 검사 입력

검사 입력은 자료의 출처와 용도에 따라 구분한다. 각 검사의 `평가 입력` 열은 아래 목록에 따라 `- 분류명: 입력 명칭, 입력 명칭` 형식으로 분류별로 줄을 나눈다. 실행 당시 입력·검사 대상 결과·별도 평가 자료 순서로 적고, 입력이 없는 분류는 생략한다. 측정 방법에는 실제로 사용할 부분과 대조 절차를 쓴다. 해당 검사의 측정 방법과 성공 기준은 모든 판정에 함께 제공한다.

| 구분 | 용도 |
| --- | --- |
| 실행 당시 입력 | 평가 대상이 실행 시점에 받은 프롬프트 구성요소·자료·상태 |
| 검사 대상 결과 | 해당 실행이 실제로 반환하거나 기록한 내용 |
| 별도 평가 자료 | 평가용으로 준비한 독립 기준과 연결해서 사용할 다른 검사 기록 |

#### 입력 선정 원칙

- 업무 모델에 제공한 지침 본문은 **시스템 프롬프트**, 작업 자료 본문은 **사용자 프롬프트**로 부른다. 전송 형식인 `system`·`user` 메시지와 구분하고, 구성요소는 실제 제목과 필드명에 맞춰 지칭한다.
- 프롬프트 전체를 기본 입력으로 넣지 않는다. 각 검사에 필요한 구성요소를 선택하고, 그 안에서도 판정에 필요한 조항·필드·기록을 원문으로 추출한다. 원본 위치·버전과 추출 범위를 남긴다.
- 자료를 줄여도 검사 대상인 모든 목표·조건·주장과 그에 대응하는 증거는 보존한다. 성공 기록만 고르거나 출력이 참조한 근거만 남겨 누락·근거 없는 추가·실패·수정 이력을 숨기지 않는다. 판정에 필요한 문맥이 부족하면 해당 원문 범위를 확장한다.
- 같은 내용이 모델 반환값·작업 이력·공개 응답에 반복되면 한 번만 제공하고 다른 위치를 연결한다. 반영·보존을 대조하는 검사에서는 비교할 양쪽 값을 유지한다.
- 기대 결과만으로 대조할 수 있으면 이를 만드는 데 사용한 프롬프트·명세를 다시 제공하지 않는다. 별도 평가 자료도 해당 검사에 필요한 항목·조항만 제공한다. 적용 조건이 없는 자료는 생략하고, 필요한 증거를 확보하지 못한 경우와 구분한다.
- 규칙 기반 검사는 필요한 값을 코드로 직접 대조한다. 보존 대상 전체를 검사해야 하면 범위를 줄이지 않고 구조 비교를 수행하며, 이를 LLM 입력으로 전환하지 않는다. 원본 보관 범위와 평가용 LLM에 제공하는 범위는 구분한다.

#### 실행 당시 입력

프롬프트 구성은 [모델 입력 구성](../runtime/prompts.md)과 [조립 코드](../../src/prompting.py), 상태 필드는 [실행 상태](../agent/state.md)를 따른다. 아래 명칭은 기존 자료의 부분을 가리키며 새 업무 필드를 만들지 않는다.

| 입력 명칭           | 원본 위치                                                    | 제공 범위                                                                                      |
| --------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 공통 원칙           | 시스템 프롬프트의 `[공통 원칙]`                                      | 해당 검사의 행동 제한·해석 원칙에 필요한 조항                                                                 |
| 현재 Agent 역할     | 시스템 프롬프트의 `[현재 Agent 역할]`                                | 현재 역할의 담당 작업·위임 범위·완료 조건 중 검사할 내용                                                          |
| 이번 노드의 작업 지침    | 시스템 프롬프트의 `[이번 노드의 작업 지침]`                               | 해당 검사에 적용되는 조항.<br>추가된 시각화 지침도 필요한 부분만 포함                                                     |
| 현재 작업 목표        | 사용자 프롬프트의 `[현재 작업 목표]`                                   | 실제 제공된 `request.goal`.<br>목표 누락을 검사할 때는 모든 목표를 보존                                             |
| 작업 조건           | 사용자 프롬프트의 `[필수 조건]`·`[선호 조건]`·`[제외 조건]`                  | 해당 판단에 적용되는 조건과 조건의 종류.<br>조건 누락 검사는 전체 적용 조건 포함                                              |

| 기존 공개 응답        | 사용자 프롬프트의 `[기존 공개 응답]`                                   | 현재 요청이 가리키는 기존 설명·질문·후속 작업 문장                                                              |
| 기존 공개 산출물       | 사용자 프롬프트의 `[기존 공개 산출물]`                                  | 요청 대상 식별·선택·보존·변경 대조에 필요한 산출물의 참조·설정·내용                                                    |
| 입력 작업 이력        | 사용자 프롬프트의 `[작업·판단 이력]` 또는 `[작업 결과와 검증 이력]`               | 관련 기록의 `id`·`node`·`decision`·`reason`·`action`·`outcome`.<br>자료 본문은 제외하고 연결된 실패·검증·수정 기록은 보존 |
| 입력 자료 내용        | 실제 프롬프트에 포함된 작업 결과의 `output`                             | 검사할 주장·판단과 관련된 자료 행·본문·하위 설명.<br>메타데이터만으로 판단할 수 없을 때 사용                                       |
| 입력 자료 정보        | 실제 프롬프트에 포함된 작업 결과와 검증 기록                                | 결과 ID·대상·기간·열·단위·출처·버전·행 수·성공 여부·검증 판정 중 필요한 값.<br>자료 행·긴 설명 본문은 제외                           |

| 조회 가능한 자료 목록    | 실제 프롬프트의 `[조회 가능한 자료 목록]`                                | 요청 처리에 필요한 자료의 제공 범위·열·조회 조건.<br>선택한 자료 외에 필요한 후보도 보존                                         |
| 가공 가능한 결과 ID와 열 | 사용자 프롬프트의 `[가공 가능한 결과 ID와 열]`                            | 가공 인자에서 참조할 수 있는 결과 ID와 열                                                                  |
| 시각화 목록과 입력 조건   | 실제 프롬프트의 `[시각화 목록과 입력 조건]`·`[시각화 선택 목록]`·`[상세 뷰의 표현 범위]` | 해당 호출에 제공된 뷰의 이름·목적·자료·표현 범위와 필요한 입력 조건.<br>뷰 선택에 필요한 대안 후보도 보존                               |
| 도구 기능 설명        | 해당 호출에 바인딩한 도구·에이전트 명세                                   | 제공한 후보의 이름·기능 설명.<br>인자 스키마는 제외                                                               |
| 도구 입력 명세        | 해당 호출에 바인딩한 도구·에이전트 명세                                   | 선택한 대상의 인자 구조·제약과 검사할 필드의 설명                                                               |
| 사용·공개 조건        | 실제 제공한 프롬프트 또는 적용 설정의 해당 조항                              | 자료·호출 대상의 사용 권한과 사용자별 공개 조건 중 해당 검사에 필요한 내용.<br>없는 조건을 새로 만들지 않음                              |
| 에이전트 입력         | 역할을 시작할 때 받은 요청·상위 호출 인자와 초기 `State`                     | 원래 목적·조건·대화·화면 문맥·시작 이벤트 중 검사할 부분.<br>내부에서 다시 정리한 목표로 원래 요청을 대체하지 않음                          |
| 실행 전 상태         | 평가 대상 노드·에이전트·흐름의 진입 시점 `State`                          | 측정 방법에서 지정한 원본 필드·기록.<br>상태 보존 검사는 보존 대상 전체를 코드로 대조                                           |

모델에 제공되지 않은 정보를 알고 있었다고 가정하지 않는다. 필요한 정보가 누락된 경우 입력 구성 문제와 판단 오류를 구분한다. 미완료 목표·미확보 정보를 평가자가 요약한 목록으로 실제 요청·이력을 대체하지 않으며, 사전에 검토한 기대 내용은 별도 평가 자료로 관리한다.

#### 검사 대상 결과

| 입력 명칭 | 원본 위치 | 제공 범위 |
| --- | --- | --- |
| 모델 반환값 | 해당 모델 호출의 구조화된 반환값과 형식 검사에 필요한 원본 응답 본문 | 측정 방법에서 지정한 필드.<br>형식 오류가 발생하면 확보한 원본 본문과 해당 오류를 함께 제공.<br>토큰 사용량·동일 내용의 작업 이력 사본은 제외 |
| 호출 내역 | 평가 대상과 연관 호출의 추적 기록 | 검사할 호출의 이름·인자·역할·순서·종료 상태·오류·연결 ID.<br>반환 본문은 제외하며 횟수 검사는 해당 경계의 모든 호출 포함 |
| 호출 반환값 | 호출 추적 또는 기존 `results[].output`의 실제 도구·하위 반환값 | 검사할 결과·판정·출처·버전·하위 응답의 해당 부분.<br>원본 호출과 연결 |
| 모델 호출 입력 | 실제 모델 호출에 전송한 프롬프트·도구 바인딩·응답 명세 | 입력 조립·전달을 검사할 필드·조항과 호출별 모델·역할·버전.<br>전체 본문을 기본 제공하지 않음 |
| 신규 작업 이력 | 실행 전후 `results`를 대조해 식별한 평가 대상 노드·에이전트 실행의 기록 | 실제 추가·완성된 기록 중 검사할 필드.<br>기존 이력의 보존 여부는 별도 상태 검사에서 확인 |
| 실행 후 상태 | 평가 대상 노드·에이전트·흐름의 반환·오류 종료 시 확보한 `State` | 실행 전 상태와 대조할 동일 필드·기록.<br>전체 상태를 LLM에 제공하지 않음 |
| 공개 응답 | 각 공개 시점과 최종 반환의 `response.kind`·`content` | 검사할 진행 안내·최종 응답·질문.<br>시점·버전을 보존하며 산출물은 별도 입력으로 지정 |

| 작성 내용 | 모델 반환값의 작성 문장·근거 요약 또는 공개 응답·산출물의 내용 | 해당 평가 단위에서 정한 출력·공개·반환 시점의 내용을 사용.<br>책임 범위의 문장·수치·출처·해석·전달 내용을 보존하며 같은 내용의 사본은 한 번만 제공 |

자료는 같은 실행·노드·호출로 연결하고 원본 위치를 보존한다. 후속 참조는 실제 기록이 확보된 범위에서만 판정한다. 저장 위치와 현재 수집 범위는 [단위 평가 실행기](../runtime/evaluation-runner.md)를 따른다.

#### 별도 평가 자료

| 입력 명칭 | 내용과 제공 범위 |
| --- | --- |
| 동작 명세 | 현행 기능·실행 흐름·상태·도구 계약 중 해당 검사의 출력 형식·쓰기 범위·필수 호출·기록·처리 조건에 해당하는 조항과 버전 |
| 기준 자료 | 독립적으로 확보한 원자료·계산값·출처·지표 정의·관측 범위·확인 상태 중 검사할 부분과 그 출처·버전 |
| 기대 결과 | 사례 실행 전에 검토한 기대 내용·행동과 적용 조건.<br>해당 검사의 목표·조건·진행 방향·부족 정보·필수 응답·질문 대상 등 필요한 항목만 제공 |
| 허용 범위 | 해당 검사에 적용할 수치 오차·해석 범위·동일 의미의 표현·대안 선택 조건 |
| 결함 주입 내역 | 해당 사례에 삽입한 지시·누락·장애의 내용·위치·발생 조건.<br>실제 제공·발생 여부는 실행 증거로 확인 |
| 관련 검사 결과 | 같은 실행에서 참조할 검사 ID의 판정·세부 확인 내용·증거 위치.<br>참조할 담당 조건은 측정 방법에 명시 |

기대 결과는 실행 당시 입력과 동작 명세를 근거로 사전에 검토한다. 그 기준을 평가 대상의 결과에 맞춰 바꾸지 않는다. 결함 주입 내역은 시험 설정이고 관련 검사 결과는 평가 후 생성되는 기록이므로 독립 정답으로 취급하지 않는다. 별도 평가 자료는 업무 모델의 입력이나 업무 상태에 추가하지 않는다.

추가 입력 명칭이 필요하면 먼저 이 목록에 정의한 뒤 검사 표에서 사용한다.

## 3. 실행 결과 기록

실행마다 코드·자료·모델·설정·평가 기준의 버전을 남긴다. 같은 사례를 반복해도 실행 ID로 구분하고, 해당 평가 단위가 정한 기준으로 검사 결과를 기록한다. 세부 조건·항목은 각각 확인해 충족 여부·오류·미확인 사항과 원인을 판정 근거에 남긴다. 예상 밖 실행 실패도 기록한다.

| 기록 항목 | 기록할 내용 |
| --- | --- |
| 실행 ID | 이번 실행을 구분하는 식별자 |
| 사례 ID | 실행한 사례 |
| 검사 ID | 적용한 검사 |
| 평가 방식 | 규칙 기반, LLM 기반 중 해당 검사에 지정한 방식 |
| 평가자 정보 | 판정 코드 또는 평가 모델·설정·판정 지침의 버전 |
| 판정 대상 | 검사한 실행·응답·주장·필드·산출물의 식별자 |
| 검사 실행 여부 | 실행 또는 미실행 |
| 실제 결과 | 관측한 값이나 행동 |
| 증거 위치 | 사용한 평가 입력의 원본 위치·버전·추출 범위와 조건부 제공·생략 사유 |
| 판정 | 통과·실패·미판정·비적용 |
| 판정 근거 | 기대 결과와 실제 결과를 대조한 설명.<br>세부 조건별 충족 여부·오류·미확인 사항과 증거 위치 |
| 원인 | 확인된 실패 원인 또는 원인 미확정 |

검사 ID는 평가 단위와 함께 기록한다. 다른 검사의 판정을 참조할 때는 [검사 범위와 판정 연결](#검사-범위와-판정-연결)에 따라 원래 판정·증거와 연결한다.

## 4. 판정 원칙

| 판정 | 의미 |
| --- | --- |
| 통과 | 적용 기준을 충족한 증거가 있음 |
| 실패 | 적용 기준을 위반한 증거가 있음 |
| 미판정 | 기준이나 증거가 부족해 판단할 수 없음 |
| 비적용 | 해당 사례에서 검사할 책임이나 조건이 아님 |

검사 적용 여부는 입력 상황·담당 책임과 검사 표의 적용 조건으로 정한다. `항상`은 지정된 평가 대상의 모든 실행에 적용한다는 뜻이다. 필수 내용·수행의 누락은 비적용 사유가 아니며, 실제로 추가된 동작·출력도 해당 조건에 따라 검사한다. 호출 실패나 증거 부족으로 판정할 수 없는 경우는 미판정으로 구분한다.

미실행은 판정과 별도로 기록하며 비적용으로 바꾸지 않는다. 미실행·미판정을 통과로 간주하지 않는다. 수행 기록이 없으면 수행 검사를 통과시키지 않는다.

사전에 허용한 표현·대안 뷰 등은 동일 정답으로 인정한다.

검사별 판정과 평가 단위의 종합 판정을 구분한다. 종합 판정은 해당 단위 문서의 필수 검사·지표·합격 기준을 따르며, 평가 범위별 결과를 구분해 보고한다.

판정 결과와 검증 완료 여부를 구분한다. 해당 단위 문서에서 정한 중단 조건에 따른 생략을 제외하고, 실패가 확인돼도 아직 확인하지 못한 필수 조건은 근거에 남기고 검증 미완료로 관리한다.

검사를 수행했는지와 결과가 정확한지는 구분한다. 올바른 거부·질문·부분 반환은 기대 행동을 충족할 수 있지만 업무 완료와 같지는 않다. 최종 결과에서 수정해도 앞서 제공한 오류를 통과로 바꾸지 않는다.

다른 단위의 성공으로 평가를 대신하지 않는다. 기록으로 원인을 확인할 수 없으면 추측하지 않는다. 과거 실행을 현재 기준으로 검토한 결과는 당시 기준에 따른 평가와 구분한다.

### 검사 범위와 판정 연결

사례의 각 대상·조건에는 담당 검사를 하나 정한다. 다른 검사에서 같은 조건을 확인해야 하면 원래 판정·증거를 참조하며, 참조한 조건을 자기 검사의 별도 통과·실패로 다시 판정하지 않는다. 각 검사에는 직접 담당하는 조건의 결과만 반영한다.

| 검사 대상 | 담당 범위 |
| --- | --- |
| 판단·선택과 그 이유 | 해당 판단·선택의 전용 검사에서 요청·자료·작업 상태에 맞는지 확인한다. |
| 직접 작성·추가한 설명 | 내용 검사에서 수치·주장·범위·확인 수준·한계·출처 등 담당 조건을 확인한다. |
| 하위 결과의 전달·통합 | 전달 검사에서 하위 반환값과 대조해 누락·왜곡을 확인한다.<br>하위 결과 자체의 정확성은 반환 주체의 검사에서 확인한다. |
| 상태 반영·이력 기록 | 노드 내부의 담당 상태 갱신·이력 기록은 노드 평가에서 확인한다.<br>노드가 반환한 상태·이력을 다음 단계로 보존·전달하는 동작은 에이전트 실행 평가에서 확인한다. |
| 검토 판단 | 검토 대상의 실제 결함과 검토자가 반환한 판정·수정 사유를 대조한다.<br>검토 대상 자체의 품질과 검토 판단의 정확성을 구분한다. |

한 응답에 직접 작성한 내용과 하위 결과를 전달한 내용이 섞이면 부분별로 담당 검사를 연결한다. 판단 이유가 공개 설명에도 반복되면 같은 내용·기준의 판정은 재사용하고, 전달 중 달라진 부분은 다시 대조한다. 누락된 필수 내용도 담당 검사의 대상에 포함한다.

같은 실행·버전·대상·조건에 대한 동일 판정은 한 지표 안에서 한 번만 집계하며, 여러 지표에서 함께 사용할 수 있다. 하나의 원인으로 서로 다른 대상·조건의 위반이 발생하면 각각의 증거로 판정한다. 한 검사가 실패했다는 이유만으로 다른 검사도 실패시키지 않는다.

수정본은 원래 결함을 담당한 검사의 기준으로 평가하고 이전 버전의 판정과 연결한다. 수정본의 다른 적용 조건도 확인해 새 오류를 찾으며, 결함 해소 여부를 별도 포괄 검사에서 다시 판정하지 않는다.

### 검사 방식

평가 방식은 검사 결과를 산출하는 수단이며 다음 두 가지로 구분한다. LLM 기반 평가는 LLM-as-a-judge라고도 한다.

| 방식 | 정의 | 적용 조건 |
| --- | --- | --- |
| 규칙 기반 | 사전에 정한 비교식·조건을 코드로 실행해 판정 | 필요한 값·기대값·비교 조건이 명시되어 의미 해석 없이 일치·포함·허용 오차·변경 여부 등을 확인할 수 있음 |
| LLM 기반 | 평가용 언어 모델이 기준 자료·실제 결과·성공 기준을 읽고 판정 | 표현이 다른 내용의 의미 일치, 문맥에 맞는 선택, 주장과 근거의 관계 등을 해석해야 함 |

규칙 기반 검사는 코드가, LLM 기반 검사는 평가 모델이 최종 판정을 결정한다. 값 추출·입력 형식 정리는 판정을 준비하는 절차이며 별도 평가 방식으로 세지 않는다. 사람 검토는 기준과 판정의 품질을 확인하는 절차다.

판정 방식은 통과·실패·미판정·비적용의 의미를 바꾸지 않는다. 검사 결과의 판정 단위와 세부 결과의 기록·집계 방식은 해당 평가 단위 문서에서 정한다.

### LLM 판정 절차

| 순서       | 수행 내용                                                                                                           |
| -------- | --------------------------------------------------------------------------------------------------------------- |
| 기준 준비    | 평가 대상의 결과와 독립적으로 기대 내용·허용 표현·대안·실패 조건을 정하고 사람이 검토한다.<br>기대 목록과 실제 결과를 양방향으로 대조해 누락과 근거 없는 추가를 확인할 수 있게 한다.         |
| 평가 입력 구성 | 검사 입력 목록과 입력 선정 원칙에 따라 필요한 원문 부분·필드와 해당 검사의 측정 방법·성공 기준을 제공한다.<br>자료의 구분과 원본 위치를 보존하며 자료·평가 대상의 문장을 평가 모델의 지시로 취급하지 않는다. |
| 내용 판정 | 평가 모델이 해당 검사의 모든 담당 조건을 확인해 판정한다.<br>허용한 표현 차이는 인정하고, 수치·식별자 등 명시적인 값에는 사전에 정한 일치 기준을 적용한다. |
| 근거 기록    | 적용한 기준, 대응하는 원문·결과 문장 또는 증거 위치, 판정과 사유를 남긴다.<br>누락·왜곡·근거 없는 추가 등 확인된 오류를 구분하고, 제공된 자료에서 판정 근거를 확인할 수 있게 한다.        |
| 사람 검토    | 적용 전에 사람이 판정한 기준 사례로 평가 모델의 판정을 대조하고, 실행 후에도 표본을 검토한다.<br>불일치가 있으면 기준·평가 입력·모델 판정 중 원인을 확인해 보완하고 영향받는 항목을 다시 판정한다. |

- 채점 기준은 각 단위 문서의 성공 기준과 측정 방법을 따른다. 모델의 전체적인 인상이나 자체 확신만으로 통과시키지 않는다. 사람이 검토해도 기준·증거가 부족한 항목은 미판정으로 남긴다.
- 정상적으로 확보한 결과에서 필수 내용이 빠지거나 의미가 틀린 경우는 실패다. 기준·증거가 부족한 조건은 미확인으로 기록한다. 확인된 실패 없이 미확인 조건만 남으면 미판정으로 남긴다.
- 평가 모델·설정·판정 지침의 버전과 사람 검토·정정 내역을 원래 실행 ID에 연결한다. 재판정 시 이전 판정과 근거를 보존한다.
- 평가용 모델은 저장된 실행 증거를 채점할 때 호출한다. 업무 노드의 모델 호출 수·응답시간에 포함하지 않으며, 평가 모델의 호출 실패는 해당 검사의 미판정 사유로 기록한다. 평가 대상 자체의 기술적 실행 실패로 세지 않는다.

자동 채점의 현재 지원 범위는 [단위 평가 실행기의 제약](../runtime/evaluation-runner.md#7-현재-제약과-후속-작업)을 따른다.

### 기술적 실패와 기능 판정

기술적 실행 실패는 예외·통신 장애·실행 한도 초과 등 기술적 문제로 평가 대상의 실행이 실패한 경우다. 종료 상태와 원인으로 구분한다.

- 정상적인 거부·질문·부분 반환과 반환 내용의 기능 오류는 그 이유만으로 기술적 실행 실패로 세지 않는다.
- 하위 호출 실패를 기대한 방식으로 처리하고 정상 반환한 실행은 하위 실패만으로 기술적 실행 실패로 세지 않는다.
- 기술적 실패로 필요한 결과·증거를 확보하지 못한 검사만 미판정으로 남긴다. 오류 처리 적절성처럼 증거로 판단할 수 있는 검사는 통과·실패로 판정한다.
- 기능 판정과 별도로 기술적 실패와 원인을 기록하고, 기술적 실패를 측정하는 지표가 있으면 해당 호출을 반영한다.

## 5. 결과 보고

평가 범위, 사례별 판정, 지표, 미실행·미판정 항목을 보고한다. 합격 여부와 진단용 수치를 구분한다.

### 5.1 지표 집계

기능 정확성과 기술적 실행 안정성·응답시간을 구분해 집계한다. 지표의 종류·계산 방법·집계 시점·합격 기준은 해당 단위 문서를 따른다.

- 검사 항목별 통과율과 사례별 통과율을 함께 쓰는 경우 같은 검사 판정 기록을 사용한다.
- 검사 항목별 통과율은 같은 검사 ID별로 집계하며, 전체 검사 결과를 합친 통과율로 대신하지 않는다. 사례별 통과율은 사례 ID별로 한 번 계산한다.
- 비적용 검사는 사유와 함께 제외한다. 미실행·미판정의 분모 포함 여부는 각 지표의 계산 방법을 따른다.
- 비율 지표는 분자·분모의 실제 건수를 함께 남긴다. 분모가 0이면 산출 불가다.
- 응답시간의 p95는 측정값의 95%가 그 값 이하인 지점이다. 상위 호출에 포함된 하위 호출 시간은 다시 더하지 않는다.
- 미종료 호출은 응답시간 통계와 종료된 호출을 기준으로 하는 지표에서 제외하고 건수·경과 시간을 기록한다.

### 5.2 검증 완료 현황

통과율과 별도로 지정한 전체 필수 사례의 검증 완료 여부를 관리한다. 사례의 완료·통과 조건과 통과율의 분모는 해당 단위 문서를 따른다.

| 기록 항목 | 기록할 내용 |
| --- | --- |
| 전체 필수 사례 수 | 평가 대상으로 지정한 필수 사례 수 |
| 검증 완료 사례 수 | 해당 단위의 기능 판정 완료 조건을 충족한 사례 수.<br>통과·실패 사례 수를 구분한다. |
| 검증 미완료 사례 수 | 해당 단위의 완료 조건을 충족하지 못한 사례 수.<br>미실행·미판정·필수 조건 미확인 등 사례별 사유 |
| 미실행·미판정 검사 수 | 검사 ID별 미실행·미판정 건수와 사유.<br>기술적 실패로 판단할 수 없는 건수를 함께 표시한다. |

검증 완료 사례 수와 미완료 사례 수의 합은 전체 필수 사례 수와 같아야 한다. 통과율만으로 검증 완료 여부를 대신하지 않는다.

### 5.3 개선 사항

| 개선 구분 | 판단 기준 | 보고할 내용 |
| --- | --- | --- |
| 구현 수정 | 확정 기준을 실제 동작이 위반함 | 실패 증거와 수정할 동작 |
| 평가 체계 보완 | 기준·사례·증거가 부족하거나 잘못됨 | 오판 원인과 보완할 평가 기준 |

한 문제에 두 원인이 함께 있으면 각각 기록한다. 실제 기능 실패와 평가 자료 부족을 섞어 보고하지 않는다.
