# 작업 목적 파악

상태: 검토용 명세. 수정일: 2026-11-11.

[노드 평가 개요·지표·합격 판정](README.md) · [공통 평가 기준](common.md)

## 평가 범위

작업 목적 파악 노드(N01)가 요청을 해석해 반환한 목표·조건과 필수 정보 부족 판단을 평가한다.

## 출력 형식

N-F.1은 아래 형식과 [공통 형식 기준](common.md#출력-형식의-공통-기준)을 적용한다.

| 필드 | 자료형 | 필수 여부 | 형식 기준 |
| --- | --- | --- | --- |
| `request` | 객체 | 필수 | 아래 목표·조건 필드로 구성한다. |
| `request.goal` | 문자열 | 필수 | 공백 외 문자가 있어야 한다.<br>파악한 작업 목표를 담는다. |
| `request.constraints` | 객체 | 선택 | 생략하면 조건이 없는 것으로 해석한다. |
| `request.constraints.required` | 문자열 배열 | 선택 | 필수 조건 목록.<br>생략하면 빈 배열이다. |
| `request.constraints.preferred` | 문자열 배열 | 선택 | 선호 조건 목록.<br>생략하면 빈 배열이다. |
| `request.constraints.excluded` | 문자열 배열 | 선택 | 제외 조건 목록.<br>생략하면 빈 배열이다. |
| `reason` | 문자열 | 필수 | 목표·조건을 파악한 이유를 담는다. |
| `needs_input` | 불리언 | 필수 | 사용자 정보가 더 필요하면 `true`, 그렇지 않으면 `false`다. |

조건 필드의 생략이 형식상 허용돼도, 요청에 명시된 조건이 빠지면 N01-O.2에서 실패로 판정한다.
목표·조건 구조의 기준은 [요청과 조건](../../agent/state.md#11-request)이다.

## 시험 사례

| 사례                                                    | 기대 결과                                     | 적용 검사            |
| ----------------------------------------------------- | ----------------------------------------- | ---------------- |
| 사용자가 요청에 대상·목적·조건을 명확하게 작성한 경우                        | 명시된 요구를 빠짐없이 정리하고 의미와 조건의 구분을 보존한다.       | N01-O.2, N01-O.1 |
| 사용자가 “이 지역”처럼 표현하여 함께 전달된 현재 화면 정보로 요청 대상을 확인해야 하는 경우 | 화면에서 확인한 대상을 목표·조건에 정확하게 반영한다.            | N01-O.2, N01-O.1 |
| 사용자가 질문에 답해 지역·기간 등의 필수 정보를 추가로 알려준 경우                | 새 정보와 기존의 유효한 요구를 함께 정리하고 정보 부족 여부를 갱신한다. | N01-O.2, N01-O.1 |
| 사용자가 다른 주제의 새 요청을 한 경우                                | 변경 조건과 새 목표를 반영하고 유효하지 않은 이전 조건을 제외한다.    | N01-O.2, N01-O.1 |
