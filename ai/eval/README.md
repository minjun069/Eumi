# 평가 실행 안내

수정일: 2026-11-14.

평가는 실제 입력과 원본 응답을 저장하는 단계와, 저장된 증거를 검사 기준으로 판정하는 단계로 나눈다. 노드 단독 평가는 서비스와 같은 코드로 모델 입력을 만들고 모델 응답을 한 번 수집한다. 설치·사례 입력·DB 준비·단위별 실행 범위는 [단위 평가 실행기](docs/runner.md), 판정 기준은 [평가 방법](docs/methods.md)을 따른다. 이 문서는 채점 명령의 선택과 노드 채점의 입력·결과를 설명한다. 실행 전체 채점의 입력·집계·저장 계약은 [실행 전체 채점](docs/runner.md#8-실행-전체-채점)에서 관리한다.

실행 입력·결과와 채점 결과는 일반 JSON으로, 시간순 실행 기록은 전체 호출 스냅샷을 담은 JSONL로 저장한다. 채점 결과는 `eval.assessment_store.load_assessment`로 읽는다.

평가 코드·기준·입력·실행 결과는 `Eumi/ai/eval/`에 둔다. 명령은 `Eumi/ai/`에서 `python -m eval`로 실행한다. 처음 실행할 때는 [입력과 실행 설정](docs/runner.md#2-입력-준비), 해당 [시나리오 안내](../docs/README.md#평가), 아래 채점 명령 순서로 확인한다.

| [tools/](tools/) | 도구 채점·지표 |

채점기는 [공통 증거·저장 준비](batch_store.py)로 실행 묶음과 계획을 읽고 결과 저장을 연결한다. [평가 지문](provenance.py)은 실행·채점 코드의 해시를 모으고, 과거 기록의 문서 경로를 현재 기준과 대조한다. 저장한 원문과 해시는 읽기 과정에서 변경하지 않는다.

## 실행기와 명령

| 실행기 | 책임 | 연결 명령 |
| --- | --- | --- |
| 시나리오 실행기 | 도구는 실제 처리, 노드 단독은 모델 입력·원문 수집, 에이전트·생성 흐름은 상태 변경까지 실행하고 저장 | `run` |
| 규칙 평가 실행기 | 저장된 값의 형식·수치·참조와 실행 경계를 기준과 비교 | 도구는 `score`, 노드는 `score-nodes`, 실행 전체는 `score-executions`에서 호출 |
| LLM 평가 실행기 | 정형 평가 정의의 검사 기준과 해당 입력·출력을 별도 평가 모델에 제공하여 의미 판단 | `score-nodes --method all`에서 호출 |
| 최종 출력 품질 평가 | 실제 반환에 채택된 작성 호출을 기존 규칙·LLM 평가기로 평가 | `score-outputs`에서 호출. LLM은 `--method all`로 선택 |

`score`는 세 도구의 저장 결과를 채점한다. `score-nodes`는 규칙 평가와 LLM 평가를 단계별로 조정하고 노드·역할별 결과를 집계한다. `score-executions`는 여섯 역할·동별 보고서의 운영 지표를 집계하고, 사용자 요청 전체·동별 보고서는 실행 연결과 최종 반환도 검사한다. 채점 명령은 업무를 다시 실행하지 않으며, `score`·`score-executions`·`score-nodes --method rules`는 외부 모델도 호출하지 않는다.

노드 채점은 `interpret`, `act`, `decide`, `compose`, `ask`와 여섯 에이전트 역할을 구분한다. 노드 단독 실행은 반환값을 업무 State에 적용하지 않고 도구·하위 에이전트·렌더링을 실행하지 않는다. `agent`·`workflow`는 기존 업무 흐름을 실행하며, 그 기록에서 하위 에이전트를 포함한 노드의 원본 모델 호출을 추출한다. 보고서 작성·검토·재작성은 원문과 원래 호출 순서를 유지하고 같은 부모 노드 아래에서 평가한다. 작업 선택만 실행한 `selection` 결과도 채점하지만 노드별 지표에는 넣지 않는다.

## 실행 전체 채점

독립 에이전트 실행은 `eval/outputs/evaluations/<에이전트명>/<묶음-ID>`에, 보고서 전체 실행은 `eval/outputs/evaluations/<묶음-ID>`에 저장한다. 아래 채점 명령에는 실행 명령이 출력한 묶음 경로를 넣는다. 여러 에이전트를 선택하면 각 역할에 별도 실행·채점 묶음을 만든다.

[기존 21개 시나리오](scenarios/nodes/README.md)는 색인을 직접 전달해 역할 단독 또는 보고서 전체를 실행한다. 입력 파일을 별도로 만들지 않으며 시작 상태·스냅샷을 내부에서 기존 실행기에 연결한다. 선택법·시작점·자동 채점 범위는 [기존 시나리오 직접 실행](docs/runner.md#기존-시나리오-직접-실행)을 따른다.

```powershell
uv run python -m eval run eval/scenarios/nodes/scenarios.json --target request
uv run python -m eval run eval/scenarios/nodes/scenarios.json --unit workflow --target report
uv run python -m eval score-executions <실행묶음경로>
```

[실행 연결 사례](scenarios/execution/README.md)는 사용자 요청, 공유 한도 소진, 한 동의 보고서 작성과 기존 이력으로 재진입하는 네 합성 사례를 제공한다. 실제 업무 실행의 증거를 수집한 뒤 별도로 채점한다.

```powershell
uv run python -m eval validate eval/scenarios/execution/basic.json
uv run python -m eval run eval/scenarios/execution/basic.json --repeat 3
uv run python -m eval score-executions <실행묶음경로>
```

검사 범위는 [공통 실행 평가](docs/execution/common.md)와 [보고서 실행 평가](docs/execution/dashboard-report.md)를 따른다. 명령 옵션, `execution-expectations-v1`, 운영 목표·단가, 결과 파일 없는 실행의 누적 기록 복구, 기능·운영 판정과 버전 대조는 [실행 전체 채점 계약](docs/runner.md#8-실행-전체-채점)을 참조한다. 저장한 `execution-evaluation-v1`은 [에이전트 실행 평가 뷰어](viewers/execution/README.md)에서 연다. 실행 연결 검사·보고서 완성률·운영 통계·반복·재평가를 확인하며, 기능 대상과 역할 단독 운영 진단을 구분한다. 아래 절은 `score-nodes`의 사용법이다.

## 최종 출력 품질

에이전트를 실행한 같은 묶음에서 실제 최종 답변·보고서 산출물의 품질을 별도로 평가한다. 기존 21개 시나리오의 EX 선언을 바꾸거나 입력 파일을 추가하지 않는다.

```powershell
uv run python -m eval score-outputs <실행묶음경로> --method all --judge-model <평가 모델 이름>
uv run python -m eval score-outputs <실행묶음경로> --check N-F.1
```

현재 응답 작성 기준을 재사용하며, 수정 전 초안·검토자 응답은 최종 품질 집계에서 제외한다. 같은 작성 호출의 판정은 반환 항목들이 함께 참조한다. 작성 원문이 없거나 실제 반환과 연결되지 않은 결과, 독립 비교 자료가 없는 규칙은 미판정으로 남긴다. 최종 품질은 [실행 평가 뷰어](viewers/execution/README.md)에서 EX 기능·운영 결과와 구분해 확인한다. 역할별 평가 대상·필터·저장 구조·판정 재사용은 [최종 출력 품질 계약](docs/runner.md#9-최종-출력-품질)을 따른다.

## 실행

명령은 `Eumi/ai`에서 실행한다. 다음 경로는 준비한 입력 파일과 실제 묶음 경로로 바꾼다.

```powershell
uv run python -m eval validate <입력 파일>
uv run python -m eval run <입력 파일> --repeat 3
uv run python -m eval score-nodes eval/outputs/evaluations/<노드명>/<묶음-ID>
uv run python -m eval score-nodes eval/outputs/evaluations/<노드명>/<묶음-ID> --method all --judge-model <평가 모델 이름>
uv run python -m eval score-nodes eval/outputs/evaluations/<노드명>/<묶음-ID> --case <사례-ID> --check N-F.1 --row N-F.1/interpret
```

| 노드 채점 옵션 | 동작 |
| --- | --- |
| `--method rules` | 기본값. 규칙 검사만 실행하며 LLM 검사는 미실행·미판정으로 기록 |
| `--method all` | 규칙 검사와 LLM 검사를 단계 순서에 따라 실행 |
| `--judge-model` | `all`에서 필수인 평가 전용 모델 이름. `rules`에서는 지정 불가 |
| `--case` | 저장된 실행 계획에서 채점할 사례 ID. 여러 번 지정 가능 |
| `--check` | 사례가 선언한 검사 중 채점할 검사 ID. 여러 번 지정 가능 |
| `--row` | 현재 JSON의 상황별 행 ID. 여러 번 지정 가능하며 해당 행이 속한 검사로 범위를 제한 |
| `--env-file` | 평가 모델 연결 설정 파일. 기본값 `.env` |
| `--output` | 기존에 없는 새 채점 JSON 파일 경로. 생략하면 묶음의 `assessments/<실행 이름>_채점NN.json` |

평가 모델은 업무 실행 모델과 별도로 생성한다. `all`도 필요한 기준·증거가 없거나 선행 단계가 통과하지 않으면 해당 평가 모델을 호출하지 않는다. 채점 결과 저장 성공의 종료 코드는 0이며 평가 통과 여부와는 별개다. 입력·계획 오류는 2, 읽기·저장 오류는 1이다. 재채점은 같은 실행 이름에 새 채점 번호를 붙이며 기존 결과를 덮어쓰지 않는다. 실행 이름·번호·한국시간과 채점 명령의 공통 저장 구조는 [저장 결과](docs/runner.md#4-저장-결과)를 따른다.

선택 옵션은 사례의 기존 선언과 교차한다. 같은 옵션을 여러 번 지정하면 그 ID들을 선택하고, 서로 다른 옵션은 모두 충족해야 한다. 사례에 없는 검사를 자동으로 추가하지 않는다. `--check`와 `--row`를 함께 쓰면 행이 속한 검사도 `--check`에 포함해야 한다. 존재하지 않는 ID나 서로 맞지 않는 선택은 입력 오류다. Python의 `score_nodes`는 같은 범위를 `case_ids`, `check_ids`, `row_ids`로 받는다.

채점 전에 모든 예정 반복의 저장 증거를 읽고 실제 노드·역할·호출·선택 도구를 JSON의 `bindings.when`과 대조한다. 조건 불일치가 확인된 사례·호출·평가 항목은 제외하고 이유를 남긴다. 조건 증거가 없거나 모호하면 미판정 대상으로 유지한다. 이후 평가를 취소해도 이 선택 계획을 사용하므로 아직 채점하지 못한 반복과 범위 밖 반복을 구분할 수 있다. 원본 사례와 실행 증거는 변경하지 않는다.

## 평가 자료 준비

사례의 `assessment`에 적용할 검사·호출 범위와 규칙 검사에 필요한 비교 자료를 둔다. 이 내용은 `run`의 업무 모델 입력과 State에 전달되지 않는다. 현재 입력 계약은 [사례 정의](schema.py)와 [노드 평가 정의](nodes/schema.py)를 따른다.

실행 중 노드 시점을 평가할 때는 `initial.execution`으로 기존 실행 메타데이터를 보존할 수 있다. 새 실행 입력과 복원 입력의 제공 조건은 [사례 입력](docs/runner.md#2-입력-준비)을 따른다.

보고서 `compose`는 사례의 `model_call`로 한 모델 호출을 지정한다. 각 호출에 필요한 기존 입력을 `initial`로 준비하며 앞선 작성·검토를 자동 실행하지 않는다.

| `model_call` | 대상 역할 | 수집할 응답 |
| --- | --- | --- |
| `selection` | 보고서 선정 | 뷰 선정 |
| `selection_review` | 보고서 선정 | 기존 선정 검토 |
| `draft` | 보고서 설명·인사이트 | 초안 작성 또는 기존 검토를 반영한 재작성 |
| `draft_review` | 보고서 설명·인사이트 | 기존 초안 검토 |
| `review_retry` | 보고서 설명·인사이트 | 기존 초안의 검토 재실행 |

`model_call`을 생략하면 초기 상태에서 다음에 필요한 첫 모델 호출만 실행한다. 모델 호출 없이 끝나는 단계나 지정한 호출에 필요한 입력이 없는 경우에는 실행 오류를 남기며, 응답 품질을 통과로 판정하지 않는다. 이 필드는 보고서 역할의 `node/compose`에서만 사용한다.

| 항목 | 노드 채점에서 사용하는 내용 |
| --- | --- |
| `checks` | 실행할 검사 ID 목록. 생략하면 `expected.items`에 명시한 검사만 사용하며, 빈 목록은 검사를 실행하지 않음 |
| `reference` | 검사 ID를 키로 하는 규칙 검사 기준 자료. 해당 규칙에 자기 ID의 값만 전달 |
| `expected` | `schema_version`이 `node-expectations-v1`인 객체와 `items` 배열. 검사·호출 선택과 결과 연결에 사용하며, 규칙 검사는 항목의 비교 조건도 사용 |
| `tolerance` | 규칙 검사 ID를 키로 하는 허용 범위. 수치 비교는 항목별 허용 오차가 우선 |
| `required` | 필수 사례 여부. 생략한 사례가 있으면 필수 사례의 종합 통과를 보류 |

`items`의 각 항목은 사례 안에서 고유한 `id`와 현행 정형 평가 정의의 검사 ID를 지정하는 `check`를 갖는다. 평가할 검사·호출 범위는 실행 전에 정한다. 자유 형식의 기존 평가 자료는 보존하지만 규칙 비교 항목으로 자동 변환하지 않는다.

모든 노드 LLM 검사는 실행 당시 입력·실제 출력과 현행 검사 기준으로 판정한다. 항목의 ID·검사 ID·호출 범위는 평가 대상 선택과 결과 연결에 사용한다. 기대답안·비교 조건·`reference`·`tolerance`는 평가 프롬프트와 판정 근거에 포함하지 않으며, `applicable` 선언으로 LLM 판정을 생략하지 않는다. 기대값 생략을 이유로 모델 호출을 중단하지 않는다.

| 항목 | 지정하는 내용 |
| --- | --- |
| `row_id` | 해당 `check`에 속한 상황별 평가 행. 생략하면 현재 호출에 적용하는 행을 사용 |
| `node` | 해당 조건을 확인할 업무 노드 |
| `role` | 해당 노드를 실행하는 에이전트 역할 |
| `occurrence` | 같은 역할·노드가 해당 실행에 등장한 순서. 1부터 시작 |
| `call` | 해당 노드가 직접 실행한 모델 호출 이름 |
| `call_index` | 해당 노드의 직접 모델 호출 순서. 1부터 시작 |
| `path` | 규칙 검사에서 비교할 원본 모델 출력 내부의 JSON Pointer |
| `value` | 규칙 검사에서 비교할 독립 기대값 |
| `match` | 규칙 비교 방식. 기본 `equal`, 선택 `subset`, `present`, `absent` |
| `pattern` | 문자열에서 비교할 부분을 추출하는 정규식. 캡처 그룹은 최대 하나 |
| `extract` | 추출값의 수치 비교는 `number`, 문자열 비교는 `text` |
| `tolerance` | 해당 항목의 수치 허용 오차. `absolute`·`relative` 사용 |
| `applicable` | 규칙 검사의 적용 여부 선언. 입력 양식상 `false`이면 `reason`에 사유 필수이며, LLM의 적용 여부 판단에는 사용하지 않음 |
| `inputs` | 실제 입력·출력 근거의 출처·경로·명칭. `source`, `path`, 선택 `label`로 지정. 별도 `reference` 경로는 규칙 검사에서만 사용 |

범위를 생략한 평가 항목은 해당 검사 행이 적용되는 노드·호출에 사용한다. 작성과 검토 등 평가할 호출이 다르면 `node`, `role`, `occurrence`, `call`, `call_index`로 대상을 구분하고, 같은 검사 안의 상황을 지정할 때는 `row_id`를 사용한다. 호출 이름과 순서는 실제 추적 구조를 따른다. 지정한 노드·호출이 실행 증거에 없으면 미판정 사유를 남긴다. 관측되지 않은 에이전트 내부의 노드 종류·횟수는 임의로 만들지 않으므로, 반드시 실행되어야 하는 범위는 평가 항목에 명시한다.

독립 노드 사례의 호출 순서는 항상 1이다. 보고서 작성·검토를 각각 실행할 때는 `model_call`별 입력과 평가 항목을 준비하고 `call_index`도 1로 지정한다. 같은 사례에 다른 호출의 평가 항목이 남아 있으면 사례의 지정 대상 밖 항목으로 제외한다. 에이전트·생성 흐름에서 추출한 호출은 원래 부모 노드 안의 순서를 사용한다.

채점과 지표에는 지정한 검사·노드·호출 범위만 포함한다. 범위 밖 검사를 추가하거나 빠진 검사를 통과로 만들지 않는다. 저장된 원본 호출은 유지하며, 평가 범위를 좁혀도 노드 발생 순서와 호출 순서는 원래 번호를 사용한다.

규칙 비교의 `path`는 모델 출력 객체를 기준으로 한다. 작업 선택의 `/arguments_json/` 하위 경로는 문자열에 담긴 JSON 객체를 해석해 비교한다. `equal`은 값 전체를, `subset`은 객체의 지정 부분을 대조하며 배열 순서·길이는 유지한다. 산출물 유지 검사 `N04-O.2`에서 `/artifact_ids`를 `equal`로 비교할 때는 ID 집합을 대조한다. `present`와 `absent`는 경로의 존재 여부를 비교한다. 기대값 생략과 명시한 `null`은 구분한다. 수치 허용 오차의 계산은 [도구 채점의 기대값 형식](docs/runner.md#기대값-형식)과 같다.

규칙 검사의 `inputs`는 실제 전송한 `messages`와 모델 원문의 `output`, 독립 기준인 `reference`의 경로를 지정한다. `state`를 지정한 항목은 실제 모델 입력 근거로 대조하지 않고 미판정으로 남긴다. 규칙·LLM 검사 모두 State나 현재 프롬프트 파일로 실행 당시 입력을 보충하지 않는다.

모든 노드 LLM 검사는 선택한 호출에 저장된 `messages` 전체와 `response_schema` 전체를 `모델 호출 입력`으로 받는다. 메시지의 순서·역할·본문·부가 필드와 당시 응답 형식을 그대로 보존한다. 항목의 `inputs`로 이 범위를 좁히거나 다른 자료를 덧붙이지 않는다. 출력은 검사별로 정한 필드를 제공하며, 자료 전송과 인용 경로는 [평가 프롬프트와 원문 추적](#평가-프롬프트와-원문-추적)을 따른다.

평가 모델의 근거 인용은 실제 제공한 표식에 대응해야 한다. `입력 1`과 프롬프트에 표시한 `[입력 1]`은 같은 근거로 연결한다. 대괄호 한 쌍을 제외한 이름이 허용된 표식과 정확히 일치해야 하며, 없는 표식·부분 이름·임의 경로는 미판정으로 남긴다. 원본 모델 응답은 그대로 보존한다.

LLM 판정의 항목 번호에는 기대 내용이나 비교 방법을 붙이지 않는다. 실제 자료에서 확인할 대상·조건·필수 내용은 선택한 검사 기준에 따라 판정한다. 실행 당시 필요한 입력이나 출력이 없으면 해당 사유로 미판정 처리한다.

규칙 검사에서 항목을 비적용으로 지정해도 항상 적용하는 검사 전체를 면제할 수 없다. 비교할 기준이나 필요한 입력이 없는 항목은 미판정이다. 사례 작성자는 규칙 기대 항목이 비교할 조건 전체를 포함하는지와 기준의 독립성을 확인한다.

선택 계획에 남은 비적용 항목도 실제 호출 증거가 없으면 미판정으로 유지한다. 사전 비적용 선언만으로 관측되지 않은 호출의 판정을 완료하지 않는다.

규칙 검사에서 호출·산출물을 선택하지 않을 것으로 준비했더라도 실제 출력에서 선택했다면 관련 검사를 비적용으로 생략하지 않는다. 명백한 출력과 비적용 선언이 충돌하면 미판정으로 남기고, 규칙으로 확인할 수 있는 호출·자료 제한은 추가로 대조한다.

보고서 설명·인사이트의 분량 검사는 `reference["N-F.1"].format.completed`에 완성본 여부를 불리언으로 준비한다. 미완성 안내에는 완성본 분량을 적용하지 않으며, 적용 여부가 없으면 분량은 미판정이다. 문장 수는 구두점을 기준으로 세고 소수·URL·인용·목록 번호를 구분한다. 문장의 의미와 필요한 내용은 LLM 검사가 담당한다.

시각화 규칙은 실제 메시지의 뷰·입력 프로필을 우선 사용한다. 별도 고정 스냅샷을 제공할 때는 해당 검사의 `reference.visualization`에 `views`와 `input_profiles`를 둔다. 현재 배포 카탈로그를 다시 읽어 실행 당시 프로필을 대신하지 않는다.

## 단계와 판정

선택한 검사들을 모델 호출별로 형식 준수 → 필수 내용 충족 → 내용 정확성 순서로 평가한다. 같은 단계의 검사를 마친 뒤 해당 호출의 다음 단계 실행 여부를 정한다. 한 호출의 형식 실패로 다른 호출의 평가를 생략하지 않는다.

| 앞 단계의 결과 | 뒤 단계의 처리 | 검증 완료 여부 |
| --- | --- | --- |
| 적용 검사가 모두 통과 또는 비적용 | 다음 단계 실행 | 모든 필요한 판정을 마친 뒤 결정 |
| 실패가 있음 | 선행 단계 실패로 미실행 | 다른 미판정이 없으면 실패 판정 완료 |
| 확인된 실패 없이 미판정이 있음 | 선행 단계 미판정으로 미실행 | 검증 미완료 |

선택한 범위에 LLM 검사가 있으면 `rules`는 해당 단계에서 보류한다. 이때 뒤 단계의 규칙 검사만 앞질러 실행하지 않는다. 선택한 LLM 검사까지 판정하려면 저장된 실행 증거와 평가 모델을 연결해 `all`을 사용한다. 규칙 검사만 선택했다면 그 검사 결과로 판정한다.

검사 전체 판정과 세부 항목 판정을 각각 저장한다. 하나라도 실패하면 실패를 유지하되, 남은 미판정과 검증 완료 여부는 따로 기록한다. 미실행·미판정·비적용은 통과율의 분모에서 제외하며 각각의 건수는 남긴다. 필수 사례는 선택 계획에 남은 모든 반복이 통과해야 통과로 센다. 조건이 달라 제외된 반복은 `excluded_repetitions`에 기록하며 누락·미완료로 세지 않는다. 같은 사례도 반복별로 선택된 검사·평가 항목을 사용한다. 필수 사례 통과율의 분모는 통과·실패가 판정된 사례이며, 미완료 사례·누락 반복·필수 여부 미지정을 별도로 확인한다. 평가할 반복이 없으면 통과로 만들지 않는다.

선택 계획에 남은 요청 검사에 판정이 없으면 실행 결과의 `unmatched_checks`와 기능 집계의 `missing_checks`에 기록하고 완료로 처리하지 않는다. 비적용으로 선언한 평가 항목도 실제 호출 증거가 없으면 미판정으로 남긴다. 다른 검사의 통과나 사전 비적용 선언으로 이 누락을 면제하지 않는다.

노드·역할별 집계에서도 각 반복의 명시한 평가 범위를 확인하며, 다른 그룹만 평가하도록 선택된 반복은 해당 그룹의 누락으로 세지 않는다.

원본 모델 응답을 JSON으로 다시 해석해 형식을 검사한다. 실제 전송 입력과 원문으로 판정하며 업무 코드의 수용 여부·State 반영·노드 종료는 품질 통과 조건이 아니다. 원문을 확보한 형식 오류는 실패이며, 원문 부재·부모 호출 연결 누락·상충 기록으로 판단할 수 없는 부분은 미판정이다. 원문을 받은 뒤 후처리가 실패하거나 부모 노드의 종료 기록이 누락되어도 확인 가능한 출력은 평가한다. 선택한 모델 호출의 오류·미종료는 모델 운영 통계에, 부모 노드의 후처리 오류는 원본 실행 추적에 구분해 보존한다.

형식 검사에는 실행 당시 제공한 응답 스키마와 평가 전용 스키마, 구조 차이 경로도 남긴다. 이 진단은 계약 불일치를 확인하는 자료이며, 실제 출력의 형식 판정을 대신하지 않는다.

## 운영 지표와 목표

기능 판정과 별도로 선택한 모델 호출의 기술적 실패율, 응답시간, 입력·출력 토큰 수, 호출 수, 기술적 재시도 수를 노드·역할별로 집계한다. `operational.measurement_scope`는 `selected_model_calls`다. 노드 단독·에이전트·생성 흐름 모두 같은 모델 호출 경계를 사용하며, 부모 노드의 후처리 오류·도구·하위 에이전트·평가 모델의 사용량은 포함하지 않는다. 부모 노드 전체의 시간·오류·사용량은 원본 실행 추적에서 확인한다.

같은 부모 노드에서 선택한 모델 호출들의 시간·토큰·호출 수를 합산하고, 작성·검토를 각각 채점해도 부모 노드를 여러 실행으로 세지 않는다. 시간은 각 선택 모델 호출의 경과 시간 합계로, 호출 사이의 후처리·대기 시간은 제외한다. 선택한 모델의 기술적 실패 여부를 확인할 수 있어야 정상·오류 시간과 실패율에 포함한다. 이는 모델 출력 평가의 측정 범위이며, [노드 지표](docs/nodes/README.md#22-운영-지표)의 실제 노드 전체 실행 측정과 구분한다.

실패율은 선택 모델 중 기술적 실패가 확인된 노드별 측정 수를, 선택 모델 호출이 종료되고 기술적 실패 여부를 확인할 수 있는 노드별 측정 수로 나눈다. 종료 기록은 있으나 원문·오류 증거가 없어 분류할 수 없는 측정과 실제 미종료 호출은 따로 센다.

시간에는 중앙값과 p95를, 토큰·호출·기술적 재시도에는 평균과 p95를 제공한다. `technical_retries_by_kind`에서는 선택한 모델의 기술적 재시도만 집계하며 도구·하위 에이전트 재시도는 포함하지 않는다. 내용 재작성은 기술적 재시도로 세지 않는다. p95는 정렬한 표본의 `ceil(0.95 × 표본 수)`번째 값이다. 사용량·재시도 근거가 없으면 0으로 추정하지 않으며 누락·미종료 수를 따로 기록한다. 기술적 실패율의 분모도 실패 여부를 확인할 수 있는 종료 호출만 포함한다.

선택한 모델 호출이 미종료이면 관측 사용량을 `unfinished_usage`에 부모 노드·실행 ID와 함께 별도로 남긴다. 이미 받은 토큰 합계, 토큰 측정이 없는 호출 수, 관측한 선택 모델 호출 수와 기술적 재시도를 구분하며 종료된 측정의 통계에 합산하지 않는다.

현재 자동 집계는 노드·역할별이다. 모델별·입력 규모별 비교는 자동으로 나누지 않는다. 실제 모델 이름은 SDK 응답의 `response_metadata.model_name`이 있는 경우 원본 추적에서 확인할 수 있고, HTTP 요청의 `body.model`은 요청한 모델 이름이다. 두 값이 없으면 추정하지 않는다. 모델·입력 규모가 다른 실행을 비교할 때는 원본 모델 정보·실제 입력과 사전에 정한 시험 조건을 함께 확인한다.

입력 묶음의 `node_performance` 배열에 노드·역할별 운영 목표를 지정한다. 도구의 `performance`와 별도다.

| 항목 | 내용 |
| --- | --- |
| `target` | 목표를 적용할 노드 |
| `role` | 목표를 적용할 에이전트 역할 |
| `metric` | `response_time` 또는 `failure_rate` |
| `case_ids` | 목표를 측정할 대표 사례 ID 배열 |
| `group` | 선택 모델 호출 응답시간의 `normal` 또는 `error`. 기능 통과·실패와 구분하는 기술적 종료 종류 |
| `statistic` | 응답시간의 `median` 또는 `p95` |
| `max_seconds` | 응답시간의 최대 허용 초 |
| `max_rate` | 기술적 실패율의 최대 허용 비율. 0부터 1 사이 |
| `environment` | 시험 환경 설명 |
| `data_size` | 대표 자료 크기 설명 |

목표·시험 조건이 미확정이거나 지정 사례의 예정 반복·필수 측정이 빠졌으면 운영 목표를 통과시키지 않는다. 확인 가능한 표본의 수치는 남기되 목표 판정은 미판정이다. 목표가 없으면 운영 판정은 미판정으로 남는다. 노드 종합 판정의 범위는 기능과 지정된 운영 목표이므로, 목표를 지정하지 않은 기능 통과를 운영 성능 통과로 해석하지 않는다.

채점 범위를 좁혀도 `node_performance`의 원래 대표 사례·예정 반복·목표값은 축소하지 않는다. 그중 일부가 선택 범위에서 빠졌으면 남은 측정만으로 목표를 통과시키지 않는다.

## 저장 결과와 기준 버전

채점 명령은 `assessments/<채점 ID>/`에 공통 자료와 사례·검사별 판정을 나눠 저장한다. 원본 `report.json`과 기존 단일 JSON은 보존하며 자동 이관하거나 삭제하지 않는다. 파일 배치·완료 확인·읽기 API는 [공통 저장 계약](docs/runner.md#4-저장-결과)을 따른다. 노드 결과를 다시 읽으면 기존 `node-evaluation-v1` 판정 구조로 연결된다.

[노드 평가 결과 뷰어](viewers/nodes/README.md)에서 노드·역할별 지표, 반복별 판정, 모델 호출별 실제값·근거, 규칙 검사의 기대값과 선택·제외 계획을 확인한다. 자동 조회는 로컬 HTTP 서버에서 경량 목록인 `eval/outputs/evaluation-viewer/catalog.json`을 먼저 읽고, 선택한 묶음·채점·사례·검사에 필요한 원본 파일만 요청한다. 기존 단일 JSON은 명시적으로 선택할 때 읽는다. 원문 전체를 합친 `results.js`는 사용하지 않는다. 서버 실행·수동 열기는 [뷰어 사용 방법](viewers/nodes/README.md#사용-방법), 읽는 순서와 목록 갱신은 [공통 조회 안내](docs/runner.md#4-저장-결과)를 따른다. 아래 표는 채점 JSON의 항목이다.

| 결과 항목 | 내용 |
| --- | --- |
| `runs` | 예정한 사례·반복별 판정, 검증 완료 여부, 연결하지 못한 평가 항목 |
| `runs[].model_scope` | 선택 계획에 남은 실행의 모델 이름·호출 순서·원본 위치. 대상 식별용 기록 자체를 판정·운영 통계에 합산하지 않음 |
| `assessments` | 노드별 검사 전체·세부 판정, 실행 여부, 사유, 원문 증거 위치와 호출별 판정 |
| `nodes` | 노드·역할별 기능 집계, 검증 미완료 현황, 운영 통계·목표 판정 |
| `criteria` | 사용한 정형 평가 정의 원문·검사 정의·관련 원칙·사례 기준·실행 계획·운영 목표 |
| `criteria.effective_cases` | 선택한 반복의 검사·평가 항목을 모은 집계용 사례 사본 |
| `selection` | 요청한 선택 조건, 사례·검사·평가 항목의 선택·제외·미판정 사유와 반복별 실제 평가 계획 |
| `criteria_sha256` | 평가 기준의 해시 |
| `evidence_sha256` | 읽은 실행 파일의 해시 |
| `evaluator_sha256` | 평가 코드의 해시 |
| `provenance` | 실행 당시와 현재의 사례 기준·문서 버전 비교. `same`, `changed`, `unknown` |
| `judge_trace` | 업무 추적과 분리한 평가 모델의 실제 입력·원본 응답·오류·사용량 |
| `status` | 채점 절차 종료 상태. `completed`도 모든 검사의 판정 완료나 통과를 뜻하지 않음 |

재채점할 사례의 검사·호출 범위와 규칙 비교 조건은 실행 묶음의 `suite.json`에서 읽는다. 이를 보완할 때는 일반 JSON으로 읽은 이 파일의 `assessment`를 수정하고, `runs/<실행 ID>/case.json`과 실제 실행 기록·기존 채점 결과는 보존한다. 다음 채점의 `provenance`에는 원래 `assessment`와 변경 여부가 기록된다. 원본 시나리오 파일만 수정하면 이미 저장한 실행 묶음의 선언은 바뀌지 않는다. LLM 판정에는 저장된 기대답안이나 비교 조건을 전달하지 않는다.

LLM 검사 기준은 매 채점 때 [노드 평가](docs/nodes/README.md)에 연결한 JSON에서 읽는다. 검사 정의와 관련 공통 원칙은 JSON을 단일 원본으로 사용하며, Markdown의 표나 보관본에서 기준을 추출하지 않는다. 현재 상황의 검사 행에서 판정에 필요한 내용과 연결된 원문 조항을 선택해 자연어 구획으로 제공한다. 전체 기준 원문·출처·해시와 선택 조항의 위치는 평가 기록에 보존한다.

`checks`에는 원본 표의 한글 열을 사용하는 평탄한 검사 행을 둔다. 평가기는 `bindings`의 실행 상황으로 행을 선택하고, 해당 행의 평가 입력과 선택한 판정 조항을 사용한다. LLM 행은 `judge_fields`에서 적용 조건·측정 방법·성공 기준의 원문 구간을, 원칙 참조의 `clause_ids`에서 공통·대상별 조항을 지정한다. 조항의 용도 분류·문자 범위·원문 해시 검사는 [판정 조항 선택](docs/nodes/migration.md#판정-조항-선택)을 따른다. 필드·원칙의 전체 원문 해시가 선택 정보와 다르면 평가 정의 로딩을 거절하므로 원문 변경 시 선택 정보도 함께 검토해야 한다.

노드 검사 결과의 `related_checks`는 저장·뷰어 형식을 유지하기 위한 빈 목록이며, 기준 본문의 검사 ID에서 채우지 않는다.

규칙 검사도 현행 JSON을 읽되, 문장 변경을 실행 코드로 자동 변환하지 않는다. 선택한 행을 규칙 비교와 LLM 평가에 같은 방식으로 연결하며, 범위를 좁혀도 전체 정의에 대한 규칙 해시 검사는 유지한다. 규칙 기준 원문이 구현 당시 해시와 다르면 규칙 판정을 보류한다. 변경된 기준과 구현을 대조해 코드를 갱신한 뒤 다시 평가해야 한다. 실행 당시와 기준이 달라졌다는 기록은 변경 승인이나 과거 결과의 재현을 뜻하지 않는다. 실행 지문에는 현행 평가 Markdown과 JSON을 포함하며, 이관 대조용 원본 보관본은 제외한다.

취소 시 이미 완료한 판정과 미완료 항목을 `cancelled` 결과로 저장한 뒤 취소를 전달한다. 계획에 있지만 실행 등록이 없는 반복, 등록 뒤 결과 파일이 없는 반복, 채점하지 못한 반복은 통과로 처리하지 않는다. 저장에 실패한 채점은 오류로 보고하며 읽을 수 있는 JSON이 있는지 확인한다.

### 평가 프롬프트와 원문 추적

평가 모델에는 판정 기준, 실행 당시의 모델 호출 입력, 검사 대상 출력을 구분해 제공한다. 모델 호출 입력은 저장된 메시지 배열과 응답 스키마를 원본 값으로 복원할 수 있는 JSON으로 표시한다. 출력은 검사별로 필요한 필드를 자연어 구획으로 표시한다. 별도 기대답안과 비교 자료는 제공하지 않는다.

시스템 메시지는 평가자 역할로 시작하고, 선택한 원문 조항을 `평가 대상과 적용 조건`·`대조할 기준`·`담당 범위`·`공통 판정 규칙`으로 모은 뒤 응답 표식 계약으로 끝낸다. 조항의 구획과 묶음 순서는 JSON의 선택 정보로 지정하며, 대조할 기준은 관련 조항을 묶은 번호 목록으로 제공한다. 공통 규칙은 판정의 의미·우선순위·사유 기록으로 통합하고, 구체 기준에 이미 있는 대조 절차는 반복하지 않는다. 담당 범위는 현재 검사에서 제외하는 대상을 간결하게 안내하며, 응답 필드 지시는 한데 모은다. 검사별 조건·예외는 유지한다.

역할·호출 종류로 행을 고르는 것과 내용이 검사 적용 조건에 해당하는지 판정하는 것은 구분하며, 선택한 적용 조건은 계속 제공한다. 공통 판정 규칙은 JSON의 조항을 읽고 고정 안내에 중복해서 두지 않는다. 운영·수정 이력과 해당 검사에 필요 없는 완료 조항은 선택하지 않으며, 완료 범위를 확인하는 검사에는 그 기준을 유지한다. 원문의 선택 범위·구획·묶음 검증은 [판정 조항 선택](docs/nodes/migration.md#판정-조항-선택)을 따른다.

각 검사의 측정 방법과 성공 기준에 맞춰 출력 필드를 명시한다. 예를 들어 질문의 필수 내용은 질문 본문을, 보고서 검토의 정확성은 적합 여부와 판단 이유를 함께 대조한다. 선택하지 않은 출력 필드는 원본에 남기며, 빠진 필수 필드를 빈 값으로 채우거나 일부 출력만 보고 전체 출력이 없다고 판단하지 않는다. 필드 선택은 [검사별 선택 코드](nodes/prompt_fields.py), 전송 구획 구성은 [전송 메시지 구성 코드](nodes/prompt_rendering.py)에서 관리한다. 기준 원문이나 응답 계약이 바뀌면 출력 필드 선택도 대조·갱신해야 한다. 새 행·호출에 전체 출력 선택을 자동 적용하지 않는다.

필수 내용 검사에 제공할 필드는 [단계별 역할과 평가 경계](docs/methods.md#노드-출력과-에이전트-실행)를 함께 대조한다. 목적 파악의 목표·조건·이유처럼 후속 판단이 읽는 내용과, 사용자에게 전달할 응답·질문 본문을 구분해 선택한다. 판정 기준은 [노드 검사의 세 축](docs/nodes/common.md#노드-검사의-세-축)과 각 검사 정의에서 관리한다.

현재 LLM 검사 37개 행의 실행 입력은 모두 `모델 호출 입력`이다. 저장된 모든 메시지의 원래 순서·역할·본문·부가 필드와 당시 `response_schema` 전체를 제공한다. 메시지에 있는 업무 지침·도구 명세·대화·작업 이력·자료 본문·메타데이터·실패·검토 기록·반복된 값도 그대로 포함한다. 검사 기준에 따라 입력 일부를 추출하거나, 중복을 줄이거나, 승인된 설명만 골라 노출하지 않는다.

원문에 있는 업무 지침은 업무 모델의 응답이 입력과 맞는지 대조하는 근거다. 평가 모델 자신의 지시로 실행하지 않는다. 전체 자료가 제공돼도 근거로 사용할 수 있는 범위는 각 검사 기준을 따른다. 예를 들어 승인된 설명을 사용해야 하는 검사에서는 평가 모델이 설명·검토·참조의 전체 원문을 보고 승인 연결과 사용 범위를 판단한다.

메시지 목록이 없거나 메시지·보관된 응답 스키마의 형식이 손상되면 평가 모델을 호출하지 않고 미판정으로 남긴다. 과거 기록에 응답 스키마가 없으면 현재 코드의 스키마로 보충하지 않으며, 미보관 자체로 호출을 차단하지 않는다. 자료의 내용·승인 연결·충족 여부는 전체 원문을 받은 평가 모델이 기준에 따라 판단한다. 확보한 출력의 누락·잘못된 값은 입력 기록의 기술적 누락과 구분해 평가한다.

내용 대조와 증거 인용은 [LLM 판정 절차](docs/methods.md#llm-판정-절차), 판정값과 확인하지 못한 조건의 사유 기록은 [판정 원칙](docs/methods.md#4-판정-원칙)을 따른다. 현재 각 노드 검사는 담당 기준을 실행 당시 입력·원본 출력과 대조해 독립적으로 판정한다. 기준 본문의 다른 검사 ID는 책임 범위 안내이며, 다른 검사의 판정과 재사용 조항은 평가 모델에 제공하지 않는다. 선행 검사 결과에 따른 실행 중단과 판정 집계는 실행기가 처리한다.

모델 호출 입력은 `null`, `[]`, `{}`, `false`, `0`과 빈 문자열을 원래 값으로 유지한다. 입력의 식별자·도구명·단계·상태·참조를 바꾸지 않으며, 실패·검토 이력을 재해석한 요약이나 승인 표시를 덧붙이지 않는다. 출력의 부재와 선택에서 제외한 필드는 해당 기록으로 구분한다.

`판정 항목`에는 `항목 1`처럼 결과를 연결할 번호만 표시하고, 인용할 실제 자료에는 `입력 1`·`출력 1` 같은 짧은 표식을 붙인다. 검사 ID·원래 항목 ID·실행 선택용 역할 코드·추적 경로를 별도 판정 자료로 덧붙이지 않는다. 원본 메시지·응답 스키마와 선택한 출력에 이미 있는 식별자·값·문자열·경로는 보존한다.

호출별 `judge.prompt`는 선택 당시 자료, 전송 전 구조와 실제 전송 문자열을 구분해 보관한다. 아래 항목과 기준 원문은 채점 JSON에 그대로 보관한다.

| 기록 항목 | 내용 |
| --- | --- |
| `messages` | 평가 모델에 실제 전송하는 자연어 시스템·사용자 메시지 |
| `payload` | 전체 모델 호출 입력·원본 출력과 결과 연결용 항목 ID를 보관하는 전송 전 구조 |
| `source_payload` | 전체 모델 호출 입력·원본 출력의 사본과 결과 연결용 항목 ID |
| `criteria` | 선택한 행과 연결 원칙의 전체 원문·경로·행·해시, 선택한 필드·원칙 조항의 원문 위치와 실제 시스템 메시지 위치 |
| `evidence_mappings` | 기존 저장 형식을 유지하는 빈 목록. 입력 원문을 압축·병합하지 않음 |
| `fields` | 전체 모델 호출 입력과 선택한 출력의 구획·명칭·원본 경로·존재 상태와 값 또는 부재 사유 |
| `assessment_fields` | 기존 저장 형식을 유지하는 빈 목록 |
| `excluded_paths` | 출력 필드 선택에서 제외한 원본 경로. 전체 모델 호출 입력은 제외하지 않음 |
| `evidence_labels` | 전송한 자료 표식과 원본 경로·자료 종류의 연결. `missing_path`는 누락 위치, `json_path`는 문자열에 담긴 JSON의 내부 위치 |
| `expectation_ids` | 전송한 판정 항목 번호와 원래 항목 ID의 연결 |

행의 선택 기록은 `criteria[0].selected_fields[].clauses`, 원칙의 선택 기록은 해당 원칙의 `selected_clauses`에 둔다. 각 조항에는 선택 정보의 구획·묶음인 `section`·`group`과 실제 전송 문구인 `sent_text`를 남긴다. `system_start`·`system_end`는 시스템 메시지에서 0부터 세는 문자 범위이며, 시작 문자는 포함하고 끝 문자는 제외한다. 같은 전송 문구는 한 번만 넣고, 여러 원문에서 선택했으면 각 원문 기록을 같은 전송 범위에 연결한다.

`payload`·`source_payload`의 `assessment.expectations`에는 결과 연결용 `id`만 보관한다. 기대답안·별도 기준 자료·허용 오차·비교 방법은 이 구조와 사용자 메시지에 넣지 않으며 해당 자료의 인용 표식도 만들지 않는다. 검사 기준 원문과 선택 조항은 `criteria`와 시스템 메시지에 기록한다.

기준 출처·실행 추적용 경로·행·해시는 기록에 남기며 모델에 보내지 않는다. 평가 모델은 제공한 판정 항목 번호와 실제 자료 표식으로 결과를 반환한다. 평가기는 표식을 검사한 뒤 원래 항목 ID와 증거 경로로 되돌려 판정 결과에 저장한다. 누락은 확인한 상위 자료를, 문자열에 담긴 JSON은 원본 문자열을 인용하고 세부 위치는 표식 연결 기록에 남긴다. 판정 항목의 누락·중복, 제공하지 않은 표식이나 자료의 인용은 미판정으로 처리한다. 통과·실패에 필요한 출력 표식이나 대조한 입력 표식이 없으면 미판정으로 처리한다. 이 검사는 표식의 제공 여부와 자료 종류를 확인하며, 인용한 내용이 판정 사유를 뒷받침하는지는 내용 판정과 사람 검토에서 확인한다.

## 구현 검증 범위

뷰어 통합 검증의 모의 모델·소규모 임시 산출물은 실행기와 화면 자료 연결을 확인하는 용도다. 이 통과 결과나 가상 화면 샘플을 실제 누적 결과 전체의 로딩·표시·응답성 검증으로 해석하지 않는다. 실제 누적 자료에서는 최초 목록, 묶음·채점 전환, 사례·검사 선택 때 요청한 파일과 크기, 로딩 오류·지연을 별도로 확인한다.

기존 실패는 [보관 원문 안내의 기록 해시 불일치에서 파생된 3개](tests/test_node_criteria_preservation.py), [API 왕복의 기대 완료 상태 불일치](../tests/test_roundtrip_evidence.py)다. 별도 [노드 화면 연결 검사](viewers/nodes/runner_integration.py)의 모의 판정·기대값 불일치 1개도 이동 전부터 동일했다. 이번 위치 정리에서는 보관 원문의 기준 해시와 평가 판정·기대값을 바꾸지 않았다.

외부 모델 품질, 운영 DB·백엔드·Tableau 연결과 Docker 이미지 실행은 이 구조 검증에 포함하지 않는다.

### 프롬프트 변경의 품질 비교

프롬프트 변경 전후를 실제 평가 모델과 사람 판정으로 비교하는 시험은 아직 실행하지 않았다. 준비한 응답을 사용한 단위 테스트나 전체 입력의 전달 확인만으로 판정 품질이 개선됐다고 판단하지 않는다.

같은 사람이 사전에 판정한 별도 사례를 준비한다. 정상 요약·허용한 재서술, 근거에 없는 인과관계 추가, 대상·기간 변경, 근거 부족, 필수 내용 누락을 포함하고, 사례별 적용 검사·기대 판정·근거를 고정한다. 같은 저장 입력·원본 출력·평가 모델·설정·반복 수에 변경 전후 프롬프트를 적용해 항목별 결과를 비교한다.

사람이 적합하다고 판정한 내용을 실패로 잡는 오탐, 사람이 확인한 위반을 놓치는 미탐, 미판정 건수를 각각 기록하고 판정 근거도 대조한다. 평가 모델이 실제 반환한 토큰 사용량과 호출 응답시간은 품질 결과와 함께 비교한다. 사용량이 없으면 추정값을 실제 측정으로 대신하지 않는다. 차이가 생기면 기준 조항·입력 선택·모델 판정 중 원인을 확인하고, 기준을 완화하지 않은 채 해당 범위를 재검증한다.
