# 결정 기록: 로그인 방식과 에이전트 흐름 전달 방식

- 결정일: 2026-10-28 (2026-10-29, 2026-11-02 수정)
- 결정: 로그인은 서버 세션(Spring Session JDBC, PostgreSQL 저장)으로 관리하고, 세션 ID를 HttpOnly 쿠키에 담는다. 에이전트 동작 흐름은 2026-11-02부터 ③ 폴링(A 방식)으로 전달한다. BE가 질문 행을 저장하고, AI(FastAPI)가 진행·완료·실패·취소 행을 `ai_message`에 직접 저장하고, 화면은 1초마다 마지막으로 받은 행 이후를 조회한다. (10/28~11/2에는 ① EventSource(SSE) + 쿠키였다. 쿠키에 담는 값은 JWT가 아닌 세션 ID)
- 비교한 대안: ② Authorization 헤더 + fetch 스트림, ③ 폴링, ④ 쿠키에 JWT + 리프레시 토큰
- 에이전트 패널 계약: [docs/api/ai-agent-panel.md](../api/ai-agent-panel.md), `docs/api/openapi.json` 2.3.0 (API-03·03-S1·03-S2·36~38)

## 결정에 영향을 준 조건

- 서비스는 웹 하나이고, 화면과 API가 Nginx 한 주소 아래에 있다 (같은 출처)
- 도메인은 SSAFY 제공 도메인을 쓴다. 다른 팀 사이트와 상위 도메인을 공유한다
- 인증 기능은 아직 구현 전이다 (10/28 기준)
- 요구사항: 에이전트 흐름을 생성 중에 단계 단위로 보여주고, 끝난 뒤 다시 조회할 수 있어야 한다
- 로그인을 즉시 끊어야 하는 시점이 있다: 로그아웃, 비밀번호 변경(다른 세션), 임시 비밀번호 발급, 탈퇴
- 프론트 1명, 백엔드 2명, 개발 기간 2주 (10/29 ~ 11/08)
- 사례자 개인 정보를 다루는 서비스다
- (11/2 추가) AI가 진행 단계와 답변을 `ai_message`에 직접 쓴다. AI 계정(`eumi_ai`)은 `ai_message` 읽기·추가만 가능하다

## ② 헤더 + fetch 스트림 대비 (로그인 쿠키 결정의 근거, 유지)

| 얻은 것 | 감수한 것 | 감수할 수 있었던 이유 |
|---|---|---|
| 스크립트가 쿠키를 읽을 수 없어 XSS가 생겨도 로그인 정보가 새지 않음 | CSRF 대비가 새로 필요 | Spring Security의 CSRF 토큰(쿠키 토큰 방식)을 켜 두고, 데이터를 바꾸는 GET 금지와 CORS 우리 도메인만 허용을 함께 지킨다. 세션 방식에서는 CSRF 보호가 기본으로 켜져 있어 설정만 맞추면 된다. 반면 ②의 토큰 탈취 위험은 화면 코드(특히 에이전트 답변 렌더링)가 늘 때마다 계속 신경 써야 한다 |
| 토큰 보관 위치(localStorage, 메모리) 고민이 사라짐 | 세션 쿠키 설정 | 쿠키 발급·검증·만료를 Spring Session과 Spring Security가 맡는다. 직접 짤 것은 로그인 API와 회원별 세션 삭제뿐이다 |

10/28 판에 있던 스트림 관련 두 줄(브라우저의 재연결·이어 받기, GET으로만 스트림 열기)은 11/2 폴링 전환으로 뺐다.

## ③ 폴링으로 바꾼 이유 (2026-11-02)

10/28에는 '생성 중 실시간'과 글자 단위 확장을 이유로 ③ 폴링 대신 ① SSE를 골랐다. 11/2에 AI가 DB에 직접 쓰기로 하면서 BE가 흐름을 중계할 일이 없어져, 조회 방식으로 바꿨다.

| 얻은 것 | 감수한 것 | 감수할 수 있었던 이유 |
|---|---|---|
| AI가 DB에 쓴 행을 그대로 읽으면 되어 BE에 중계·run 메모리·이벤트 id·heartbeat가 필요 없음 | 최대 1초 지연, 실행 중 초당 1회 요청 | 단계 단위 표시라 1초 지연은 체감이 작다. 사용자 수가 적어 요청 수가 부담되지 않는다 |
| 연결이 끊겨도 다음 조회가 마지막 id부터 이어 받음. 새로고침은 처음부터 다시 읽으면 끝 | 글자 단위 스트리밍 확장은 어려움 | 요구사항은 단계·답변 표시다 |
| Nginx SSE 설정, HTTPS에서 SSE 확인이 필요 없음 | 요청 제한을 걸 때 조회 경로를 빼야 함 | 제한 대상은 로그인·인증 메일·임시 비밀번호 3개 경로뿐이다 |

## ④ 쿠키에 JWT + 리프레시 토큰 대비 (2026-10-29 추가, 유지)

| 얻은 것 | 감수한 것 | 감수할 수 있었던 이유 |
|---|---|---|
| 로그아웃·비밀번호 변경·탈퇴 때 세션을 지우면 바로 끊김 | 요청마다 세션을 DB에서 조회 | 사용자 수가 적은 서비스라 부담이 없다. JWT도 즉시 차단을 하려면 결국 서버 저장소를 조회해야 했다 |
| 토큰 갱신 단계가 없음. 조회가 401이면 로그인 화면으로 보내면 끝 | 쿠키 방식에 묶임 | 웹 하나만 쓰는 지금 조건에서는 헤더 방식의 장점이 없다. 모바일·외부 서비스가 생기면 다시 검토한다 (아래 조건) |
| 세션이 DB에 있어 재배포 후에도 로그인 유지 | FastAPI가 세션을 직접 확인할 수 없음 | 브라우저는 Spring Boot만 부르고, FastAPI는 외부에 열지 않는다. 사용자 정보는 Spring Boot가 member_id로 넘긴다 |
| 토큰 발급·서명·갱신·폐기 코드와 토큰 테이블 2개가 필요 없음 | Spring Session 테이블 2개를 구조 그대로 둬야 함 | 프레임워크가 정한 구조라 Flyway에 그대로 넣기만 하면 된다 |

## 요약

보안(로그인 정보 탈취 방지), 프론트 부담 감소, 즉시 로그아웃을 얻는 대신 백엔드의 일회성 설정(CSRF·CORS·세션 쿠키)을 감수했다. 10/29에 토큰 방식을 서버 세션으로 바꿔 직접 짤 인증 코드가 더 줄었고, SSAFY 도메인 조건 때문에 CSRF 토큰을 추가했다. 11/2에는 AI가 DB에 직접 쓰기로 하면서 에이전트 흐름을 SSE 대신 1초 조회로 바꿨다.

## 함께 지킬 것

- 세션 쿠키: HttpOnly, Secure(운영), SameSite=Lax, Domain 지정 안 함 (지정하면 같은 SSAFY 상위 도메인의 다른 팀 사이트로도 전송된다)
- Spring Session: Flyway가 테이블을 만들므로 `spring.session.jdbc.initialize-schema=never`, 세션 이름(principal)은 member_id 문자열, 유휴 만료 2시간
- CSRF: Spring Security CSRF 보호를 끄지 않고 쿠키 토큰 방식으로 둔다. 프론트는 상태를 바꾸는 요청에 `XSRF-TOKEN` 쿠키 값을 `X-XSRF-TOKEN` 헤더로 보낸다
- 데이터를 바꾸는 GET 요청을 만들지 않는다. CORS는 우리 도메인만 허용한다
- 세션 처리 시점: 로그인 성공 시 세션 ID 교체, 로그아웃 시 세션 삭제, 비밀번호 변경 시 다른 세션 삭제 후 현재 세션 ID 교체, 임시 비밀번호 발급·탈퇴 시 그 회원 세션 전부 삭제
- 에이전트 조회: 대화 소유자 확인(남의 대화는 404), `message_id > after` 오름차순, 끝 행(완료·실패·취소)을 받으면 화면이 조회를 멈춘다. 조회가 한 번 실패해도 다음 조회가 마지막 id부터 이어 받으므로 재연결 처리는 없다. 401이면 로그인 화면으로 보낸다
- Nginx: 에이전트 전용 설정(버퍼링 끄기·긴 타임아웃)을 두지 않는다. 요청 제한은 로그인·인증 메일·임시 비밀번호 경로에만 걸고 조회 경로는 뺀다
- FastAPI는 Nginx에서 외부로 열지 않고 Spring Boot만 호출한다
- 에이전트 답변을 HTML·마크다운으로 그릴 때 DOMPurify 같은 정화 라이브러리 사용

## 다시 검토할 조건

- 모바일 앱이나 외부 서비스가 API를 직접 쓰게 될 때 (쿠키보다 헤더가 편하다, 그때는 ④ 토큰 방식을 다시 본다)
- 화면과 API를 다른 도메인으로 나눌 때
- SSAFY 도메인이 아닌 독립 도메인으로 옮길 때 (CSRF 대비 근거가 달라진다)
- 답변을 글자 단위로 흘려 보여줘야 할 때 (그때 SSE를 다시 본다)
