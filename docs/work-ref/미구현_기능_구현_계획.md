## 3. 공통

### 3-1. 오류 코드 (BE `ErrorCode`에 추가)

계약에는 이미 있는 코드다. BE enum에 없어서 추가한다. 사용자 문구는 BE 기본 문구 규칙을 따르고, 세부 사유는 노출하지 않는다.

| 코드 | 상태 | 쓰는 API |
|---|---|---|
| `EMAIL_DOMAIN_MISMATCH` | 400 | API-05 |
| `EMAIL_ALREADY_EXISTS` | 409 | API-05 · 07 |
| `VERIFICATION_INVALID` · `VERIFICATION_EXPIRED` | 400 | API-06 |
| `PROOF_INVALID` · `PROOF_EXPIRED` | 400 | API-07 |
| `RATE_LIMITED` | 429 | API-05 (재발송 60초), Nginx 요청 제한과 같은 본문 |
| `WITHDRAW_PASSWORD_MISMATCH` | 400 | API-34 |
| `STATE_CONFLICT` | 409 | API-23 · 34 |
| `AI_UNAVAILABLE` | 503 | INT-04 (AI-b, INT-05가 3초 안에 202가 아닐 때) |

### 3-2. 해시와 무작위 값

- 열쇠는 `eumi.auth.hash-key`(운영 `EUMI_AUTH_HASH_KEY`)이고, 계산은 HMAC-SHA256이다. 원문은 DB · 로그에 남기지 않는다.
  - `code_hash` = HMAC(`"code:" + 이메일 + ":" + 코드`). 코드가 같아도 이메일마다 해시가 달라진다.
  - `proof_hash` = HMAC(`"proof:" + 토큰`)
  - 비교는 상수 시간으로 한다 (`MessageDigest.isEqual`).
- 무작위 값은 모두 `SecureRandom`으로 만든다.
  - 인증 코드: 숫자 6자리 (앞자리 0 허용)
  - 가입 증명: 32바이트 base64url
  - 임시 비밀번호: 아래 4-2의 규칙

### 3-3. 메일

- `MailService.sendPlainText`로 보낸다. 운영 · 로컬 모두 Mailpit에 모인다.
- 발송은 DB 변경과 같은 트랜잭션 안에서, 커밋 직전에 한다. 발송이 실패하면 DB 변경을 되돌리고 500을 반환한다.
- 발송이 성공한 뒤 커밋이 실패하는 경우는 받아들이는 한계다. 이때 메일의 값은 쓸 수 없다.
- 제목에는 `[이음이]`를 붙인다. 본문에는 값과 유효 시간만 적고, 이름 · 기관 같은 다른 개인정보는 넣지 않는다.

### 3-4. 세션 · 시간 · 잠금

- **세션 삭제:** `spring_session.PRINCIPAL_NAME` = memberId인 행을 지운다. `PasswordChangeRepository.deleteOtherSessions`를 "전부 삭제"까지 쓸 수 있게 넓힌다.
- **날짜 기준:** 서울 날짜(`Asia/Seoul`), 시각은 `Clock` 빈을 쓴다.
- **잠금 순서:** 기관 → 회원(member_id 오름차순) → 사례자(case_id 오름차순) → 자원(resource_id 오름차순). 잠금을 얻은 뒤 관련 조회를 다시 한다.
- **해시 계산 위치:** PBKDF2 계산은 트랜잭션 밖에서 한다(비밀번호 변경과 같은 방식).

### 4-2. A3 비밀번호 찾기 (API-09, FR-014 · 015)

`POST /api/auth/temp-password {email, name}` → 항상 204 (본문 없음). 입력 형식 오류만 400이다.

1. 이메일을 정규화한다(trim · 소문자). 이름은 앞뒤 공백만 뺀다.
2. 대상 회원을 찾는다. 아래 경우는 모두 아무것도 하지 않고 204를 반환한다.
   - 회원이 없음
   - 이름이 다름
   - 탈퇴함 (`withdrawn_at`)
   - 유효한 임시 비밀번호가 이미 있음 (`temp_password_expires_at` > 지금)
3. 대상이 있을 때 임시 비밀번호를 만들고 PBKDF2로 해시한다.
   - 대상이 없을 때도 해시 계산을 한 번 해서, 응답 시간으로 계정 존재 여부가 드러나지 않게 한다.
4. 트랜잭션 안에서 처리한다.
   1. 회원 행을 `FOR UPDATE`로 잠그고 2번 조건을 다시 확인한다. 조건이 바뀌었으면 204로 끝낸다.
   2. `password_hash`, `temp_password_expires_at = now() + 24시간`, `updated_at`을 바꾼다.
   3. 그 회원의 세션을 모두 지운다.
   4. 메일을 보낸다.
   5. 커밋한다.
5. **임시 비밀번호 규칙:** 12자. 영문 대문자 · 소문자 · 숫자 · 특수문자(`!@#$%^&*`)를 각각 1자 이상 넣는다. 헷갈리는 글자(`0 O o 1 l I`)는 쓰지 않는다. 비밀번호 계약(8~128자, 영문 · 숫자 · 특수문자 포함)을 만족한다.
6. **메일:**
   - 제목: `[이음이] 임시 비밀번호 안내`
   - 본문: 임시 비밀번호, 24시간 뒤 만료(서울 시각), 로그인 후 바로 비밀번호를 바꿔야 한다는 안내
7. **로그인 뒤 동작:** 지금 코드 그대로다. 임시 비밀번호로 로그인하면 `mustChangePassword: true`이고, 다른 API는 403 `PASSWORD_CHANGE_REQUIRED`다. 변경(API-32)이 끝나면 `temp_password_expires_at`이 null이 된다.
8. **요청 제한:** Nginx(분당 3 + 순간 3, 인증 메일과 합산)가 맡는다. BE는 따로 두지 않는다.
9. **받아들이는 한계:** 메일 발송이 실패하면 500을 반환한다. 대상이 없을 때는 발송 자체가 없으므로, 이 경우에만 계정 존재가 드러날 수 있다(SMTP 장애 때만 생김).
10. **FE (`/password/find`):**
    - c96cf85의 `PasswordFindScreen`을 옮긴다.
    - 이메일 · 이름 입력 → 제출 → "입력한 정보와 일치하는 계정이 있으면 임시 비밀번호를 메일로 보냈습니다" → 로그인으로 이동.
    - 429는 "잠시 후 다시 시도해 주세요"로 안내한다.
11. **테스트:**
    - 정상: 발급 → Mailpit API(`http://localhost:8025/api/v1/messages`)에서 임시 비밀번호를 읽음 → 로그인 → `mustChangePassword` 확인
    - 다른 경우: 이름이 다름 · 탈퇴 · 24시간 안에 다시 요청하면 204이고 DB · 메일 변화가 없음
    - 기존 세션이 삭제되는지 확인

**API-34 `POST /api/members/me/withdrawal {password, transfers[], resourceTransfers[]}`** → 204

1. **비밀번호 확인 (트랜잭션 밖):** 틀리면 400 `WITHDRAW_PASSWORD_MISMATCH`. 임시 비밀번호 세션은 필터가 403 `PASSWORD_CHANGE_REQUIRED`로 막는다.
2. **요청 형식 검사:**
   - 같은 `caseId` · `resourceId`가 두 번 나오면 400 `VALIDATION_ERROR`
   - `newManagerMemberId`가 나 자신이면 400 `VALIDATION_ERROR`
3. **실행 중인 AI 대화 정리:** 내 대화 중 실행 중인 것은 먼저 `AgentLifecycle.cancel`로 취소를 요청한다. 대화 삭제(API-38)와 같은 방식이다.
4. **트랜잭션:**
   1. 잠금: 기관 → 회원(나 + 요청에 나온 후임들, member_id 오름차순) → 유일 담당 사례자(case_id 오름차순) → 진행 중 자원(resource_id 오름차순)
   2. 잠금 뒤 유일 담당 사례자 집합과 진행 중 자원 집합을 다시 계산한다.
   3. 요청의 `transfers` · `resourceTransfers` 집합이 이와 정확히 같지 않으면 409 `STATE_CONFLICT`
   4. 후임이 같은 기관 · 활성 회원이 아니면 409 `STATE_CONFLICT`
   5. 적용:
      1. 유일 담당 사례자에 후임을 연결한다 (`case_manager` INSERT, 이미 있으면 그대로)
      2. 내 `case_manager` 연결을 모두 지운다
      3. 진행 중 자원의 `manager_member_id`를 후임으로 바꾼다
      4. `member.withdrawn_at = now()`
      5. 내 `ai_conversation`을 모두 삭제한다 (메시지는 FK CASCADE)
      6. 내 세션을 모두 지운다
   6. 종료 자원의 담당 FK와 상담 최초 기록자 FK는 그대로 둔다.
5. **인계가 필요 없는 경우:** 인계 대상(유일 담당 사례자 · 진행 중 자원)이 둘 다 없으면 빈 배열로 탈퇴할 수 있다. 대상이 있는데 후임 후보가 없으면, 요청 집합이 대상과 맞지 않으므로 409다.
6. 커밋 뒤 응답은 204다. 현재 세션도 지워졌으므로 FE는 로그인 화면으로 간다.
7. **FE (`/my/withdraw`):**
   - c96cf85의 `WithdrawScreen`을 옮기고 진행 중 자원 인계를 추가한다.
   - API-33을 표시하고, 사례자 · 진행 자원마다 후임을 고른다(개별 또는 일괄).
   - 비밀번호 창: 400이면 창 안에 오류를 보인다.
   - 409이면 API-33을 다시 불러오고, 아직 유효한 선택은 남긴다.
   - 성공하면 저장소 · 열린 대화를 비우고 로그인 화면으로 가서 안내를 보인다.
8. **테스트:**
   - 정상: 사례자 · 자원 인계 → 탈퇴 → 로그인 불가 · 대화 삭제 · 세션 삭제
   - 409: 요청 뒤 다른 회원이 사례자 담당을 바꾼 경우
   - 400: 비밀번호가 틀린 경우
9. **문서 (완료 MR):** openapi API-34 `x-db-objects`의 `ai_conversation_turn`을 `ai_message`로 고치고, 위 필드 정의(`resourceCount` 등)를 설명에 적는다.

### 4-4. B1 만료 대화 일일 삭제 (FR-082)

- **실행:** `@EnableScheduling`과 `@Scheduled(cron = "${eumi.batch.conversation-cleanup-cron:0 10 4 * * *}", zone = "Asia/Seoul")`
  - 매일 04:10. 04:30 DB 백업과 겹치지 않게 했다.
  - 서버가 한 대라 실행 잠금(ShedLock 등)은 두지 않는다.
- **대상:** `delete_scheduled_at <= 서울 오늘 날짜`인 대화 (한 번에 500개씩 나눠 처리). 서울 날짜는 Java에서 구해 넘기고 SQL `current_date`는 쓰지 않는다 (운영 DB 시간대가 UTC일 수 있음)
- **대화마다:**
  1. 실행 중이면 `AgentLifecycle.cancel`로 취소를 요청한다.
  2. 짧은 트랜잭션에서 같은 조건으로 다시 확인한 뒤 `DELETE FROM ai_conversation WHERE conversation_id = ? AND delete_scheduled_at <= ?` (메시지는 CASCADE)
     - 1에서 취소를 요청한 대화는 날짜를 다시 보지 않고 `conversation_id`만으로 지운다. fake 취소가 끝 행을 바로 쓰면 트리거가 `delete_scheduled_at`을 오늘 + 3개월로 늘려, 날짜를 다시 보면 취소만 되고 삭제되지 않는다 (11/10 B1 지시문)
  3. 실패한 대화는 건너뛰고 다음 날 다시 시도한다. 이미 지워진 대화는 0행이라 그냥 넘어간다.
- 늦게 도착한 AI 행은 FK로 거부된다. AI 쪽 23503 처리는 이미 있다.
- **기록 ([공통 규칙](../api/공통_응답_및_세션_규칙.md)의 FR-082 문단):**
  - 실행마다 `Conversation cleanup runId=<UUID> today=<YYYY-MM-DD> deleted=N skipped=K failed=M elapsedMs=T`를 남긴다 (시각은 로그 시각, `elapsedMs`는 E7 측정에 쓴다).
  - 실패한 대화마다 `runId`, 대화 ID, 오류 종류만 남긴다. 질문 · 답변 원문은 남기지 않는다.
- **테스트:**
  - 어제 날짜 대화 → 삭제되고 메시지도 사라짐
  - 오늘 날짜 대화 → 삭제 (기한 당일 삭제), 내일 날짜 대화 → 그대로
  - 두 번 실행해도 결과가 같음
  - 스케줄러를 기다리지 않도록 작업 메서드를 직접 호출한다

### 4-5. C4 사례자 수정 409 (API-20 · 23)

- **계약 변경 (BE MR에서 openapi와 함께):**
  - API-20 상세 응답 `CaseDetail`에 `updatedAt`(필수, date-time, 시간대 포함 · 소수 6자리)을 추가한다.
  - API-23 요청을 `CaseUpdateInput` = `CaseInput` + `updatedAt`(필수)으로 바꾼다. 등록(API-22)의 `CaseInput`은 그대로다.
- **BE:**
  1. 수정 트랜잭션에서 사례자 행을 `FOR UPDATE`로 잠근다 (지금과 같음).
  2. `case_record.updated_at`과 요청의 `updatedAt`을 비교한다. Instant로 바꿔 마이크로초까지 같아야 한다. 다르면 409 `STATE_CONFLICT`.
  3. 수정은 지금처럼 `updated_at = now()`로 바꾼다. 담당자만 바꿔도 사례자 행을 갱신하므로 시각이 바뀐다.
- **직렬화:** 소수 6자리를 그대로 보낸다. FE는 받은 문자열을 고치지 않고 그대로 돌려준다.
- **FE:**
  - 수정 폼이 상세의 `updatedAt`을 들고 있다가 함께 보낸다.
  - 409이면 "다른 곳에서 바뀌었어요" 안내 후 상세를 다시 불러온다. 이 공통 처리는 이미 있다.
- **테스트:**
  - 같은 `updatedAt`으로 두 번 수정하면 두 번째가 409
  - 다시 조회한 값으로 수정하면 204

### 4-6. A2 회원가입 (API-04~07, FR-009~013)

   1. 그 이메일의 인증 행을 `FOR UPDATE`로 잠근다.

**API-06 `POST /api/signup/email-verifications/verify {email, code}`** → 200 `{verificationToken}`
1. 인증 행을 `FOR UPDATE`로 잠근다.
   - 행이 없거나 실패가 5회 이상이면 400 `VERIFICATION_INVALID`
   - 만료됐으면 400 `VERIFICATION_EXPIRED`
2. 코드가 다르면 실패 횟수를 +1 하고 400 `VERIFICATION_INVALID`.
   - 횟수 증가는 별도 트랜잭션(`REQUIRES_NEW`)에서 커밋해, 오류 응답 때문에 되돌려지지 않게 한다.
3. 코드가 맞으면 토큰을 만들고 `verified_at` · `proof_hash` · `proof_expires_at = now() + 10분`을 함께 저장한다(CHECK가 셋을 함께 요구). 이미 인증된 행에서 다시 확인하면 새 토큰으로 바꾼다.

**API-07 `POST /api/members`** → 201 `{memberId}`, 자동 로그인 없음
1. 비밀번호를 해시한다 (트랜잭션 밖).
2. 트랜잭션:
   1. 그 이메일의 인증 행을 `FOR UPDATE`로 잠근다.
   2. 행이 없거나, 증명 해시가 다르거나, 기관이 다르면 400 `PROOF_INVALID`. `proof_expires_at`이 지났으면 400 `PROOF_EXPIRED`.
   3. 회원이 이미 있으면 409.
   4. `member`를 INSERT하고 인증 행을 DELETE한 뒤 커밋한다. 이메일 유니크 위반(23505)도 409 `EMAIL_ALREADY_EXISTS`로 바꾼다.
3. 비밀번호 · 직함 · 전화 검사는 API-32 · 31과 같은 규칙이다.

**FE (`/signup`):**
- c96cf85의 `SignupScreen` · `OrgSearchField`를 옮긴다.
- 흐름: 기관 검색 → 이메일(도메인 안내) → 코드 보내기(60초 재발송 대기) → 코드 확인 → 이름 · 비밀번호 · 직함 · 전화 → 가입 → 로그인 화면에서 안내.
- 인증 뒤 기관이나 이메일을 바꾸면 토큰을 버리고 인증 단계로 돌아간다(FR-012).

**시연:** 시연 기관 도메인(`*.eumi.test`)의 새 이메일로 가입하고, Mailpit에서 코드를 확인한다.

**테스트:**
- 정상: 코드 발송 → Mailpit에서 코드 읽기 → 확인 → 가입 → 로그인
- 거절: 도메인 불일치 400, 기존 이메일 409, 60초 안 재발송 429, 실패 5회 뒤 400, 토큰 재사용 400
