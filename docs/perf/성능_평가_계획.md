# 서비스 성능 평가 계획 (11/9)

- **상태:** 끝남 (11/13). 1회차(11/10) · 2회차(11/13)를 측정했다. 결과는 [성능_평가_결과.md](성능_평가_결과.md) · [성능_평가_결과_2회차.md](성능_평가_결과_2회차.md), 두 회차 비교는 [성능_평가_종합_설명.md](성능_평가_종합_설명.md)에 있고, 목표 · 결과는 기능명세 NFR-PER-01에 반영했다(11/15). 아래 본문은 11/9 계획 그대로이고 실제 진행과 다른 점은 7절 끝에 적었다.
- **목적:** 기능명세 NFR-PER-01(응답 성능의 인수 목표)의 목표값을 정하고, 측정 근거로 충족 여부와 개선 대상을 판단한다.
- **원칙:**
  - 사용자가 실제로 기다리는 시간을 먼저 잰다. 그다음 그 시간을 구간으로 나눈다: 외부(Tableau · LLM), 자체 API, DB, 화면 처리, 연동(저장 → 표시).
  - 운영 서버에서 잰다. 운영 DB에는 시연용 가짜 데이터만 있다. 시험 중에 만든 AI 대화 등은 시험이 끝나면 지운다.
  - 목표를 이미 충족하면, 그 조건과 측정 근거를 남기고 "개선 불필요"로 결론 낸다.

## 1. 평가 대상

사용자가 자주 쓰거나 기다림이 긴 흐름을 고른다.

| ID | 흐름 | 평가할 상황 | 확인할 내용 |
|---|---|---|---|
| E1 | 로그인 · 첫 화면 | 로그인 → 메인(위험 탐색) 진입 | 로그인 응답, 첫 화면 표시까지 |
| E2 | 위험 탐색 (Tableau 4개) | 최초 접속, 지역 · 기간 · 지표 변경 | 지도 · 차트를 실제로 보고 조작할 수 있을 때까지. 외부 Tableau / 자체 API / 화면 처리 구분 |
| E3 | 읍면동 상세 | 동 선택 → 요약 · 보고서 · 디테일 대시보드 | 요약 · 보고서(자체 API)와 디테일 대시보드(Tableau)를 따로 |
| E4 | 사례자 · 복지자원 | 목록 검색 · 정렬 · 페이지, 상세, 등록 · 수정 | 화면 표시와 저장 응답 |
| E5 | AI 패널 | 질문 제출 → 진행 안내 → 최종 답변 | 첫 진행 안내까지 · 최종 답변까지. **AI 처리 시간과 DB 저장 → 화면 표시 시간을 분리** |
| E6 | 인사이트 보고서 생성 | 월 분석 완료(INT-04) → 동마다 생성 · 저장 → INT-08 | 한 달(47개 동) 전체 시간, 동별 생성 시간, 실패율 (AI-b 배포 뒤) |
| E7 | 배치 | 만료 대화 일일 삭제(FR-082), 월 분석 파이프라인 | 실행 시간, 실행 중 화면 응답에 주는 영향 (구현 · 운영 반영 뒤) |

- 위 표의 E2와 E5가 처음 예시로 받은 두 흐름이다.
- E5는 지금 fake 모드라 AI 처리 시간이 BE의 가짜 단계(1초 간격 3단계 + 완료)다. 그래서 기준선에서는 "저장 → 화면 표시" 구간과 동시 이용 영향을 재고, 실제 AI 처리 시간은 http 전환(AI-a 배포 뒤) 뒤에 잰다.
- E5 실측 · E6은 GMS 호출 비용이 든다. 동시 · 부하 단계의 AI 사용자 수와 반복 수는 김민준과 사용량 한도를 확인한 뒤 정한다.

## 3. 허용 대기시간 (목표, 팀 합의 필요)

| 구분 | 지표 | 목표 (중앙값 / p95) |
|---|---|---|
| 자체 API | 응답 시간 (서버 처리) | 단독 ≤ 100ms / ≤ 300ms. 동시 20명 ≤ 200ms / ≤ 500ms |
| API 화면 (E1 · E4, E3 요약 · 보고서) | 화면 표시 | ≤ 1초 / ≤ 2초 |
| 저장 (E4) | 버튼 → 완료 안내 | ≤ 1초 / ≤ 2초 |
| Tableau 화면 (E2, E3 디테일) | 최초 사용 가능 | ≤ 5초 / ≤ 8초 |
| | 조건 변경 후 다시 사용 가능 | ≤ 3초 / ≤ 5초 |
| AI (E5) | 질문 → 첫 진행 안내 | ≤ 2초 / ≤ 3초 |
| | DB 저장 → 화면 표시 (연동 지연) | ≤ 1.0초 / ≤ 1.5초 (1초 조회 기준) |
| | 최종 답변 | AI 처리 시간 + 연동 지연. AI 처리 목표는 AI 담당과 정한다 (실행 한도 300초) |

- Tableau는 외부 서비스라 목표를 넉넉히 두었다.

## 4. 측정 방법

| 측정 | 방법 | 도구 (`infra/perf/`, 다음 인프라 MR) |
|---|---|---|
| 사용자 대기시간 (E1~E4) | 브라우저 자동화로 상황마다 20회 반복. 화면 구간을 시각으로 남긴다: 페이지 진입, 자체 API 응답, Tableau 시작 · 사용 가능(`.tableau-embed`의 `data-chart-state`가 `ready`), 오류 | Playwright 스크립트 (김민재 PC) |
| 구간 분리 (E2 · E3) | 자체 API = `/api` 요청 시간. 외부 Tableau = `public.tableau.com` 요청과 시작 → 사용 가능 시간. 화면 처리 = 나머지 (스크립트 해석 · 그리기) | 같은 스크립트 (요청 · 응답 시각 기록) |
| 동시 이용 부하 | 탐색 사용자(지역 · 월 · 동 요약 · 보고서 API를 생각 시간 3~8초 두고 반복)와 AI 사용자(질문 → 1초 조회 → 끝 행)를 동시에 돌린다. 단독 · 동시 · 부하 세 단계 | k6 (김민재 PC, Docker) |
| AI 구간 분리 (E5) | AI 처리 = 진행 · 완료 행의 `createdAt` − 질문 행의 `createdAt` (서버 시계). 연동 지연 = 화면에서 그 행을 처음 받은 시각 − 행 저장 시각. 질문 제출 시각으로 시계 차이를 맞춘다 | k6 AI 시나리오 |
| API 서버 처리 시간 | Nginx 접근 기록에 `$request_time` · `$upstream_response_time`을 남겨 엔드포인트별 중앙값 · p95를 구한다 | Nginx 기록 형식 추가 + 요약 스크립트 |
| DB 처리 시간 | 화면 API가 쓰는 SQL을 `EXPLAIN (ANALYZE)`로 30회 재서 중앙값 · p95. 운영 규모와 확장 규모를 함께 잰다 | SQL 파일 |
| 서버 자원 | 시험 동안 2초마다 컨테이너별 CPU · 메모리(`docker stats`), 호스트 CPU · 부하, DB 활성 연결 수를 기록 | 서버 기록 스크립트 |

## 5. 결과 정리 형식

평가 대상마다 아래 순서로 정리한다.

1. **평가 조건:** 데이터 · 사용자 수 · 기기 · 네트워크 · 반복 수
2. **현재 성능:** 단독 / 동시 / 부하마다 중앙값 · p95 · 오류 · 시간 초과 비율. 구간별 시간(외부 · API · DB · 화면 · 연동). 서버 자원
3. **주요 지연 원인:** 가장 긴 구간과 그 근거 (측정값)
4. **개선 필요 여부:** 목표(3절)와 비교한 결론. 충족이면 "개선 불필요"와 근거

개선한 경우에는 같은 조건으로 다시 재고 아래를 함께 적는다.
- 기능 · 결과가 그대로인지 확인한 방법
- 대기시간 · 오류율 변화: 개선 전 → 개선 후, 개선율(%), 실제 단축 시간

## 6. 이미 잰 것: DB 조회 (11/9, 확장 규모 시험)

1. **평가 조건:** PostgreSQL 16, 운영과 같은 스키마(V1~V20261106_01). 시연 규모(결과 235행)와 확장 규모(결과 84,000행 · 동 3,547개)에서 화면 API의 SQL을 잼
2. **현재 성능:**

   | 쿼리 (API) | 시연 규모 | 확장 규모 |
   |---|---|---|
   | 적재 월 목록 (API-10) | 0.4ms | 중앙값 9.1ms · p95 11.0ms |
   | 동 요약 (API-11) | 0.1ms | 0.07ms (PK 인덱스) |
   | 보고서 (API-12) | 0.03ms | 0.03ms (PK 인덱스) |
   | 동 목록 (API-41) · 시군구 목록 (API-40) | 0.04ms | 0.4~0.6ms |

3. **주요 지연 원인:** API-10의 `WHERE left(adm_cd10, 5) = ?`가 인덱스를 쓰지 못해 결과 표 전체를 읽는다(Seq Scan). 위험 탐색 화면은 진입 · 조건 변경 때마다 이 API를 1~2번 부른다.
4. **개선 필요 여부:**
   - 시연 규모에서는 0.4ms라 개선이 필요 없다.
   - 확장 규모에서도 목표(서버 처리 p95 300ms) 안이다.
   - 전국 단위로 넓히거나 동시 사용자가 많아지면, 표현식 인덱스 `(left(adm_cd10, 5), period_start)`를 새 V 파일로 추가하는 것을 후보로 둔다. 같은 조건에서 시험하면 9.1ms → 0.14ms(약 98% 감소)였다.

**실제 진행 (11/15 정리)**

- 측정 도구는 저장소(`infra/perf/`)에 넣지 않고 김민재 PC에 두었다 ([README.md](README.md)).
- Nginx 시간 기록 형식은 11/15 문서 MR에 넣었고 서버 반영은 그 뒤다. 그래서 1 · 2회차의 API 시간은 k6가 잰 값(네트워크 포함)이다.
- 기준선은 11/10(AI fake), 실제 AI 측정은 11/13에 했다. 실제 AI는 단독과 동시 20명 단계(AI 질문 13건)까지만 쟀고, 실제 AI 부하 50명은 GMS 크레딧 때문에 하지 않았다.
- E6 보고서는 시연 월 전체가 아니라 역삼1동 2025-12 한 건만 임시 ai로 만들어 쟀다. 운영에서는 보고서 생성 요청을 서버에서만 보낸다.
- E7은 만료 대화 삭제 실행 시간만 쟀다. 월 분석 파이프라인은 서버 사정으로 돌리지 않았다.

- 시험 계정은 시연 계정을 쓴다. 비밀번호는 실행하는 사람이 환경변수로만 넣고, 스크립트 · 결과 파일에 남기지 않는다.
- 로그인 요청 제한(분당 10)이 있어, 부하 시험은 계정마다 처음에 한 번만 로그인하고 세션을 다시 쓴다.
- 시험 시간은 팀에 미리 알린다. 운영 화면을 쓰는 시간을 피한다.
