# 2026년 11월 1일 G1 BE 작업 재개 안내

작성일: 2026-10-31. 오늘은 구현한 B0~B4와 문서를 작업 브랜치에 commit·push해 보관하고, 최신 develop 병합과 운영 설정 보완은 내일 이어서 진행하기로 사용자가 정했다. 이 문서는 원격 저장소에서도 사람과 다음 Agent가 재개할 수 있도록 필요한 상태와 검토 사항을 모은다.

## 먼저 확인할 사항

- 작업 브랜치는 `feat/be-common-foundation`이다.
- 작성 시점 HEAD와 로컬 develop은 `99e63564788f97fadc1327a4fe237ddf2e229125`다. B0~B4 코드·문서는 아직 미커밋 상태였다. 이 문서 작성 후 사용자가 직접 commit·push할 예정이므로, 재개할 때 실제 상태를 다시 조회한다.
- 사용자가 직접 fetch한 origin/develop은 `2ea2a284e609b82f6df8e569b5914fd305df862c`다. 작업 브랜치에 아직 병합하지 않았다. 내일 원격에 더 쌓인 변경이 있을 수 있다.
- 당시 origin/master는 `bcbcc724fd243031996b81fc2ca5a798371eba96`였다. 이 작업의 통합 대상은 develop이다.
- Agent는 clone·fetch·pull·commit·push·merge를 대신 실행하지 않는다. 사용자가 Git Bash에서 직접 실행한다.
- 작업 브랜치 push와 develop 병합·운영 배포 준비 완료를 구분한다. 오늘은 최신 develop 병합, infra 보완, master 병합, 서버 배포를 진행하지 않는다.

## 우선 검토할 운영 환경변수 연결

현재 backend의 application-prod.yml은 SMTP·발신 주소·해시 키를 필수로 받는다. 그런데 2ea2a28의 운영 Compose는 backend environment에 DB 설정·UPLOAD_DIR만 전달한다. env_file도 사용하지 않는다.

따라서 서버 `/srv/eumi/.env.config`에 값을 넣는 것만으로는 backend 컨테이너에 전달되지 않는다. 현재 조합으로 prod 애플리케이션을 배포하면 필수 설정 누락으로 기동 실패가 예상된다.

검토할 파일은 다음 두 개다. 최신 develop 병합 후 작업 트리에 들어온 내용을 다시 확인한다.

- `infra/deploy/docker-compose.prod.yml`: backend environment에 필요한 변수 전달.
- `infra/deploy/.env.config.example`: 키 이름과 용도 추가. 실제 운영 비밀값은 기록하지 않음.

| 변수 | 현재 운영 Mailpit 구성에서 검토할 값 |
|---|---|
| EUMI_AUTH_HASH_KEY | 서버에만 보관할 운영용 비밀값 |
| EUMI_MAIL_FROM | 사용할 발신 주소 |
| SMTP_HOST | mailpit |
| SMTP_PORT | 1025 |
| SMTP_AUTH | false |
| SMTP_STARTTLS_ENABLED | false |
| SMTP_USERNAME | 인증 미사용 시 빈값 |
| SMTP_PASSWORD | 인증 미사용 시 빈값 |

컨테이너 사이 SMTP 주소는 `mailpit:1025`다. localhost:1025는 호스트에서 실행하는 로컬 BE 설정과 구분한다.

infra 수정은 처음 승인된 backend 범위 밖이므로, 내일 변경 이유·파일·범위를 사용자에게 확인받고 진행한다. 오늘 이 보완은 승인되거나 실행된 것으로 취급하지 않는다. 실제 서버 설정 파일도 열거나 변경하지 않았다.

## 최신 협업 규칙과 문서 정합성

최신 CONTRIBUTING은 운영 비밀값을 서버 `/srv/eumi/.env.config`와 인프라 담당 개인 보관 사본으로 관리하도록 정리했다. Jenkins credentials에 남는 항목과 구분하고, backend 실행·인계 문서가 새 운영 전달 방식과 맞는지 확인한다.

채팅을 그대로 저장한 코드 해설은 당시 설명의 기록이다. 과거 기준 커밋·파일 수를 현재 상태라고 단정하지 않는다. 최신 실행 상태는 이 재개 문서와 실제 Git·코드, 갱신된 검증 기록으로 판단한다.

## 내일 진행 순서

1. 사용자 push 결과와 실제 작업 브랜치·커밋·변경 파일·upstream을 읽기 전용으로 확인한다. 오늘 commit·push가 성공했다고 미리 가정하지 않는다.
2. 사용자가 최신 원격 참조를 갱신한 뒤, 작업 브랜치의 기준부터 origin/develop까지 변경을 다시 비교한다. 오늘 확인한 2ea2a28을 내일의 최신 상태라고 가정하지 않는다.
3. 미커밋 변경을 보존한 상태에서 사용자가 로컬 develop을 fast-forward하고 작업 브랜치에 develop을 merge한다. 충돌이 있으면 파일별로 검토한다.
4. 운영 환경변수 연결이 최신 develop에서 이미 보완됐는지 다시 확인한다. 남아 있으면 위 infra 두 파일과 관련 문서의 추가 수정 범위를 승인받는다.
5. 승인된 수정은 별도 커밋으로 구분할 수 있도록 구현·기록한다. 실제 비밀값은 Git·문서·로그에 넣지 않는다.
6. test·integrationTest·bootJar와 실제 jar HTTP 검사를 재실행한다. 추가로 가짜 설정을 이용한 운영 Compose 해석·변수 전달·prod 기동을 검증한다. 설정 검사에서 비밀값이 펼쳐지는 config 출력을 남기지 않는다.
7. fixture 검사, 실제 로컬 통합, prod 설정 fixture, 실제 서버·브라우저 검증의 결과를 구분해서 문서에 남긴다.
8. 사용자가 보완 커밋을 push하고 develop 대상 MR을 진행한다. infra 변경이 포함되면 협업 규칙의 리뷰어 승인 후 병합 조건을 적용한다.

운영 연결 검토 후의 별도 후속 범위는 API-39~42, FE F1~F3, A1~A3와 암호 인코더·seed OPEN-04다. 승인 없이 해당 기능까지 확대하지 않는다.

## 검사 실행 참고

Git Bash에서도 backend 폴더에서 Wrapper를 실행할 수 있다. JDK 21과 Docker의 로컬 PostgreSQL·Mailpit이 준비돼 있어야 한다.

```bash
cd /c/Users/rapal/Desktop/자율PJT/eumi/backend
./gradlew test integrationTest bootJar --console=plain
```

이번 PC의 JDK 압축본은 `C:\Users\rapal\Desktop\자율PJT\.tools\eumi-jdk21\jdk-21.0.13+9`에 있다. Git Bash에서 현재 세션에만 지정하려면 다음을 사용할 수 있다.

```bash
export JAVA_HOME='C:/Users/rapal/Desktop/자율PJT/.tools/eumi-jdk21/jdk-21.0.13+9'
export PATH="$(cygpath -u "$JAVA_HOME")/bin:$PATH"
export GRADLE_USER_HOME='C:/Users/rapal/Desktop/자율PJT/.tools/gradle-home'
java -version
```

다른 환경은 자신의 JDK 21 경로를 사용한다. Git은 사용자가 실행하며, 위 검증 명령을 문서에 적었다는 사실만으로 내일 재검증을 통과한 것으로 표시하지 않는다.
