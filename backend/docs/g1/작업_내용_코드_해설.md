**2. 전체 요청이 처리되는 구조**

현재 BE 요청은 대략 다음 흐름으로 처리됩니다.

```text
HTTP 요청
  ↓
RequestIdFilter
  요청 UUID 생성, 응답 헤더와 로깅 컨텍스트 설정
  ↓
Spring Session / Spring Security
  SESSION 쿠키를 이용한 세션·인증 복원
  ↓
CSRF 검사
  상태 변경 요청의 쿠키·헤더 검증
  ↓
제한 세션 검사
  비밀번호 변경이 필요한 사용자의 업무 접근 제한
  ↓
경로별 인증·인가 검사
  공개 경로인지, 인증이 필요한 경로인지 확인
  ↓
Controller
  정상 DTO / Health / 204 처리
```

오류는 발생 위치에 따라 처리 경로가 다릅니다.

```text
Security 필터에서 발생한 오류
  → AuthenticationEntryPoint / AccessDeniedHandler
  → ApiErrorWriter
  → 공통 오류 JSON

Controller·Service에서 발생한 오류
  → GlobalExceptionHandler
  → 공통 오류 JSON

Servlet 오류 처리로 넘어온 오류
  → ApiErrorController
  → 공통 오류 JSON
```

이렇게 나눈 이유는 **컨트롤러의 예외 처리기만으로 Security 필터에서 발생하는 오류까지 모두 처리할 수는 없기 때문**입니다. 발생 위치가 달라도 클라이언트가 받는 JSON 구조는 같게 만들었습니다.

**6. B1 — requestId를 생성하고 연결한 부분**

확인할 파일은 [RequestIdFilter.java](C:/Users/rapal/Desktop/자율PJT/eumi/backend/src/main/java/com/eumi/backend/common/web/RequestIdFilter.java:17)입니다.

읽을 메서드는 다음 두 개입니다.

- `requestId()`: 해당 요청의 UUID를 만들거나 기존 값을 가져옵니다.
- `doFilterInternal()`: 응답 헤더·MDC를 설정하고 다음 필터로 넘깁니다.

처리 순서는 다음과 같습니다.

1. 요청 속성에 이미 ID가 있는지 확인합니다.
2. 없으면 서버가 UUID를 생성합니다.
3. 요청 속성에 보관합니다.
4. `X-Request-Id` 응답 헤더에 넣습니다.
5. 응답 본문의 `meta.requestId`도 같은 값을 사용합니다.
6. 요청이 끝나면 MDC에서 값을 제거합니다.

중심 코드는 다음입니다.

```java
String id = requestId(request);
response.setHeader(HEADER, id);
response.setHeader(HttpHeaders.CACHE_CONTROL, "no-store");
MDC.put("requestId", id);
```

그리고 `finally`에서 정리합니다.

```java
MDC.remove("requestId");
```

클라이언트가 보낸 `X-Request-Id`를 그대로 채택하지 않고 서버가 생성합니다.

현재는 이 필터에서 BE 응답에 공통으로 `Cache-Control: no-store`를 붙입니다. 따라서 Health도 본문은 기존 형태를 유지하지만 해당 헤더는 붙습니다.

MDC는 요청 ID를 로깅 컨텍스트에 보관하는 기능입니다. **모든 로그 줄에 requestId를 자동 출력하도록 전체 로그 패턴까지 변경한 것은 아닙니다.** 일반 예외 로그에서는 requestId를 명시적으로 출력하도록 구현했습니다.

4. 새 SecurityContext를 만듭니다.
5. 현재 요청의 SecurityContextHolder에 설정합니다.
6. SecurityContextRepository에 명시적으로 저장합니다.

```java
strategy.onAuthentication(authentication, request, response);

var context = SecurityContextHolder.createEmptyContext();

SecurityContextHolder.setContext(context);

repository.saveContext(context, request, response);
```

**12. B3 — CSRF 준비 API와 검증을 구현한 부분**

**쿠키 설정**

[CSRF 저장소 설정](C:/Users/rapal/Desktop/자율PJT/eumi/backend/src/main/java/com/eumi/backend/config/SecurityConfig.java:30)의 `csrfTokenRepository()`를 보면 됩니다.

```java
var repository = CookieCsrfTokenRepository.withHttpOnlyFalse();

repository.setCookieCustomizer(cookie ->
        cookie.path("/")
              .httpOnly(false)
              .sameSite("Lax")
              .secure(secure));
```

인증 쿠키와 CSRF 쿠키의 용도를 구분해야 합니다.

| 구분 | SESSION | XSRF-TOKEN |
|---|---|---|
| 목적 | 서버 로그인 세션 식별 | 상태 변경 요청의 CSRF 검증 |
| Path | `/api` | `/` |
| HttpOnly | true | false |
| FE에서 직접 읽기 | 하지 않음 | 헤더에 넣기 위해 읽음 |
| 별도 전달 헤더 | 없음 | `X-XSRF-TOKEN` |

CSRF 쿠키의 Path를 `/`로 둔 이유는 FE 화면 경로에서도 읽을 수 있어야 하기 때문입니다.

**준비 API**

[CsrfController.java](C:/Users/rapal/Desktop/자율PJT/eumi/backend/src/main/java/com/eumi/backend/auth/csrf/CsrfController.java:11)의 코드는 짧습니다.

```java
@GetMapping("/auth/csrf")
public ResponseEntity<Void> prepare(CsrfToken token) {
    token.getToken();
    return ResponseEntity.noContent()
            .cacheControl(CacheControl.noStore())
            .build();
}
```

`token.getToken()`이 중요한 부분입니다. 지연된 토큰을 실제로 준비하도록 접근하고, 응답 본문은 만들지 않습니다.

외부 주소는 context-path가 붙은 다음 주소입니다.

```text
GET /api/auth/csrf
```

**SPA 처리**

보안 설정의 다음 코드에서 raw 쿠키 값과 XOR 토큰 처리를 맞췄습니다.

```java
.csrf(csrf -> csrf.spa().csrfTokenRepository(csrfRepository))
```

계획 단계에서는 별도 SPA 처리기 파일도 제안했지만, 실제 버전에서 제공하는 내장 기능을 확인해 사용했습니다.

FE가 연결할 흐름은 다음과 같습니다.

1. CSRF 준비 API를 호출합니다.
2. `XSRF-TOKEN` 쿠키를 읽습니다.
3. 변경 요청의 `X-XSRF-TOKEN` 헤더에 원문 값을 넣습니다.
4. 로그인·로그아웃·암호 변경 후 다시 준비합니다.

현재 FE 코드를 이 흐름으로 변경한 것은 아닙니다.

공개 로그인·가입 요청도 CSRF를 검사합니다. 따라서 인증이 필요 없는 API라도 CSRF 헤더가 없으면 403이 발생합니다. 보호된 변경 요청에서도 CSRF 검사가 인증 검사보다 먼저 거절할 수 있으므로 모든 미인증 요청이 항상 401로 끝나는 것은 아닙니다.

유효한 쿠키가 이미 있으면 준비 API를 다시 호출해도 기존 토큰을 유지할 수 있습니다. 이때 `Set-Cookie`가 다시 나오지 않는 것을 실패로 처리하지 않도록 검사를 구성했습니다.


다른 로컬 포트라면 다음처럼 지정합니다.

```powershell
.\scripts\Verify-CommonHttp.ps1 -BaseUrl http://localhost:8081/api
```

전체 Gradle 검사는 다음 명령입니다.


앞서 실행한 최종 결과는 fixture 15개·통합 4개·실제 jar HTTP 5개 통과와 `bootJar` 성공입니다.
