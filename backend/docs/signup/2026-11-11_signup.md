## 2. 계약·DTO·오류와 승인된 계획 차이

계약 형식과 달라진 점은 없다. 루트 `docs/`·OpenAPI·DB 마이그레이션·FE·Nginx·SecurityConfig는 고치지 않았다. 다음 네 곳은 사용자 지시가 계획 4-6보다 우선한다.

1. API-06 실패 횟수는 REQUIRES_NEW를 쓰지 않는다. 이메일 인증 행을 잠근 같은 트랜잭션에서 증가시키고 결과값을 반환해 커밋한 뒤, 트랜잭션 밖에서 VERIFICATION_INVALID 400을 던진다. 자기 행 잠금을 다른 트랜잭션이 기다리는 문제를 피한다.
2. API-07은 잠금 없는 증명·기관·인증 여부·만료·회원 중복 사전 확인 후에만 PBKDF2를 수행한다. 무작위 토큰으로 비밀번호 해시 CPU를 쓰지 못하게 한다. 실제 가입 트랜잭션에서는 모두 다시 확인한다.
3. API-05 첫 요청은 잠글 인증 행이 없을 수 있다. 동시 INSERT의 유니크 위반은 트랜잭션 롤백 후 RATE_LIMITED 429로 반환한다. 실패한 요청은 메일을 보내지 않는다.
4. API-04 keyword 누락·공백은 VALIDATION_ERROR 400이다. 현재 OpenAPI의 선택 입력·빈 기본값에 대한 설명 보완은 병합 뒤 인프라 문서 MR에서 한다.

### 형식과 저장

- 기관 검색은 trim한 keyword가 1~200 코드 포인트여야 한다. `position`으로 문자 그대로 검색하고 org_name·org_id 순으로 최대 20개를 반환한다. 관할명은 MyRepository와 같은 지역 뷰 조인을 사용한다.
- 이메일은 trim·Locale.ROOT 소문자로 정규화한다. 마지막 @ 뒤 도메인이 기관 official_domain과 완전히 같아야 하며 하위 도메인은 거절한다. DB에는 조회·중복 확인용 정규화 식별자만 저장하고 원문 입력을 기록하지 않는다.
- 문자열은 기존 TempPasswordRequest.StringValue로 JSON 문자열만 받는다. orgId는 JSON 정수만 받으며 1~9007199254740991이다. 모르는 필드는 거절하고 요청·증명 응답의 toString은 redacted다.
- 이름은 trim 후 1~100 코드 포인트다. 비밀번호는 trim 없이 기존 8~128자·영문·숫자·특수문자 규칙과 기존 PasswordEncoder를 쓴다. 직함은 trim 후 비면 null, 최대 100 코드 포인트다. 전화는 null 또는 계약 패턴이며 빈 문자열은 400이다.
- 인증 코드 해시는 UTF-8 HMAC-SHA256의 `code:` + 정규화 이메일 + `:` + 코드이고, 증명 해시는 `proof:` + 토큰이다. AuthHashProperties.hashKey를 사용하고 결과 32바이트를 BYTEA에 넣는다. Mac은 호출마다 만들고 비교는 MessageDigest.isEqual로 한다.
- 코드는 SecureRandom 숫자 6자리, 증명은 SecureRandom 32바이트의 base64url 무패딩 43자다. 재발송·재확인 때 직전 값과 우연히 같으면 다시 생성한다.
- 코드 10분·증명 10분·재발송 60초·실패 5회는 SignupService 상수 한 곳에 둔다. 이메일 인증의 네 시각과 회원 생성·수정 시각을 Clock으로 직접 계산해 저장한다. 만료는 expiresAt <= 현재 시각일 때 거절한다.
- 응답 expiresAt은 소수 없이 초 단위의 서울 오프셋 ISO 8601이다. DB TIMESTAMPTZ의 순간값은 유지한다. 코드·토큰 원문은 DB에 저장하지 않고, 비밀번호는 PBKDF2 해시로만 저장한다.

### 추가 오류 코드

| 코드 | 상태 | 상황 |
|---|---|---|
| EMAIL_DOMAIN_MISMATCH | 400 | 기관 공식 도메인과 불일치, 하위 도메인 포함 |
| EMAIL_ALREADY_EXISTS | 409 | 탈퇴 포함 이미 사용한 이메일, 가입 INSERT 유니크 위반 |
| VERIFICATION_INVALID | 400 | 인증 행 없음·실패 5회 이상·코드 불일치 |
| VERIFICATION_EXPIRED | 400 | 코드 만료 |
| PROOF_INVALID | 400 | 증명 행 없음·미인증·이메일/기관/해시 불일치·이미 소비한 토큰 |
| PROOF_EXPIRED | 400 | 가입 증명 만료 |

## 3. 권한·트랜잭션·잠금

기존 SecurityConfig에서 네 경로가 공개이며 POST 세 곳에는 CSRF가 적용된다. 가입은 세션 인증이나 자동 로그인을 하지 않고, 가입 응답에 SESSION Set-Cookie가 없다.

- API-05: 기관·도메인·회원 사전 확인 → 인증 행 FOR UPDATE → 회원 중복 재확인 → 60초 검사 → 기존 인증 행 DELETE·새 INSERT → MailService 발송 → 커밋. 메일 실패면 기존 코드·증명까지 원상태로 롤백한다.
- API-06: 인증 행 FOR UPDATE → 행/실패 한도 → 코드 만료 → 해시 비교. 오답 횟수도 커밋한다. 성공 시 verified_at·proof_hash·proof_expires_at 세 칸을 함께 갱신한다. 같은 코드 재확인은 새 토큰을 발급해 옛 토큰을 무효로 한다.
- API-07: 잠금 없는 증명·중복 사전 확인 → JDBC 연결 반환 → PBKDF2 → 인증 행 FOR UPDATE → 증명·만료·중복 재확인 → 회원 INSERT·인증 행 DELETE → 커밋. 같은 토큰 동시 요청은 하나만 성공한다.

서비스에 바깥 @Transactional을 두지 않았다. PBKDF2가 호출될 때 실제 트랜잭션과 DataSource 연결 자원이 모두 없는지 검사했다. 메일은 기존 SMTP를 통한 Mailpit 접수이며 DB 커밋과 최종 배달의 원자성을 보장하지 않는다. 메일 접수 후 DB 커밋 실패로 쓸 수 없는 코드가 배달될 수 있다는 계획 3-3의 한계는 유지한다.

IP 요청 제한은 기존 Nginx가 담당한다. BE에는 별도 IP 제한기나 테이블을 추가하지 않았다. 이메일별 60초 재발송 제한과 코드 실패 횟수는 기존 인증 행으로 관리한다.

## 5. FE 인계·남은 일

- 기관 검색은 비로그인이며 검색어 누락·공백은 400이다. 최대 20개 목록의 orgId·orgName·sidoName·sigunguName·officialDomain을 사용한다. `%`, `_`, 역슬래시도 일반 문자로 비교한다.
- POST 전에 GET /api/auth/csrf로 쿠키를 준비하고 raw XSRF-TOKEN 값을 X-XSRF-TOKEN 헤더로 전달한다. SESSION 로그인 없이 사용할 수 있다.
- API-05의 expiresAt은 서울 오프셋·초 단위 ISO 8601이다. 60초 안 재발송은 429이며 새 메일을 보내지 않는다. 성공한 재발송은 옛 코드와 증명을 폐기한다.
- 코드 실패는 최대 5회다. 그 뒤에는 맞는 코드도 VERIFICATION_INVALID이므로 재발송 대기 후 코드를 다시 받아야 한다. 실패 횟수는 400이어도 DB에 남는다.
- 코드 재확인은 토큰을 바꾼다. verificationToken은 10분 동안 유효하고 가입에서 한 번만 소비한다. 기관·이메일이 바뀌면 토큰을 버리고 인증을 다시 진행한다.
- 가입 뒤 자동 로그인은 없다. 201 memberId를 받은 뒤 로그인 화면으로 안내한다. 직함을 비우면 null, 전화 빈 입력은 FE에서 null로 보낸다. 비밀번호는 공백을 포함해 원문을 보낸다.
- 400 fieldErrors 필드 이름은 keyword, orgId, email, code, verificationToken, name, password, title, phone이다. unknown 필드·JSON 타입 오류·필수 JSON 키 누락 등 파싱 오류는 INVALID_JSON이며 필드 목록이 비어 있을 수 있다. 위 오류 코드 표로 재요청·재인증·중복 안내를 구분한다.
