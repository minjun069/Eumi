## 2. 남긴 범위·삭제한 코드·계약 차이

| 남긴 항목 | 정확한 인식 범위 | 치환값 |
|---|---|---|
| 이름 | 독립된 표지 `이름`·`성명`·`성함`·`사례자명`·`회원명` | `[이름]` |
| 생년월일 | 독립된 표지 `생년월일` | `[생년월일]` |
| 이메일 | 기존 ASCII 이메일 패턴 | `[이메일]` |
| 휴대전화 | 회원가입·마이페이지 스키마의 `01[016789]-숫자3~4자리-숫자4자리` | `[전화번호]` |

이름·생년월일 표지 뒤의 `:`·`：`·`=`와 가로 공백을 허용한다. 값은 세미콜론·줄바꿈·입력 끝까지 통째로 가리며 앞뒤 구분자는 보존한다. 값이 공백뿐이면 그대로 둔다. 표지 앞에 글자·숫자·밑줄이 붙은 다른 단어는 표지로 처리하지 않는다.

이름 데이터·성씨를 DB에서 조회하지 않고, 단어 수·호칭·이름 뒤 질문 어휘를 추측하지 않는다. 구분자 없이 같은 줄에 질문을 붙이면 그 질문도 가려진다. 표지 없는 이름·날짜는 자동 인식하지 않는다. 생년월일이 테이블에 있다고 모든 날짜를 가리는 방식은 사용하지 않는다.

삭제한 코드: RESIDENT_NUMBER, ADDRESS, ACCOUNT·ACCOUNT_VALUE, 복합 표지 생성, NAME_WORD·NAME_TAIL·HONORIFIC·QUESTION_WORD·QUESTION_BOUNDARY, 이름 단어 수·조사·문장부호 기반 값 종료 추론과 범용 전화번호 분기. QuestionMasker는 104줄에서 26줄로 줄었다.

070·지역번호·+82·구분자 없는 휴대전화 등 회원 API 표준 밖의 표기는 이번 지원 범위가 아니다. 나이·성별·지역명·행정동 코드·관리번호·일반 분석 날짜를 추가로 가리지 않는다. 비밀번호·인증 코드·세션·쿠키의 기존 로깅 차단은 유지한다.

계약과 달라진 점: 마스킹 범위·값 경계 변경이 있다. DTO·요청/응답 필드·상태 코드·오류 코드·DB 구조는 변경하지 않았다. 사용자 최신 삭제 지시로 BE부터 반영했으며 docs/api는 담당 범위에 따라 직접 수정하지 않고 아래에 반영할 문구를 인계한다.

## 3. 권한·잠금·저장 경로

소유권·임시 암호 제한·트랜잭션·writer 잠금·끝 행 경합·복구·취소·진단 정책은 그대로다. API-03은 처리 결과만 DB에 저장한다. 별도 원문 사본은 저장하지 않지만 지원 범위 밖의 내용은 처리 결과에 남아 DB·조회 응답·AI에 제공될 수 있다. 완전한 비식별화를 보장하지 않는다.

질문 본문은 처리 전후 모두 로그에 추가하지 않았다. AI 호출은 기존처럼 대화 ID·질문 ID만 전달한다. 이번 범위 변경은 신규 질문에 적용하며 기존 저장 메시지를 재처리하거나 수정하지 않는다.

## 4. 검사

기존의 주민번호·금융번호·상세주소·자연어 추론을 지원하는 검사는 새 범위에 맞게 교체했다. 회원 설정 검사 8개와 세션·권한·AI 통신·복구·취소 검사는 유지한다.

`gradlew.bat test --tests '*AgentConfigurationTests' --console=plain`:

- 수정 전 새 범위 검사 27개 중 8개 실패.
- 수정 후 27개 모두 통과: 설정 8개, 지원 범위와 제외 범위 19개.
- 제외 범위는 합성 입력으로 검증하며, 실제 개인정보를 입력하지 않는다.

통합 검사 두 개는 이름·생년월일·회원 연락처의 처리 및 제거한 범위·지역 분석 값의 보존을 각각 실제 DB SELECT·HTTP GET·Fake 완료로 확인하도록 변경했다. 기존 진행·커서·이어 질문 검사의 이름 입력도 세미콜론으로 구분했다.

전체 명령 `gradlew.bat test integrationTest bootJar --console=plain`은 JDK 21.0.11·Gradle 9.8.2와 사용자가 실행해 둔 PostgreSQL·Mailpit에서 통과했다.

| 단위·설정·MVC·로컬 HTTP stub | 76개 통과, 실패·오류·생략 0 |
| 실제 PostgreSQL·HTTP·Mailpit 통합 | 39개 통과, 실패·오류·생략 0 |

단위 수가 110개에서 76개로 줄어든 것은 기존 범위의 마스킹 검사 53개를 축소 범위 검사 19개로 교체했기 때문이다. 설정 검사 8개와 나머지 단위 검사 49개는 유지한다. 실제 DB·HTTP 통합 검사 개수는 39개로 같다. 테스트는 자신이 만든 데이터·세션만 정리하고 공용 시퀀스를 초기화하거나 되돌리지 않는다.

브라우저·FastAPI·Nginx·운영 HTTPS·부하·프로세스 재시작 장애 검사는 실행하지 않았다.

8080은 이 작업 폴더의 BackendApplication 프로세스인지 확인한 뒤 최신 Fake로 갱신했다. 합성 이름·생년월일·표준 휴대전화·이메일이 가려지고 주민번호·계좌·상세주소·행정동·분석 날짜는 새 범위대로 유지되는지 저장 메시지 전체를 비교했다. 확인용 대화 1개는 해당 회원·UUID로만 삭제하고 세션은 로그아웃했다. 최신 Fake는 8080에 실행 중이다.

## 5. 계약·리뷰 인계

계약 담당자가 다음 설명을 docs/api/ai-agent-panel.md의 범위 표와 OpenAPI의 AgentQuestionRequest.question에 반영해야 한다:

> 서버는 이름·생년월일의 명시 표지 필드와 회원 API 표준 형식의 이메일·휴대전화만 가린 뒤 저장한다. 명시 필드 값은 세미콜론·줄바꿈·입력 끝까지 가리며 구분자 밖의 질문을 보존한다. 그 밖의 식별정보 자동 인식이나 완전한 비식별화를 보장하지 않는다. 질문 본문은 로그에 남기지 않는다.

AgentMessage.content와 ConversationListItem.firstQuestion·ConversationDetail.firstQuestion 설명도 동일한 저장 처리 결과를 참조하게 한다. 사람용 API 명세표·테이블 정의서 설명은 같은 범위로 정리하고, 이미 적용된 V 파일은 주석도 수정하지 않는다.

FE에는 개인정보 입력 자제와 표준 표지·구분자 안내를 인계한다. 이름·주소 표현을 임의로 추가하며 범위를 다시 확장하지 않는다. 실제 AI 전환 시에도 처리 결과 전체가 비식별화됐다고 가정하지 않는다. AI 시간 값·재시작 한계·운영 모드 전달은 이전 인계와 같다.
