## 3. 잠금·오류 격리·진단

### 끝 행 경합

- 메시지 writer의 대화 잠금을 `FOR UPDATE OF c`에서 `FOR KEY SHARE OF c`로 변경했다. 질문 접수의 대화 `FOR UPDATE`는 유지한다.
- KEY SHARE는 대화 삭제·키 변경을 막으면서 트리거의 비키 컬럼 갱신과 호환된다. 잠금 호환성은 [PostgreSQL 17 행 잠금 문서](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)를 확인했다.
- 실제 독립 JDBC 연결 두 개로 이전 FOR UPDATE 순서에서 40P01을 재현했다. eumi_app 연결로 AI와 같은 직접 INSERT 경로를 사용한 검사이며 실제 FastAPI·eumi_ai 계정 연결 검사는 아니다.
- 수정된 writer가 KEY SHARE를 잡은 상태에서 별도 AI 연결이 완료를 먼저 커밋하고, 뒤의 BE 취소 INSERT가 23505가 되어 false를 반환하는 것을 확인했다. 끝 행은 하나다.
- 40P01도 다른 끝 행이 커밋됐다면 false로 처리한다. 아직 끝나지 않았다면 롤백 후 새 트랜잭션에서 한 번만 재시도한다. 관련 없는 23505는 그대로 오류로 남긴다.

### 조회 가용성·로그

- 메시지 조회의 인증·소유권 검사와 실제 SELECT는 정상 오류 처리를 유지한다. 선택적 복구 과정만 예외를 격리해, 복구 쓰기가 실패해도 읽을 수 있는 메시지는 200으로 반환한다.
- AgentDiagnostics는 conversationId·작업명·HTTP 상태 또는 예외 종류만 WARN으로 남긴다. 질문·응답 본문·예외 메시지·스택·쿠키·세션 값은 기록하지 않는다.
- start·status·cancel, 예약 취소 보완, Fake 진행·실패 행 저장, HTTP 전송·파싱·상태 오류에 진단을 추가했다.
- cleanup에서 다른 잠금 칸의 상태를 읽는 cancelling 필드는 volatile로 지정했다. 재시작에 따른 상태 소실 문제를 해결했다고 주장하지 않는다.
- HttpAgentClient는 HTTP/1.1로 고정했다. JDK HTTP stub에서 프로토콜과 Upgrade 헤더 부재를 확인했으며 uvicorn 실연결 결과는 아니다.

## 5. 인프라 인계·남은 것

### 운영 배포 전 필수: AI 모드 전달

현재 `infra/deploy/docker-compose.prod.yml`의 backend environment에는 EUMI_AI_MODE 전달이 없다. 사용자의 수정 범위 규칙에 따라 infra 파일은 직접 수정하지 않았다. Jenkins 배포는 master push(develop → master MR 병합) 때 실행된다. 인프라 담당자가 그 전에 다음 순서로 반영해야 한다.

1. 서버 `.env.config`에 `EUMI_AI_MODE=fake`를 먼저 설정한다. 실제 서버 설정은 이 작업에서 읽거나 수정하지 않았다.
2. 운영 Compose backend environment에 아래 항목을 추가하고 `infra/deploy/.env.config.example`도 맞춘다:

```yaml
EUMI_AI_MODE: ${EUMI_AI_MODE:?.env.config에 EUMI_AI_MODE가 필요합니다}
```

3. Compose는 `env_file`로 자동 전달하지 않는다. 서버 파일의 값이 Compose 보간을 거쳐 backend 컨테이너 environment로 전달되는지 확인한다. 서버 값보다 위 필수 보간이 먼저 반영되면 Compose 해석 단계에서 실패해 web 배포도 함께 실패할 수 있다.
4. 실제 전환 시 `EUMI_AI_MODE=http`, `AI_BASE_URL`, 네 업무 시간 환경변수를 함께 전달한다. 현재 미확정 시간 값을 운영 합의값으로 넣지 않는다.

변수 전달 없이 이 prod 설정을 배포하면 의도대로 기동 실패한다. 서버 값 → Compose 전달·확인 → master 배포 순서를 지킨다. develop 병합만으로 운영 배포가 실행되지는 않는다.
